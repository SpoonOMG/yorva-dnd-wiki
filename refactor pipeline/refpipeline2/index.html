    План: Этап 9 — Разделение NARRATION и NO_ROLL + валидатор уместности UI-действий¶

    Документ для передачи ИИ-агенту. Все решения зафиксированы. Агент не вносит изменений по своему усмотрению. При расхождении с фактами — стоп и отчёт.

    0. Общие правила¶

    Наследуются из основного плана (§0). Дополнения:

    0.1. Контекст¶

    Этапы 1–8 завершены. Фактическое состояние кода (по отчёту агента): - ActionType содержит NARRATION и INVALID, оба маппятся в resolveNoRoll. - IntentType содержит: ATTACK, MOVE, CAST, CHECK, SOCIAL, USE_ITEM, REST, DISMISS_SPELL, DEATH_SAVE, AMBUSH_PREP, LOOT, EQUIP, NARRATION, INVALID. - IntentClassifier используется в ActionParser (гейт 3.5). - StateContextBuilder создаёт CharacterContext и EnemyContext. - IntentValidator уже проверяет базовые прекондиции. - TurnMechanics не имеет флага нарратива.

    0.2. Что запрещено делать без явного указания¶

    • Удалять существующие значения IntentType и ActionType.
    • Менять сигнатуру IntentClassifier.classify(...) иначе, чем описано.
    • Менять промпт IntentClassifier иначе, чем описано.
    • Менять applyStateChanges.
    • Трогать CatalogClassifier и LlmDslTranslator (они @Deprecated).
    • Рефакторить «заодно».

    0.3. Порядок этапов¶

    Строго 9.1 → 9.2 → 9.3 → 9.4 → 9.5 → 9.6. Возврат только через откат коммита.

    0.4. Формат отчёта¶

    Как в §0.5 основного плана.

    3. ЭТАП 9.2: ContextCheckResult — три исхода валидации 🔴¶

    3.1. Цель¶

    Ввести тип результата, различающий «неуместно в контексте» (→ нарратив) и «невозможно по правилам» (→ отказ с причиной).

    3.2. Файлы создать¶

    backend/app/src/main/kotlin/com/yorva/rules/intent/ContextCheckResult.kt

    3.3. Файлы изменить¶

    backend/app/src/main/kotlin/com/yorva/rules/intent/IntentValidator.kt
backend/app/src/main/kotlin/com/yorva/rules/intent/IntentClassifier.kt

    3.4. Шаги¶

    3.4.1. Создать ContextCheckResult.kt: 

    package com.yorva.rules.intent

sealed class ContextCheckResult {
    data class Valid(val intent: Intent) : ContextCheckResult()
    data class WrongContext(val reason: String) : ContextCheckResult()
    data class Impossible(val reason: String) : ContextCheckResult()
}

    3.4.2. В IntentValidator добавить новый метод checkContext(intent, character, enemy): ContextCheckResult, не удаляя существующий validate.

    Существующий validate оставить как есть (обратная совместимость). Новый метод — для этапа 9.

    3.4.3. Логика checkContext по таблице:

    Intent.intent WrongContext (→ NARRATION) Impossible (→ INVALID)
    ATTACK enemy == null actionEconomy.actionUsed; method.id не в inventory
    DODGE enemy == null (не в бою) actionUsed
    DISENGAGE enemy == null actionUsed
    DASH — actionUsed
    HIDE enemy != null и враг видит (нужен флаг из EnemyContext, если его нет — считать всегда WrongContext только вне боя) actionUsed
    HELP нет союзника (если данных нет — считать всегда WrongContext) actionUsed
    AMBUSH_PREP enemy != null (уже в бою) actionUsed
    CHECK — actionUsed
    USE_ITEM method.id == null (не указан предмет) actionUsed; method.id не в inventory
    LOOT нет цели для лута actionUsed
    EQUIP — actionUsed; method.id не в inventory
    CAST — actionUsed; слот недоступен; spell не в spellsKnown
    SOCIAL — —
    DEATH_SAVE не без сознания —
    DISMISS_SPELL нет активной концентрации —
    MOVE — — (движение в 5e бесплатное)
    REST — уже отдыхали сегодня
    NARRATION — —
    INVALID — —

    3.4.4. Для проверок, где нужны данные из CharacterContext/EnemyContext — использовать фактические поля этих классов (по префлайту §1.1). Если поле отсутствует (например, EnemyContext.seesPlayer), не добавлять поле на этом этапе. Вместо этого — считать проверку WrongContext при enemy == null и Valid при enemy != null. Упрощение допустимо, уточнение — отдельный этап.

    3.4.5. В IntentClassifier.classify(...): после получения Intent от LLM и перед возвратом — вызвать intentValidator.checkContext(intent, character, enemy).

    Обработка результата: - Valid → вернуть result.intent как есть. - WrongContext(reason) → вернуть intent.copy(intent = IntentType.NARRATION, reasoning = reason). - Impossible(reason) → вернуть intent.copy(intent = IntentType.INVALID, reasoning = reason).

    Логировать исход через IntentTraceLogger: validationResult = "context_ok" | "context_wrong:${reason}" | "context_impossible:${reason}".

    3.4.6. Не менять сигнатуру classify(...).

    3.5. Тесты¶

    Создать IntentValidatorContextTest.kt: - Тест 1: ATTACK без врага → WrongContext. - Тест 2: ATTACK с врагом, слотом, оружием в инвентаре → Valid. - Тест 3: DODGE вне боя → WrongContext. - Тест 4: DODGE в бою, слот свободен → Valid. - Тест 5: CAST без слота заклинания → Impossible. - Тест 6: DASH при actionUsed = true → Impossible. - Тест 7: AMBUSH_PREP в бою → WrongContext. - Тест 8: NARRATION → Valid. - Тест 9: INVALID → Valid.

    Расширить IntentClassifierTest: - Тест: LLM вернул ATTACK, но enemy = null → classify возвращает Intent(intent = NARRATION, reasoning = <причина>).

    3.6. Acceptance¶

    • ./gradlew :app:build — SUCCESS.
    • ./gradlew :app:test — SUCCESS.
    • В логах при вызове classify с неподходящим контекстом видно validationResult = "context_wrong:...".

    3.7. Запреты¶

    • Не добавлять новых полей в CharacterContext/EnemyContext.
    • Не менять промпт IntentClassifier (кроме списка значений из этапа 9.1).

    5. ЭТАП 9.4: resolveNarration и разведение с resolveNoRoll 🔴¶

    5.1. Цель¶

    NARRATION перестаёт идти через resolveNoRoll. Отдельный путь, который не трогает экономию и не формирует причину отказа.

    5.2. Файлы изменить¶

    backend/app/src/main/kotlin/com/yorva/rules/TurnResolver.kt

    5.3. Шаги¶

    5.3.1. Создать приватный метод resolveNarration(...): 

    private fun resolveNarration(
    req: ActionRequest,
    character: CharacterState,
    enemy: Enemy?
): TurnMechanics {
    return TurnMechanics(
        action = req.raw,
        diceRolls = emptyList(),
        description = req.description ?: "Попытка без механического эффекта",
        stateChanges = emptyList(),
        enemy = enemy,
        enemyDefeated = false,
        manaInsufficient = false,
        manaCost = null,
        droppedItems = emptyList(),
        consumesAction = false,
        dslId = null,
        dslParam = null,
        isNarration = true
    )
}

    Точные поля TurnMechanics — по префлайту §1.1. Если поле называется иначе — использовать фактическое имя, но логика та же: пустые stateChanges, consumesAction = false, isNarration = true.

    5.3.2. В dispatch: - ActionType.NARRATION → вызвать resolveNarration(req, character, enemy). - ActionType.INVALID → вызвать resolveNoRoll(req.description ?: "Не удалось распознать действие"). - ActionType.NO_ROLL → оставить как есть.

    5.3.3. Убедиться, что buildEconomyChanges не добавляет SpendAction/SpendBonusAction для NARRATION. Если dispatch возвращает consumesAction = false, buildEconomyChanges уже не должен добавлять SpendAction. Проверить визуально и тестом.

    5.3.4. Проверить checkActionEconomy: он не должен блокировать NARRATION (нарратив не требует слота). Если блокирует — добавить исключение: 

    if (req.type == ActionType.NARRATION) return null  // не проверяем экономию

    5.4. Тесты¶

    Расширить NarrationInvalidActionTypeTest: - Тест: NARRATION возвращает TurnMechanics(isNarration = true, stateChanges = emptyList(), consumesAction = false). - Тест: NARRATION при character.actionEconomy.actionUsed = true всё равно выполняется (не блокируется). - Тест: NARRATION не добавляет SpendAction в stateChanges. - Тест: INVALID возвращает TurnMechanics(isNarration = false) с описанием причины. - Тест: NO_ROLL ведёт себя как раньше.

    5.5. Acceptance¶

    • ./gradlew :app:build — SUCCESS.
    • ./gradlew :app:test — SUCCESS.
    • NARRATION не трогает actionEconomy.

    - Если isNarration == false — ничего не добавлять (обратная совместимость).

    8.3. Функциональные сценарии (ручная проверка)¶

    Проверить в UI или через API:

    1. «атакую» без врага → ход проходит, нарратив описывает попытку, HP врага не меняется, экономия действия не списывается.
    2. «уклоняюсь» вне боя → нарратив «не от кого уклоняться», экономия не списывается.
    3. «отхожу» вне боя → нарратив «разрывать нечего», экономия не списывается.
    4. «рвусь вперёд» (рывыок) → слот действия списывается, движение происходит.
    5. «скрываюсь» вне боя → слот действия списывается, скрытность применяется.
    6. «помогаю» без союзника → нарратив «некому помочь», экономия не списывается.
    7. «устраиваю засаду» в бою → нарратив «не до засады, бой идёт», экономия не списывается.
    8. «ищу следы» → слот действия списывается, проверка совершается.
    9. «использую зелье» с зельем в инвентаре → слот списывается, HP восстанавливается.
    10. «использую зелье» без зелья → отказ с причиной, экономия не списывается.
    11. «кастую fireball» без слота → отказ с причиной, экономия не списывается.
    12. «отдыхаю» → короткий отдых запускается.
    13. «я открываю для себя много новых идей» → NARRATION, механики нет, экономия не списывается.
    14. «абракадабра какджасд» → INVALID, отказ, экономия не списывается.
    15. «открываю огонь по упырю» в бою → ATTACK, урон нанесён, экономия списана.

    Ключевые проверки во всех сценариях «WrongContext» и «INVALID»: слот действия не должен списываться.

    8.4. Отчёт¶

    Агент возвращает сводный отчёт по форме §0.5 основного плана, плюс результаты ручных сценариев из 8.3 (если запускал интеграционные тесты, дублирующие эти сценарии — приложить их).

    9. Чего в этом плане нет¶

    • Не добавляется ActionType.HELP. Если его нет — маппинг в NO_ROLL, отдельный этап позже.
    • Не удаляются @Deprecated-классы CatalogClassifier и LlmDslTranslator.
    • Не меняется NarratorOutput и structured output нарратора (это отдельный этап 6, уже сделан).
    • Не расширяется EnemyContext полями вроде «видит ли игрока» — упрощение допустимо, уточнение отдельно.
    • Не трогается SemanticActionNormalizer, SemanticDictionary, whitelist.
    • Не меняется формат TurnResponse.
    • Не реализуется уточняющий вопрос («что именно использовать?»). Если USE_ITEM без предмета → WrongContext → нарратив.
