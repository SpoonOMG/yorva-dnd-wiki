    ADR-0019: Activatable / AbilityResolver — единый контракт активации способностей¶

    Status¶

    Accepted

    Context¶

    Суть проблемы¶

    В движке способности разных источников резолвятся разрозненно и без общего контракта:

    • Классовые фичи активируются через ClassFeatureHelper.detectFeature — поиск фичи по ключевому слову в тексте действия (classes/ClassFeatureHelper.kt:22-37), проверка стоимости (canAfford, :42-50) и трата (spendCost, :75-85). Эффект фичи в контракте не декларирован — только стоимость (действие + классовый ресурс); эффект отдаётся нарративно (LLM).
    • Заклинания резолвятся двумя путями: legacy resolveSpellOrSummon (rules/TurnResolver.kt:1872-1946, мана) и resolveCastSpell (:1954-2008, через SpellService.canCast/castSpell + слоты).
    • Предметы — resolveUseItem (TurnResolver.kt:2144-2209) с захардкоженной логикой зелье/свиток (ItemBonuses.hpBonus/damageBonus).
    • Враги — Enemy.features: List<String> (rules/GameState.kt:697) — строковые коды архетипа, резолвятся ad-hoc в applyEnemyTurn.

    Интерфейса Activatable и резолвера AbilityResolver в коде нет (grep = 0). Единственная модель, несущая поля контракта активации, — ClassFeature (classes/CharacterClass.kt:51-65: actionType, resourceId, choice/options). Spell, Feat, SkillDef — параллельные модели без общего контракта.

    Канон 5e (PHB)¶

    • Способности бывают: spells (заклинания), class features (классовые умения), feats (черты), racial traits (расовые черты), item abilities (свойства предметов), monster actions (действия монстров).
    • У каждой: действие (action / bonus action / reaction / free), ресурс (слот заклинания / классовый ресурс / заряды / без лимита), эффект (урон / состояние / лечение / бафф / утилита).
    • «Activatable» — доменный концепт объединения этих категорий, не термин 5e.

    Факты (файл:строка)¶

    Сайты активации и стоимость¶

    • Фичи: ClassFeatureHelper.detectFeature фильтрует cls.features по actionType != null && != PASSIVE и матчит actionLower.contains(feature.name.lowercase()) (ClassFeatureHelper.kt:24-36). canAfford проверяет слот действия (:44-48) и классовый ресурс (hasResource, :52-70). spendCost эмитит SpendAction/SpendBonusAction/SpendReaction + SpendClassResource (:75-85). Вызовы — TurnResolver.kt:271-272 (детект + canAfford) и :474 (buildEconomyChanges → spendCost).
    • Ресурсы: ClassResources (GameState.kt:1409-1437) — rage/ki/bardicInspiration/channelDivinity/ wildShape/actionSurge/secondWind/layOnHands/sorceryPoints/pactSlots/arcaneRecovery/naturalRecovery. StateChange.SpendClassResource (:1258), SpendSpellSlot (:1199), SpendMana (:1197).
    • Экономия действий — два механизма: (а) ActionEconomyRegistry (rules/economy/ActionEconomyRegistry.kt, action_economy.yml → EconomySlot по ActionType/dsl/классу); (б) ClassFeatureHelper (маппинг FeatureActionType → слот). Дубль маппинга «слот → Spend*» есть и в buildEconomyChanges (TurnResolver.kt:456-472), и в ClassFeatureHelper.spendCost (:76-84).
    • FeatureRegistry не существует; фичи парсятся в ClassRegistry.kt:78 (FeatureActionType.valueOf(at.uppercase())).

    Хранение способностей у персонажа¶

    CharacterState не имеет поля features — классовые фичи выводятся из canonicalClassId → ClassRegistry → CharacterClass.features. Есть: feats (:453), spellsKnown (:455), spellbook (:456), preparedSpells (:457), l1Choices (:488), classResources (:479), actionEconomy (:474).

    StateChange.ActivateFeature¶

    Определён (GameState.kt:1269 — data class ActivateFeature(val featureName: String)), но никто его не эмитит — только применяется в SessionService.kt:2716. По сути «мёртвый» вариант StateChange.

    Дубль #5 — резолверы «строка → ability/attribute»¶

    Один и тот же маппинг имени характеристики/навыка повторён в 6+ местах:

    Резолвер Место Что делает
    attributeForSkill(skill) TurnResolver.kt:1263-1270 код навыка → str/dex/int/wis/cha
    detectAttribute(action, character) TurnResolver.kt:3089-3100 regex → имя + mod (default Dex)
    detectCastingAttribute(action, character) TurnResolver.kt:3103-3110 regex → ментальная (default Int)
    spellMod = when(spellcastingAbility.uppercase()) SessionService.kt:122 строка → модификатор
    SkillDef.ability skills/SkillRegistry.kt:9-16 поле способности навыка
    CharacterClass.primaryAbility/spellcastingAbility classes/CharacterClass.kt:13 строковые поля класса
    getAbilityScore(attributes, ability) rules/SavingThrowResolver.kt:91 имя → значение

    Это тот самый дубль #5 из ADR-0011 (Draft, развилка K enum Ability, L alias-резолвер). ADR-0017 (SpellcastingStats.of + SpellcastingAbility) принят, но в коде пока не реализован — заклинательная способность остаётся сырой строкой CharacterClass.spellcastingAbility + when(...) в SessionService.

    Соседние решения (не переизобретать)¶

    • ADR-0010 §9 — модель хода/раунда, экономия действий, castingTime → трата слота.
    • ADR-0012 — enum DamageType + DamageResolver.apply(raw, type, target).
    • ADR-0013 — enum StatusId + ConditionResolver + StatusContext.
    • ADR-0014 — StatusInstance + ConditionLifecycle.removeAll.
    • ADR-0015 — ExhaustionResolver.effectsFor.
    • ADR-0016 — слоты заклинаний как единственный ресурс.
    • ADR-0017 — SpellcastingStats.of + enum SpellcastingAbility (связан с дублем #5).
    • ADR-0018 — LevelUpApplier (применение фич при level-up; авто применяет только пассивные).
    • ADR-0011 Draft — enum Ability{STR,DEX,CON,INT,WIS,CHA} + alias-резолвер (= дубль #5). Настоящий ADR может закрыть дубль #5 через AbilityResolver.resolveAbility.

    Decision¶

    Приняты следующие решения (A–P):

    • A = A3 — интерфейс Activatable как чистые данные (без поведения) + внешний AbilityResolver. Консистентно с DamageResolver/ConditionResolver (ADR-0012/0013).
    • B = B1 — object AbilityResolver (stateless), по образцу DamageResolver/ConditionResolver.
    • C = C3 — гибрид: AbilityResolver — фасад (валидация стоимости + экономия действий), делегирует эффект по kind.
    • D = D1 — обернуть существующие модели адаптером (Activatable как view над Spell/ClassFeature/Feat). Модели не переписывать.
    • E = E2 — CharacterState.activatableIds: List<ActivatableId>. Реестр — источник правды.
    • F = F1 — sealed AbilityCost: SpellSlot(level) | ClassResource(id, amount) | Charges(n) | Free.
    • G = G3 — castingTime для заклинаний + actionType для остальных. Унификация единого actionType (G2) — ФАЗА 3.
    • H = H1 — активация возвращает List<StateChange>.
    • I = I1 — AbilityResolver.resolveAbility + enum Ability { STR, DEX, CON, INT, WIS, CHA }. Перенос из ADR-0011 (развилка K). Закрывает дубль #5 (7 резолверов «строка → ability»).
    • J = J2 — расовые черты (racial traits) — ФАЗА 3. Контракт Activatable проектируется расширяемым.
    • K = K2 — ItemAbility — отдельная подсистема. Общий AbilityCost/AbilityEffect — да, resolver — нет.
    • L = L2 — Enemy.features остаётся ad-hoc. Унификация под Activatable — ФАЗА 2+.
    • M = M3 — ClassFeatureHelper переводится постепенно. Фасад сейчас, переходы сайтов — ФАЗА 2.
    • N = N1 — только контракт + скилет resolver, без реализации эффектов. Реализация — ФАЗА 2.
    • O = O3 — маппинг «слот → Spend*» выносится в ActionEconomyRegistry. TurnResolver.buildEconomyChanges + ClassFeatureHelper.spendCost консолидируются.
    • P = P2 — StateChange.ActivateFeature включается в контракт Activatable (эмитится AbilityResolver при активации способности с kind = FEATURE).

    Обязательные уточнения¶

    • ADR-0019 закрывает дубль #5 из ADR-0011 (7 резолверов «строка → ability»). Enum Ability определён здесь (перенос из ADR-0011, развилка K).
    • ADR-0019 закрывает НОВЫЙ дубль O — маппинг «слот → Spend*»: TurnResolver.kt:456-472 + ClassFeatureHelper.kt:76-84 → ActionEconomyRegistry.
    • ADR-0011 пересматривается: дубль #5 закрыт здесь; в ADR-0011 остаётся 5 дублей. Финализация ADR-0011 — после 0019.
    • N1 — контракт + скилет resolver, без реализации. Реализация адаптеров Spell/ClassFeature — ФАЗА 2.
    • P2 — StateChange.ActivateFeature эмитится AbilityResolver.
    • D1 — обернуть модели, не переписывать.
    • J2 — racial traits откладываются, контракт расширяемый.

    Proposed Options¶

    A. Форма Activatable¶

    • A1 — интерфейс: interface Activatable { id; name; actionType; cost: AbilityCost?; resolve(...) → List<StateChange> }.
    • Минимальный контракт, реализуют существующие модели (Spell/ClassFeature/…). — Логику эффекта приходится тащить в каждую модель или во внешний резолвер; данные (описания) и поведение смешиваются.
    • A2 — sealed class / data class с дискриминатором: единый тип с полем kind (SPELL/FEATURE/ITEM/…)
    • общие поля + специфичные. + Один тип для хранения List<Activatable>; простая (де)сериализация. — Нужна миграция существующих моделей (D2/D3); риск раздутого типа.
    • A3 — интерфейс-«описание» + внешний резолвер: Activatable остаётся чистыми данными (без поведения), AbilityResolver применяет по kind. + Чистое разделение данных/поведения; консистентно с ADR-0012/0013 (Resolver-паттерн). — Два новых типа вместо одного.

    B. Форма AbilityResolver¶

    • B1 — object AbilityResolver: как DamageResolver/ConditionResolver. + Консистентно с соседними резолверами; нет DI. — Трудно мокать/параметризовать.
    • B2 — Spring-бин @Service: как SpellService/ActionEconomyRegistry. + DI, тестируемость, инжекция реестров. — Тянет зависимость на Spring в домен.
    • B3 — распределённые резолверы по типу (SpellActivator, FeatureActivator, …). + Каждый тип изолирован. — Дублирование общей рамки (cost/action economy), расползание контракта.

    C. Роль AbilityResolver¶

    • C1 — единая точка: активировать(activatable, target, state) → List<StateChange>; внутри — cost + economy + эффект. + Один вход для всех способностей; проще валидировать. — Сложный внутренний switch; надо тянуть все под-резолверы.
    • C2 — только контракт: резолвер задаёт сигнатуру/типы, активация по kind в TurnResolver.
    • Минимальный scope (N1). — Не закрывает дубль экономии/эффектов, остаётся ad-hoc.
    • C3 — гибрид: AbilityResolver — фасад (общая рамка: валидация cost + economy), делегирует эффект по kind. + Баланс единообразия и изоляции. — Сложнее C1/C2.

    D. Миграция существующих моделей¶

    • D1 — обернуть: Activatable как обёртка/адаптер над существующими Spell/ClassFeature. + Не трогает публичные модели. — Двойная модель данных, синхронизация.
    • D2 — переписать: заменить модели на Activatable-подтипы. + Чисто, одна модель. — Крупный breaking change, затрагивает ClassRegistry/SpellService/сериализацию.
    • D3 — параллельно: старые модели остаются, новый контракт добавляется рядом и постепенно переводит сайты активации. + Инкрементально, безопасно. — Временная избыточность, два пути заклинаний и так уже есть.

    E. Хранение активаций у персонажа¶

    • E1 — CharacterState.features: List<Activatable>: материализовать способности в состоянии. + Быстрый доступ, не надо ходить в реестр. — Дублирование данных реестра; рассинхрон при level-up.
    • E2 — activatableIds: List<ActivatableId>: ссылки на реестр, состояние хранит только id. + Один источник правды (реестр), маленькое состояние. — Каждый резолв требует lookup по реестру.
    • E3 — без хранения (derived): как сейчас — выводить из canonicalClassId/spellsKnown/инвентаря.
    • Ноль миграции. — Разные источники остаются разрозненными (главная боль, которую ADR хочет снять).

    F. Ресурсы/стоимость¶

    • F1 — sealed AbilityCost: SpellSlot(level) | ClassResource(id, amount) | Charges(n) | Free.
    • Единый тип стоимости, покрывает все категории. — Новый тип, миграция ClassFeature.resourceId.
    • F2 — поля на Activatable (resourceId, amount, usesSpellSlot). + Проще, нет sealed-иерархии. — Нестрогая типизация, комбинации «resourceId + slot» не выразимы.
    • F3 — cost как часть ActionEconomy: стоимость = слот действия + опциональный ресурс. + Меньше новых типов. — Смешивает «чем платить» (ресурс) и «что тратим» (действие).

    G. Экономия действий¶

    • G1 — через ActionEconomyRegistry: как сейчас (ActionType/dsl → EconomySlot). + Уже работает для глобальной экономии. — Не связано с FeatureActionType фич; два маппинга остаются.
    • G2 — поле actionType на Activatable: единое поле (ACTION/BONUS_ACTION/REACTION/FREE/PASSIVE).
    • Одна точка правды для способности. — Дублирует FeatureActionType и CastingTime/UseAction.
    • G3 — castingTime для заклинаний + поле для фич: заклинания — CastingTime enum, фичи/предметы — actionType. + Минимальная миграция. — Разные поля для разных категорий.

    H. Связь с Condition/DamageResolver (эффект)¶

    • H1 — активация возвращает List<StateChange>: (Damage/ApplyStatus/Heal/…). + Консистентно с тем, как TurnResolver уже работает; Damage/Condition резолверы остаются как есть. — Эффект не типизирован на уровне контракта.
    • H2 — Activatable сам применяет эффекты (mutating): способность мутирует CharacterState/Enemy.
    • Компактно. — Ломает иммутабельность, трудно тестировать.
    • H3 — типизированный AbilityEffect (sealed): активация возвращает AbilityEffect, который транслируется в StateChange. + Строгий контракт эффекта. — Дополнительный слой между активацией и StateChange.

    I. AbilityResolver vs дубль #5¶

    • I1 — объединить в AbilityResolver.resolveAbility: единый enum Ability (ADR-0011 K) + резолв строки/навыка/класса/заклинателя. + Закрывает дубль #5 раз и навсегда. — Большой scope, тянет ADR-0011/0017.
    • I2 — enum Ability + Enum.valueOf: только тип-безопасность, без общего резолвера. + Дёшево. — Дубль «строка→mod» остаётся в SessionService/TurnResolver.
    • I3 — оставить как есть: ADR-0019 не трогает дубль #5. + Меньше scope. — Дубль сохраняется (противоречит цели консолидации).

    J. Расовые черты (racial traits)¶

    • J1 — вводить RacialTrait как Activatable сейчас. + Полный охват канона. — Расы ещё не реализованы (ФАЗА 3), преждевременно.
    • J2 — отложить в ФАЗУ 3: контракт Activatable проектируется так, чтобы racial traits легли позже.
    • Без преждевременной работы. — Нужно гарантировать расширяемость контракта сейчас.

    K. Item abilities¶

    • K1 — ItemAbility как Activatable: useAction/bonuses → AbilityCost + AbilityEffect.
    • Единый контракт. — Предметы — не «способности персонажа»; особая механика потребления.
    • K2 — отдельная подсистема предметов: resolveUseItem остаётся, контракт только для spell/feature.
    • Не тянет предметы в способности. — Дубль активации остаётся.

    L. Enemy actions¶

    • L1 — унифицировать под Activatable: Enemy.features → List<Activatable>. + Один резолвер для игрока и врага. — Враг — не CharacterState; другой lifecycle/ресурсы.
    • L2 — оставить отдельно: враг резолвится ad-hoc. + Меньше scope. — Контракт покрывает не весь канон.

    M. Миграция ClassFeatureHelper/FeatureRegistry¶

    • M1 — удалить → AbilityResolver: detectFeature/canAfford/spendCost заменяются резолвером.
    • Убирает ad-hoc дубль. — Полная переписка сайтов активации фич.
    • M2 — оставить фасадом: ClassFeatureHelper делегирует в AbilityResolver. + Совместимость. — Временный слой.
    • M3 — постепенно: переводить сайты по одному. + Инкрементально. — Длительный переходный период.

    N. Scope ADR-0019¶

    • N1 — только контракт + AbilityResolver (интерфейс/типы, без реализации эффектов). + Минимальный, быстрый. — Не даёт выгоды сразу (сайты остаются ad-hoc).
    • N2 — контракт + реализация для Spell/ClassFeature. + Снимает главный дубль. — Средний scope.
    • N3 — всё сразу (spell/feature/feat/item/enemy). + Полный охват. — Большой, рискованный, тянет ФАЗУ 3.

    O. Дубль маппинга «слот → Spend*»¶

    • O1 — консолидировать в AbilityResolver (часть C3): фасад сам эмитит Spend* по слоту. + Одна точка «стоимость → StateChange». — Смешивает экономию действий с контрактом способностей.
    • O2 — оставить как есть: TurnResolver.buildEconomyChanges + ClassFeatureHelper.spendCost остаются.
    • Ноль изменений. — Дубль сохраняется (две копии одного маппинга).
    • O3 — вынести в ActionEconomyRegistry: registry — единственный владелец маппинга «слот → Spend*».
    • Владелец слотов отвечает за их трату; консистентно с ADR-0010 §9. — Правки в двух call-sites.

    P. StateChange.ActivateFeature (мёртвый)¶

    • P1 — удалить как мёртвый: StateChange.ActivateFeature (GameState.kt:1269) никто не эмитит.
    • Чисто, убирает dead code. — Ломает совместимость, если он используется где-то вне TurnResolver.
    • P2 — включить в контракт Activatable: AbilityResolver эмитит ActivateFeature(featureName) при активации способности с kind = FEATURE. + Оживляет существующий StateChange, даёт трейс активации. — Нужно согласовать семантику (когда/что эмитится).
    • P3 — оставить как есть: не трогать. + Ноль изменений. — Dead code остаётся, контракт неполон.

    Consequences¶

    Плюсы¶

    • Единый контракт Activatable для всех способностей (spell/feature/feat + расширяемый под racial trait).
    • AbilityResolver — единый фасад активации (стоимость + экономия действий + делегирование эффекта).
    • Дубль #5 закрыт: 7 резолверов «строка → ability» → 1 (resolveAbility + enum Ability).
    • Дубль O закрыт: маппинг «слот → Spend*» — единая точка в ActionEconomyRegistry.
    • Dead code StateChange.ActivateFeature оживлён (P2) — трейс активации фич.
    • Enum Ability — типобезопасность вместо строковых маппингов.
    • sealed AbilityCost — единая строго типизированная стоимость (слот/ресурс/заряды/free).

    Минусы¶

    • AbilityResolver — новый компонент, требует тестов и инжекции в TurnResolver.
    • Activatable как обёртка (D1) — временная двойная модель данных до полной миграции.
    • Enum Ability — перенос из ADR-0011 (уменьшает scope ADR-0011).
    • N1 — реализация отложена в ФАЗУ 2; выгода от контракта не сразу материализуется.

    Риски и митигация¶

    • D1 обёртка может рассинхронизироваться с базовой моделью → unit-тесты на каждой обёртке (Spell→Activatable, ClassFeature→Activatable, Feat→Activatable).
    • I1 резолвер становится широким (ability + abilityMod + …) → разделение на resolveAbility + resolveAbilityMod (+ отдельные приватные маппинги).
    • O3 правки в двух call-sites (buildEconomyChanges + spendCost) → один общий тест на оба.

    Отложено¶

    • Реализация адаптеров Spell/ClassFeature — ФАЗА 2.
    • RacialTrait — ФАЗА 3.
    • ItemAbility resolver — ФАЗА 2+ (общие AbilityCost/AbilityEffect — сейчас).
    • Унификация Enemy под Activatable — ФАЗА 2+.
    • G2 (единый actionType для всех категорий) — ФАЗА 3.

    Untouched in this ADR¶

    • Расы / фоны / скиллы — ФАЗА 3 (см. развилку J2).
    • Сейв-DC / мана / XP — закрыты соседними ADR (0016/0017/0018).
    • ADR-0011 — не финализируется здесь; ADR-0019 закрывает дубль #5 (7 резолверов), финализация ADR-0011 — после 0019 (в нём остаётся 5 дублей).
    • Реализация AbilityResolver в коде — ФАЗА 2 (N1 — только контракт + скилет).
    • RacialTrait — ФАЗА 3.
    • ItemAbility resolver — ФАЗА 2+ (общие AbilityCost/AbilityEffect — в контракте сейчас).
    • Enemy.features — ad-hoc сейчас (L2), унификация — ФАЗА 2+.
    • G2 (единый actionType) — ФАЗА 3 (G3 — castingTime + actionType сейчас).
    • Переписывание моделей Spell/ClassFeature/Feat — не входит (D1 — обёртка, не переписывание).
