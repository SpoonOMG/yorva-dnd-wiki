    ADR-0025: Выборы при создании и level-up (ClassChoice) — реестр + pendingChoices¶

    Status¶

    Accepted

    Context¶

    Выборы игрока сегодня — два разных механизма: мягкое заполнение дефолтами на L1 и жёсткая валидация с исключением на level-up; состояние хранит результаты в строковых полях без pending-контракта. Собранные факты (файл:строка):

    Выборы сегодня¶

    Проблема¶

    Нет единой формы выбора: что выбирается, сколько и куда применяется — закодировано в if (feature.name == …) в двух местах (resolveL1Choices, LevelUpService.levelUp) с разной строгостью. Новая выборная фича = новый спецслучай + риск рассинхрона L1/level-up. Нужны: sealed-форма выбора, реестр choices: + резолвер применения/валидации, pending-контракт симметрично ASI — и регистрация нового дубля в ADR-0011.

    Прецеденты¶

    • ADR-0018 D1/E1 — pendingASI: инкремент из cls.asiLevels, остановка каскада, allocateASI + gainXp(0) (факты #6–7). D1/E1 0025 — зеркало.
    • ADR-0023 — ChoiceClassFeature как форма фичи; count — в FeatureChoice (факт #9: maxChoices); H1 Expertise/doubleProficiency.
    • ADR-0020 F1 — RaceResolver: stateless object применения (образец для C1).
    • ADR-0024 A2 — секция в classes.yml + реестр (образец для A2).

    Канон D&D 5e (PHB гл.3 «Classes», гл.4 «Backgrounds», гл.6 «Customization»)¶

    Fighting Style (Fighter L1/Paladin L2/Ranger L2 — 1 из списка); Expertise (Rogue L1/Bard L3 — 2 навыка, ×2 PB; ещё 2 на L6); Metamagic (Sorcerer L3 — 2 опции, +1 на L10/L17); Eldritch Invocations (Warlock L2 — 2+, рост по уровням); Maneuvers (Battle Master L3 — 3 приёма + 4 кости d8); tool proficiencies (класс/предыстория); ASI/feat (гл.6); Retraining — опциональное правило Tasha's (вне PHB-ядра).

    Decision¶

    1. Место хранения (A2)¶

    Секция choices: в classes.yml + ClassChoiceRegistry.kt. Симметрия ADR-0023 A2 / ADR-0024 A2 — без второго источника. choices: ссылается на ChoiceClassFeature из 0023 (форма фичи — там, форма выбора — здесь):

    choices:
  fighting_style_fighter: { kind: FIGHTING_STYLE, count: 1, options: [defense, dueling, …] }

    Допарсинг choice в SubclassRegistry (факт #10) — предусловие для ManeuverChoice (Battle Master — подкласс), входит в цикл 3.4. Пробел «Экспертиза (2)» без choice-секции (факт #11) закрывается миграцией данных.

    2. Форма выбора (B1)¶

    sealed interface ClassChoice + 7 подтипов — симметрично ClassFeature B1. Обоснование sealed: разная природа — что выбирается (навыки/стиль/метамагия), сколько (count) и что делают с выбранным (×2 PB / эффект воззвания / манёвр):

    sealed interface ClassChoice {
    val id: String
    val count: Int          // сколько опций выбрать (G1)
    val options: List<ChoiceOption>
}
data class SkillChoice(/* … */) : ClassChoice        // Rogue/Bard — N из списка навыков
data class ExpertiseChoice(/* … */) : ClassChoice    // Rogue/Bard — N навыков → doubleProficiency
data class FightingStyleChoice(/* … */) : ClassChoice // Fighter/Paladin/Ranger — 1 из списка
data class MetamagicChoice(/* … */) : ClassChoice    // Sorcerer — 2+ из списка
data class InvocationChoice(/* … */) : ClassChoice   // Warlock — N из списка
data class ManeuverChoice(/* … */) : ClassChoice     // Battle Master — 3 из списка
data class ToolChoice(/* … */) : ClassChoice         // Rogue/Bard — tool proficiency (tools.yml)

    Метамагия/воззвания/манёвры сегодня — заделы (факт #12): форма вводится сейчас, опции наполняются в 3.4 (данные) и позже (эффекты — вне 0025).

    3. Применение при создании (C1)¶

    Новый CharacterCreationService + ClassChoiceResolver.apply(state, choice, picks). Не сваливать в SessionService (там уже 3983 строки; resolveL1Choices — 75 строк спецслучаев, факт #3). Stateless object, симметрично RaceResolver (ADR-0020 F1). resolveL1Choices мигрирует в резолвер в 3.4 (см. J1); мягкая семантика L1 (дефолты, факт #3) сохраняется как режим резолвера.

    4. Применение при level-up (D1)¶

    LevelUpApplier + pendingChoices. Симметрично pendingASI (ADR-0018 D1): при получении ChoiceClassFeature — pendingChoices += choice, каскад останавливается; allocateChoice резюмирует каскад (зеркало allocateASI + gainXp(0), факт #7). allocateASI — прецедент тестовой матрицы. Примечание: сегодня LevelUpApplier выборы не трогает (факт #8) — D1 расширяет его контракт первым выборным полем; ручной levelUp (факт #1) делегирует валидацию резолверу (см. J1).

    5. Окно выбора (E1)¶

    Жёсткая остановка level-up (break в каскаде — зеркало факта #6). UI должен закрыть pendingChoices до следующего action. Панель выбора уже есть (факт #14: FeatureChoicePanel, та же форма Record<string, string[]>), но pending-потока нет — UI-часть (модал блокировки) — ФАЗА 6 (frontend), backend-часть (остановка + allocateChoice) — цикл 3.4.

    6. Валидация (F1)¶

    ClassChoiceResolver.validate(choice, picks) — серверная, источник истины. Клиентская валидация — UX-подсказка. Невалидный выбор → ошибка 400 (IllegalArgumentException, маппинг уже есть — факт #15), ждать новых picks. НЕ CharacterDeadException (факт #15: другой путь — мёртвый персонаж). Строгость унифицируется в жёсткую (уровень факта #1); мягкие дефолты остаются только режимом создания (факт #3, см. C1).

    7. Мультивыбор (G1)¶

    ChoiceClassFeature.count: Int (фактически уже FeatureChoice.maxChoices, факт #9: Metamagic 2 — задел :1104-1106, Maneuvers 3, Expertise 2 :273-275). Выбор = Set<String> picks. Валидатор: picks.size == count (+ каждый id ∈ options). Ошибка в count → застревание (см. Риски).

    8. Expertise (H1)¶

    Модификатор doubleProficiency. Симметрично ADR-0023 H1. Применение — в TurnResolver (сегодня :123 захардкожено): ClassChoiceResolver возвращает expertiseSkills: Set<String>, TurnResolver читает из state (тот же Set, что сегодня в state.expertiseSkills, — миграция без смены контракта чтения). Аналогично fightingStyle: String → значение из FightingStyleChoice (факт #5: поле остаётся, источник меняется).

    9. Retraining (I1)¶

    PHB-optional (Tasha's) — НЕ поддерживаем в 0025. Игрок не перевыбирает. Зафиксировано в Отложено (post-MVP). Форма ClassChoice перевыбор не запрещает технически — решение продуктовое, не техническое.

    10. Дубль featureChoices (J1)¶

    LevelUpService.featureChoices (:136-172, факт #1) → ClassChoiceRegistry. Регистрируется в ADR-0011 как новый дубль (следующий номер — #8; O занят): «ручной level-up ↔ авто-каскад — два пути применения выборов». Сама запись — отдельным docs-коммитом после реализации (аналогично ADR-0020 J1 / ADR-0023 J1 / ADR-0024 H1). Правило ADR-0011: новый дубль — с пометкой Resolved in ADR-0025.

    11. Объём цикла (K1)¶

    Только ADR. Реализация (ClassChoiceRegistry, ClassChoiceResolver, CharacterCreationService, pendingChoices, allocateChoice) — цикл 3.4.

    Proposed Options¶

    A. Место хранения. - A1: отдельный choices.yml — второй источник (отклонено в 0023 A1/0024 A1 тем же аргументом). - A2: секция choices: в classes.yml + ClassChoiceRegistry.kt — рекомендация архитектора. Симметрия 0023/0024. - A3: выборы только в коде (enum) — данные PHB в коде, правка = релиз.

    B. Форма выбора. - B1: sealed (7 подтипов) — рекомендация архитектора. Природа выбора — в типе; исчерпывающий when в резолвере. - B2: плоский FeatureChoice + kind-строка — сегодня так (факт #9); строковые ветви расползаются (факт #3). - B3: по классу-наследнику на механику без общего интерфейса — нет общего контракта для реестра/валидатора.

    C. Применение при создании. - C1: новый CharacterCreationService + ClassChoiceResolver.apply — рекомендация архитектора. SessionService не растёт; stateless — симметрия RaceResolver. - C2: оставить в SessionService.resolveL1Choices — +75 строк спецслучаев уже там (факт #3); файл 3983 строки. - C3: выборы при создании — в LevelUpService — смешение создания и роста.

    D. Применение при level-up. - D1: pendingChoices + остановка каскада + allocateChoice — рекомендация архитектора. Зеркало pendingASI (факты #5–7). - D2: требовать все выборы синхронно в LevelUpRequest (как сегодня, факт #1) — авто-каскад (факт #6) проскакивает выборы без pending. - D3: выборы только нарративом (LLM) — механика не применяется вообще.

    E. Окно выбора. - E1: жёсткая остановка (break), UI закрывает до следующего action — рекомендация архитектора. Симметрия ASI-остановке. - E2: каскад продолжает, выборы копятся (зеркало ADR-0018 E2) — игрок играет с неприменёнными фичами. - E3: без остановки, выборы теряются — потеря данных игрока.

    F. Валидация. - F1: серверная validate, 400 + повтор — рекомендация архитектора. Маппинг уже есть (факт #15). - F2: только клиентская — невалидный state в БД. - F3: мягкая везде (дефолты как на L1) — игрок не узнаёт об ошибке; тихая подмена выбора.

    G. Мультивыбор. - G1: count + Set<String> picks + size == count — рекомендация архитектора. maxChoices уже в данных (факт #9). - G2: список без проверки размера — недобор/перебор молча проходят. - G3: по одному запросу на опцию — N round-trip'ов на Metamagic.

    H. Expertise. - H1: doubleProficiency из резолвера, чтение из state — рекомендация архитектора. Контракт чтения не меняется (митигация SkillRoll-риска). - H2: оставить хардкод :123 + строковое поле — новые источники экспертизы (Bard L3) = новые if. - H3: экспертиза вычислением из l1Choices на лету — чтение дороже, кэш-расчёты в горячем пути бросков.

    I. Retraining. - I1: не поддерживать (post-MVP) — рекомендация архитектора. - I2: поддержать сразу — тянет версионирование выборов + UI отката. - I3: умолчать — решение не зафиксировано, реализатор угадывает.

    J. Дубль. - J1: регистрировать (#8, Resolved in ADR-0025, запись после реализации) — рекомендация архитектора. Аналогично 0020/0023/0024. - J2: не регистрировать — нарушение правила ADR-0011. - J3: резолвить записью сейчас — преждевременно, реестра нет.

    K. Объём. - K1: только ADR; реализация — 3.4 — рекомендация архитектора. - K2: ADR + частичная реализация без реестра — форма без источника. - K3: полный цикл с реализацией — нарушает «один цикл = один фокусный шаг».

    Consequences¶

    Плюсы¶

    • Choice-механики (Fighting Style, Expertise, Metamagic, Invocations, Maneuvers, Tool) — типизированы, единая форма (B1).
    • Симметрия с ADR-0018 (pendingASI) → pendingChoices (D1/E1).
    • Дубль ручной/авто-путей фиксируется проектом (J1).
    • CharacterCreationService получает чёткий контракт (ClassChoiceResolver) вместо 75 строк when (C1).

    Минусы¶

    • Миграция: fightingStyle: String → FightingStyleChoice; expertiseSkills → ExpertiseChoice (поля остаются, источник меняется).
    • ClassChoiceRegistry — седьмой регистр по паттерну.
    • UI-часть (закрытие pendingChoices) — ФАЗА 6; до тех пор backend останавливает каскад, но игрок может застрять в UI без модала.

    Риски¶

    • Зеркало pendingASI-риска: не сброшен pendingChoices → каскад не продолжится, level-up застревает. Митигация: тесты по образцу allocateASI (факт #7; матрица: сумма/кап/повторный вызов).
    • Multiselect (Metamagic 2 / Invocations N / Maneuvers 3): ошибка в count → застревание. Митигация: G1 (count в данных, не в коде)
    • валидатор size == count.
    • Expertise-миграция может задеть SkillRoll-тесты (TurnResolver.kt:123, L1FeatureChoiceTest). Митигация: H1 — резолвер возвращает тот же Set<String>, контракт чтения не меняется.
    • L1-мягкость vs level-up-жёсткость (факты #3 vs #1): унификация в жёсткую меняет поведение создания при невалидном вводе (было — тихие дефолты). Митигация: C1 — мягкость остаётся режимом создания.
    • «Экспертиза (2)» L6 без choice-секции (факт #11): если миграция пропустит — Rogue L6 без выбора. Митигация: чек-лист данных в 3.4 (все ChoiceClassFeature обязаны иметь choices:-запись).
    • Retraining-отказ (I1): игрок не перевыберет ошибочный выбор. Митигация: зафиксировано в Отложено (post-MVP).

    Отложено¶

    • Реализация (ClassChoiceRegistry, ClassChoiceResolver, CharacterCreationService, pendingChoices, allocateChoice) — 3.4.
    • UI (модал закрытия pendingChoices) — ФАЗА 6.
    • Retraining — post-MVP (I1).
    • Эффекты Metamagic/Invocations/Maneuvers — вне 0025 (форма сейчас, опции — 3.4, эффекты — позже).
    • Multiclass choices — ADR-lite позже.
