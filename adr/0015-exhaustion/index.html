    ADR-0015: Истощение (Exhaustion)¶

    Status¶

    Accepted

    Context¶

    ADR-0013 (Accepted) ввёл ядро состояний и сознательно исключил Истощение из StatusId: это не состояние из реестра, а отдельная числовая шкала на CharacterState. ADR-0014 (Accepted) закрыла duration/lifecycle состояний. Данная ADR закрывает третью и последнюю тему состояний — шкалу истощения 0..6: хранение, штрафы по уровням, источник роста, восстановление и смерть на 6.

    Канон 5e (PHB p.291) — уровни каскадные (каждый включает предыдущие):

    Уровень Эффект
    1 Помеха (disadvantage) на проверки характеристик
    2 Скорость уменьшена вдвое
    3 Помеха на броски атаки и спасброски
    4 Максимум хитов уменьшен вдвое
    5 Скорость равна 0
    6 Смерть

    Восстановление: 1 уровень за длительный отдых (при условии еды/питья). Рост: голод, жажда, жара/холод, форсированный марш, некоторые заклинания/эффекты, некоторые монстры.

    Факты (файл:строка)¶

    Хранение: - CharacterState.exhaustion: Int = 0 (GameState.kt:374); doc-комментарий :371-373 обещает «6 уровней = смерть», но ни одна строка кода смерть на 6 не реализует. - require(exhaustion in 0..6) (GameState.kt:523) — валидация границ есть. - RestResult.exhaustionRemoved: Int = 0 (GameState.kt:1087-1088).

    Восстановление (длительный отдых): - RestService.applyLongRest (RestService.kt:80-111): exhaustionRemoved = minOf(1, exhaustion) (:90), exhaustion = exhaustion - exhaustionRemoved (:97). Каноничный REST-путь. - SessionService.applyStateChanges → ветка StateChange.LongRest (SessionService.kt:2571-2587): exhaustion = (exhaustion - 1).coerceAtLeast(0) (:2579). Инлайн-путь в processTurn. - TurnResolver нарратив «Истощение −1.» (TurnResolver.kt:2035, :2095) — только текст. - Тест RestServiceTest.kt:60-67 «14.3 long rest removes exhaustion not poison» (2 → 1). - Два места декремента (−1) — потенциальный рассинхрон (RestService vs SessionService).

    Штрафы/смерть/рост — отсутствуют: - grep exhaustion по всему backend/app/src: нет ни одного применения штрафа (ни помехи на checks/attacks/saves, ни скорости, ни maxHp, ни смерти). Поле только читается при отдыхе. - Нет StateChange.GainExhaustion — поле никогда не инкрементируется в коде. Только описательные упоминания в данных: - subclasses.yml:131 — Варвар «Бешенство» (ярость) lvl 3, в описании «истощение» — без механики. - 0031-action-templates.yaml:59 — шаблон «Длительный бег» (movement, CON save DC 12), в описании «без отдыха копится истощение» — механика не подключена (только проверка). - В spells.json заклинаний с истощением нет (grep = 0). - В данных монстров (creature_archetypes) источников истощения не найдено.

    Скорость (для уровней 2 и 5): - ADR-0010 §5 (Status: Proposed, не Accepted) описывает CharacterState.speed: Int (дефолт 30), SpeedResolver.baseSpeed, ActionEconomy.movementUsed: Int, effectiveSpeed = speed + (if dash) speed. - Ни одно из этих полей в коде не существует (grep speed|Speed|movementUsed|effectiveSpeed в main/kotlin = 0; лишь комментарий «для скорости» в SimulationRunner.kt:44). - → Уровни 2 и 5 истощения не имеют поля, к которому можно прицепиться, пока не реализована Ф2 из ADR-0010.

    Точки встраивания штрафов: - resolveCheck (TurnResolver.kt:2326): помеха через hasDisadvantageOnChecks(character) (:2335) → d20WithDisadvantage(). hasDisadvantageOnChecks (:2312-2313) — хардкод-сет статусов (Отравлен, Ошеломлён, Испуган, Связан, Опутанный, Оглушён, Ослеплён). Истощения в сете нет. - resolveAttack (TurnResolver.kt:1656): attackerDisadv = hasDisadvantageOnAttacks(character) (:1703). hasDisadvantageOnAttacks (:2318-2319) — хардкод-сет + isProne. Истощения нет. - resolveSavingThrow (TurnResolver.kt:2407) и SavingThrowResolver.resolvePlayerSave (SavingThrowResolver.kt:22-53) — не консультируются с истощением (помеха на спасброски отсутствует). - resolveInitiative (TurnResolver.kt:2840, :2854) — проверка ЛОВкости; помеха только при playerSurprised (:2861). Инициатива в 5e — проверка характеристики, поэтому уровень 1 должен давать помеху и сюда (сейчас не даёт). - maxHp — плоское поле (CharacterState), не производная величина; уровня 4 (макс. HP вдвое) не существует.

    Несоответствие словаря состояний: - action-whitelist-core.yaml:255 перечисляет EXHAUSTION в «СЛОВАРЬ СОСТОЯНИЙ (CONDITIONS ENUM)(:240-264)». Но в кодеStatusId` (0013) истощения нет — словарь whitelist опережает/расходится с enum и не имеет резолвинг-логики.

    Ключевые ограничения для вариантов¶

    1. Истощение — не StatusId (по 0013 Untouched). Любое решение, добавляющее истощение в ConditionRegistry/StatusInstance, противоречит 0013.
    2. Скорости в коде нет — уровни 2/5 либо откладываются до Ф2 ADR-0010, либо требуют предварительного появления speed/effectiveSpeed.
    3. Adv/disadv сейчас — хардкод-сеты статусов, ещё не мигрированы на StatusId/kind. Помеха от истощения — это новый отдельный хук, а не расширение сета.
    4. Два места декремента отдыха (RestService vs SessionService) — 0014 (M1/alias) к этому отношения не имеет; это отдельный вопрос унификации.

    Decision¶

    Решения (A–K)¶

    • A = A1 — хранить Int 0..6 (GameState.kt:374), без изменений. require(0..6) остаётся.
    • B = B1 — ExhaustionResolver.effectsFor(level): ExhaustionEffects — data class с boolean-полями disadvantageChecks / disadvantageAttacks / disadvantageSaves / speedHalved / speedZero / maxHpHalved / death. Каскадность кодируется в effectsFor (уровень N включает все эффекты 1..N).
    • C = C3 — L1/L3/L4 реализуются сейчас; L2/L5 — после ADR-0010 §5 (speed). Точки: resolveCheck + resolveInitiative (L1); resolveAttack + resolveSavingThrow + resolvePlayerSave (L3); расчёт maxHp (L4).
    • D = D1 — StateChange.GainExhaustion(amount, target) — интерфейс. Продюсеры (spells/monsters/hard-rest) — ФАЗА 2/3.
    • E = E1 — мгновенная смерть через CharacterDeadException (audit-12 death rules). Не death saves.
    • F = F1 — −1 безусловно на long rest. Обязательное требование: унифицировать два места декремента (RestService.kt:90,97 vs SessionService.kt:2579). Единый источник — RestService.applyLongRest; SessionService.applyStateChanges делегирует в RestService.
    • G = G1 — иммунитет не моделировать сейчас. G2 — когда появится продюсер истощения для врагов.
    • H = H1 — exhaustionLevel в StatusContext (0013 I2).
    • I = I1 — L5 через speed (отложено до 0010 §5); L6 через CharacterDeadException. НЕ через blocksMove.
    • J = J2 — смерть немедленно после apply StateChange, но внутри того же processTurn (до tick). Совместимо с 0014 C3.
    • K = K1 — composition в точке вызова. AdvDisadvantageResolver не расширяем.

    Обязательные уточнения¶

    • Унификация декремента long rest — часть ADR-0015 (фикс дубля RestService vs SessionService).
    • ADR-0015 требует extension-point в AdvDisadvantageResolver (если его нет) — метод of(character) для K1.
    • Уровни 2 и 5 (speed) — мёртвые до реализации 0010 §5. Зафиксировать как зависимость, не как gap.
    • whitelist EXHAUSTION (action-whitelist-core.yaml:255) — LLM-контекст, не StatusId. Оставить как есть.
    • Смерть на 6 — не death saves. Использует CharacterDeadException из audit-12 death rules.

    Proposed Options¶

    A. Форма хранения уровня истощения¶

    A1 — оставить Int (0..6) (GameState.kt:374). - + Ноль миграций; require(0..6) уже есть. - − Магические числа 1..6 в логике штрафов; нет самодокументации каскадности.

    A2 — enum class ExhaustionLevel(0..6) с флагами каскадности. - + Каждый уровень несёт свои эффекты декларативно; исчерпывающий when. - − Миграция сериализации (ledgerJson), тесты; риск рассинхрона с require.

    A3 — sealed-класс/значение-объект (value class) Exhaustion(level: Int). - + Типобезопасность + компактная сериализация как число. - − Избыточно для шкалы 0..6; косметически.

    B. Архитектура применения штрафов¶

    B1 — единый ExhaustionResolver.apply(state): CharacterState (или effectsFor(level)). - + Один источник истины штрафов; легко тестировать; симметрично AdvDisadvantageResolver. - − Не покрывает эффекты, живущие в разных слоях (check/attack/save/maxHp/speed) — нужен API «запросить эффект по уровню», а не «применить всё сразу».

    B2 — флаги/свойства на enum-уровне (см. A2) + точечные гейты. - + Каждый гейт читает только нужный флаг (disadvantageChecks, speedHalved, …). - − Размазывает логику по нескольким резолверам; риск забыть гейт.

    B3 — инлайн-условия в каждом резолвере. - + Минимум новых сущностей. - − Дублирование when(level) в 4+ местах; худшая тестируемость. (Не рекомендуется.)

    C. Где применяется каждый уровень (точки встраивания)¶

    C1 — точечно в существующих гейтах: L1 → resolveCheck+resolveInitiative, L3 → resolveAttack+resolveSavingThrow+resolvePlayerSave, L4 → maxHp, L2/L5 → speed. - + Минимальный объём изменений; чёткая привязка файл:строка. - − L2/L5 блокируются отсутствием speed (Ф2 0010); L4 требует пересчёта maxHp.

    C2 — централизованный pre-roll хук (перед каждым броском d20 движок спрашивает «есть ли истощение → помеха/скорость»). - + Единая точка; в будущем легко добавить новые источники помехи. - − Крупный рефакторинг резолверов; риск сломать существующие adv/disadv.

    C3 — гибрид: помехи (L1/L3) — единый ExhaustionResolver (B1); L2/L4/L5 — точечно по мере появления соответствующих моделей (speed из 0010, производный maxHp). - + Реализуемое уже сейчас ядро + отложенное на данные модели. - − Частичная поставка; уровни 2/4/5 временно «мёртвые».

    D. Источник роста истощения¶

    D1 — StateChange.GainExhaustion(amount: Int) (симметрично StateChange.Damage/Heal). - + Идиоматично; подключается к applyStateChanges; источники (заклинания/монстры) смогут прокидывать через stateChanges. - − Нужен + новая ветка в applyStateChanges; пока нет ни одного продуцирующего источника.

    D2 — hard-rest механика (голод/жажда/форс-марш как отдельный движок отдыха). - + Закрывает каноничный источник (марш-бросок из 0031-action-templates.yaml:59). - − Крупная отдельная фича (RestEngine), вне объёма состояний; преждевременно.

    D3 — отложить до ФАЗЫ 2/3 (поле есть, рост — позже). - + Не строим преждевременно (AGENTS: не строить до retention). - − Шкала остаётся «только на убывание» (отдых), штрафы не на чем продемонстрировать.

    E. Смерть на 6¶

    E1 — мгновенная смерть (канон). - + Соответствует PHB p.291; простая реализация (флаг/исключение). - − Жёстко для MVP; требуется интеграция со смертью из 0012.

    E2 — CON save DC X против смерти (homebrew-смягчение). - + Мягче; больше «драматических спасбросков». - − Отход от канона; нужен отдельный DC/дизайн.

    E3 — не смерть, а «недееспособен до отдыха» (мягкий вариант). - + Минимальный риск; без интеграции со смертью. - − Неканонично; пользователи SRD-ожидают смерть на 6.

    F. Восстановление длительным отдыхом¶

    F1 — текущее: −1 безусловно (RestService.kt:90/97, SessionService.kt:2579). - + Уже реализовано; просто. - − Не учитывает еду/питьё (канон требует); два места декремента.

    F2 — −1 только при еде/питье (канон). - + Канонично; даёт смысл провизии. - − Требует модель провизии (нет в коде) — преждевременно.

    F3 — полное обнуление на long rest. - + Простейшее для игрока; нет накопления. - − Обесценивает шкалу; неканонично.

    G. Иммунитет к истощению (undead/construct)¶

    G1 — не моделировать (все получают истощение). - + Проще; соло-игрок против истощения без типов монстров. - − Неканонично (undead/construct иммунны).

    G2 — флаг иммунитета на Enemy (симметрично conditionImmunities из 0013 G2). - + Канонично; переиспользует паттерн 0013. - − Нужен источник роста для врагов (а его нет — см. D).

    H. Экспозиция в whitelist ctx¶

    H1 — exhaustionLevel в StatusContext (0013 I2 toWhitelistCtx()). - + Единый контекст; LLM видит уровень истощения. - − Расширяет контекст из 0013; надо синхронизировать с SessionService.kt:952-962.

    H2 — отдельный ключ ctx вне StatusContext. - + Не трогает 0013. - − Второй механизм экспозиции состояния.

    I. Гейты L5 (speed 0) и L6 (death)¶

    I1 — L5 через поле speed (0010 Ф2); L6 через StateChange/исключение 0012. - + Переиспользует смежные ADR; L5 реализуемо только после speed. - − L5 зависит от нереализованного 0010.

    I2 — L5 как флаг blocksMove (уже есть в 0013 E1) вместо speed. - + Реализуемо сейчас без speed-модели. - − Дуализм «speed 0» vs «флаг»; рассинхрон с 0010 в будущем.

    I3 — L6 через CharacterDeadException (0012) немедленно vs в конце хода (совместимость с 0014 C3). - + Определённый порядок относительно трёх pass 0014. - − Надо выбрать момент (см. J).

    J. Совместимость с 0014 C3 (три pass: apply → resolveSaveEnds → tick)¶

    J1 — смерть на 6 в конце хода (после tick, как результат накопления). - + Консистентно с 0014 порядком; смерть не обрывает ход на полпути. - − Отложенный эффект может показаться «несработавшим».

    J2 — смерть немедленно при достижении 6. - + Ощутимо сразу; канон (мгновенная смерть). - − Требует обрыва цепочки StateChange внутри хода.

    K. Связь ExhaustionResolver с AdvDisadvantageResolver (0013 F1)¶

    K1 — composition в точке вызова — в resolveCheck/resolveAttack/resolvePlayerSave: hasAdv = AdvDisadvantageResolver.of(c) || ExhaustionResolver.effectsFor(c.exhaustion).disadvantageChecks. AdvDisadvantageResolver не расширяем. - + Независимые источники, тестируемо, не ломает 0013. - − 3–4 точки вызова должны явно композировать.

    K2 — ExhaustionEffects передаётся внутрь AdvDisadvantageResolver как дополнительный вход. - + Единая точка помехи. - − AdvDisadvantageResolver начинает знать про exhaustion, семантически смешивает источники.

    K3 — exhaustion конвертируется в virtual StatusId (напр. VIRTUAL_EXHAUSTED_L1). - − Противоречит Untouched 0013 (exhaustion не StatusId). НЕ РЕКОМЕНДУЕТСЯ.

    Consequences¶

    Положительные¶

    • Шкала начинает работать: L1 (checks), L3 (attacks+saves), L4 (maxHp) — реализуемы сейчас.
    • Интерфейс роста задан: StateChange.GainExhaustion (D1) — источники подключатся позже без переделки контракта.
    • Унификация long rest (F1) устраняет дубль декремента (RestService vs SessionService).
    • Декларативные эффекты через ExhaustionResolver.effectsFor(level) (B1) — один источник истины.
    • Composition с AdvDisadvantageResolver (K1) — независимые источники помехи, тестируемо.

    Отрицательные¶

    • L2/L5 (speed) мёртвые до реализации 0010 §5.
    • Источники роста (spells/monsters/hard-rest) — ФАЗА 2/3; до этого шкала «только на убывание».
    • L4 (maxHp halved) требует расчёта производного maxHp — в TurnResolver или SessionService (уточнить при реализации).

    Риски¶

    • K1 — легко забыть composition в одном из 4 мест. Митигация: unit-тест «exhaustion=3 даёт disadvantage на attack и save».
    • Унификация long rest — риск сломать существующий путь. Митигация: RestServiceTest уже покрывает.

    Отложено¶

    • F2 (еда/питьё), G2 (иммунитеты), L2/L5 (speed), D-продюсеры (spells/monsters), D2 (RestEngine голода/жажды).

    Untouched in this ADR¶

    • StatusId/ConditionRegistry/StatusInstance (0013, 0014) — истощение туда не добавляется.
    • Speed-модель (0010 §5) — уровни 2/5 зависят от неё, но сама она вне объёма этой ADR.
    • Источники роста (spells, monsters, hard-rest) — ФАЗА 2/3.
    • Mana и другие ресурсы классов (следующая ADR-0016).
    • Dispel Magic (отложено в 0014 F3).
    • Голод/жажда/климат как самостоятельный RestEngine (см. D2 — вне объёма).
    • Модель провизии (для F2) — вне объёма.
