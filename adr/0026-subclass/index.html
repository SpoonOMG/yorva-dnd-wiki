    ADR-0026: Подкласс (Subclass) — форма + расширение SubclassRegistry + выбор¶

    Status¶

    Accepted

    Context¶

    SubclassRegistry существует и парсит subclasses.yml (31 подкласс), но теряет половину формы: парсит только name/level/description, игнорируя actionType/resourceId/choice (которых нет даже в YAML). Выбор подкласса работает жёстко (обязателен на 3), без pending-контракта. Собранные факты (файл:строка):

    Подклассы сегодня¶

    # Файл:строка Что найдено
    1 resources/subclasses.yml:1-318 31 подкласс, 12/12 классов покрыты: warrior 3 (champion, battle_master, eldritch_knight), wizard 3 (evocation, abjuration, necromancy), rogue 3 (thief, assassin, arcane_trickster), cleric 3 (life, light, war), barbarian 2 (berserker, totem_warrior), bard 2 (lore, valor), druid 2 (land, moon), monk 3 (open_hand, shadow, four_elements), paladin 3 (devotion, ancients, vengeance), ranger 2 (hunter, beast_master), sorcerer 2 (draconic, wild_magic), warlock 3 (archfey, fiend, great_old_one). Схема: id/classId/name/description/features[] (name/level/description в фиче). actionType/resourceId/choice/usesPerLevel/recharge — нет ни в YAML, ни в парсинге.

    9 Отсутствует SubclassId enum (grep → 0), SubclassResolver (grep → 0), pendingSubclassChoice (grep → 0).
    10 CharacterClass.subclasses CharacterClass.kt:23 — subclasses: List<String> («задел», выбор на 3). Не заполняется реестром (вторая копия связи класс→подклассы) — факт для A2 (единый источник — SubclassRegistry.getForClass).

    Проблема¶

    Подкласс — текст с обрезанной формой: реестр теряет actionType/ resourceId/choice (факты #3–4), механика — два хардкода (факт #7), ресурсные связки — только текст (факт #8), выбор — жёсткое требование без pending-контракта (факт #6). Новая рабочая фича подкласса = новый if в движке. Нужны: полная форма Subclass + допарсинг реестра + pending-контракт выбора — при живом реестре (расширение).

    Прецеденты¶

    • ADR-0023 B1/I1 — sealed ClassFeature; SubclassFeature = ClassFeature (I1 уже решён там — здесь C1 его исполняет).
    • ADR-0025 B1/D1/F1 — sealed ClassChoice; pendingChoices + allocateChoice; серверная валидация → 400 (образцы для D1/F1/H1).
    • ADR-0024 — пулы SUPERIORITY/CHANNEL_DIVINITY/WILD_SHAPE (точки привязки для факта #8).
    • ADR-0018 D1/E1 — pendingASI + остановка каскада (образец для F1).
    • ADR-0020 E1 / ADR-0021 D1 — RaceId / BackgroundId enum (образец для E1).
    • ADR-0020 H1a / ADR-0021 E1 / ADR-0022 G1b — stateless-резолверы (RaceResolver/BackgroundResolver/валидатор; образец для H1).

    Канон D&D 5e (PHB гл.3 «Classes»)¶

    12 классов × 2–8 подклассов (всего ~50–80): Barbarian (Berserker, Totem), Bard (Lore, Valor), Cleric (Life, Light, … — домен на 1), Druid (Land, Moon — круг на 2), Fighter (Champion, Battle Master, Eldritch Knight), Monk (Open Hand, Shadow, Four Elements), Paladin (Devotion, Ancients, Vengeance), Ranger (Hunter, Beast Master), Rogue (Thief, Assassin, Arcane Trickster), Sorcerer (Draconic, Wild Magic), Warlock (Archfey, Fiend, Great Old One — покровитель на 1), Wizard (школы — на 2). Уровень выбора разный (1/2/3) — факт для F1.

    Decision¶

    1. Место хранения (A2)¶

    Секция subclasses: в subclasses.yml (существует, факт #1) + SubclassRegistry (расширяется, НЕ создаётся — факт #3). Симметрия 0020/0021/0022/0023/0024/0025 — без второго источника. Расширение реестра: допарсинг actionType/resourceId/usesPerLevel/ recharge/choice (G1). CharacterClass.subclasses (факт #10) — не дублировать: единый источник связи — getForClass (факт #3, :64).

    2. Форма Subclass (B1)¶

    data class, НЕ sealed. Обоснование: подклассы однотипны (часть класса + фичи); sealed-по-подклассам = взрыв типов (31 сейчас, 50–80 в 3.4):

    data class Subclass(
    val id: SubclassId,               // E1
    val name: String,
    val parentClassId: String,        // canonicalClassId («warrior», …)
    val level: Int,                   // 1/2/3 — когда выбирается (факт #2, F1)
    val features: List<ClassFeature>, // C1
    val choices: List<ClassChoice>,   // D1
)

    level — обязательное поле: уровень выбора разный по классам (канон: cleric/warlock — 1, wizard/druid — 2, остальные — 3). Сегодня в данных униформа «3» (факт #2, пометка :94) — канон возвращается в 3.4 вместе с наполнением.

    3. SubclassFeature = ClassFeature (C1)¶

    Отдельного типа нет — исполнение I1 из ADR-0023. Форма готова (факт #4), наполнителя нет (факт #3) — допарсинг G1 закрывает разрыв. Хардкоды факта #7 мигрируют: champion → PassiveClassFeature (critRange-шаблон); draconic — в PassiveClassFeature (HP/AC-floor); patron/domain-spells — в ChoiceClassFeature (списки заклинаний). Связки факта #8: Battle Master → SUPERIORITY, Life → CHANNEL_DIVINITY, Moon → WILD_SHAPE — через resourceId (ADR-0024), без копирования механики (симметрия H1 из 0022).

    4. Subclass choices = ClassChoice (D1)¶

    ManeuverChoice (Battle Master), Domain-spells, Totem-варианты — подклассовые ClassChoice (ADR-0025 B1). Код уже собирает подклассовые choices (:141-147), но choice всегда null (факт #3) — G1 наполняет, код начинает работать без изменений. Отдельной формы выборов подкласса нет.

    5. SubclassId enum (E1)¶

    subclassId: String? (факт #5) → SubclassId enum. Симметрия RaceId (0020 E1) / BackgroundId (0021 D1). Breaking change; сессии тестовые. 31 значение сейчас, 50–80 в 3.4 (генерация enum из реестра — в 3.4, здесь только решение о форме).

    6. Выбор подкласса (F1)¶

    pendingSubclassChoice — зеркало pendingASI (ADR-0018 D1) / pendingChoices (ADR-0025 D1). Остановка каскада на уровне выбора (Subclass.level из B1 — 1/2/3, не хардкод «3»). allocateSubclass — резюме каскада, зеркало allocateASI/allocateChoice. Уточнение: level-up уже требует subclass на 3 (факт #6), parent-валидация уже есть (:129) — F1 вводит только pending-контракт, не новую логику проверок. Третьей pending-очереди не возникает сверх двух существующих (митигация — та же, что G1b в 0022).

    7. Допарсинг реестра (G1)¶

    Сегодня парсинг — только name/level/description (факт #3). Расширить на actionType, resourceId, usesPerLevel, recharge, choice (все поля уже есть в ClassFeature, факт #4). Предусловие C1/D1/H1. Миграция данных (заполнение полей в subclasses.yml) — цикл 3.4; форма парсинга — здесь.

    8. Parent validation + резолвер (H1)¶

    Subclass.parentClassId должен совпадать с CharacterState.canonicalClassId при выборе. Проверка уже есть в levelUp (:129) — переносится в SubclassResolver.apply(state, subclass) (stateless, симметрия RaceResolver/BackgroundResolver). Валидация parent — там же. ClassChoiceResolver не трогаем (чужой домен — урок E1 из 0022).

    9. Multiclass subclasses (I1)¶

    НЕ поддерживать (post-MVP). Один класс — один подкласс. PHB multiclass — optional-правила, вне ядра. Пересечений с multiclass в коде не найдено (classLevels — задел без подклассовой логики).

    10. Дубль subclass (J1)¶

    CharacterState.subclassId (факт #5) vs SubclassRegistry — новый дубль #11 (после #10 из 0022). Запись в ADR-0011 — отдельным циклом после реализации (аналогично 0020–0025 J1). Правило ADR-0011: новый дубль — с пометкой Resolved in ADR-0026.

    11. Объём цикла (K1)¶

    Только ADR. Реализация (расширение SubclassRegistry, SubclassResolver, SubclassId, данные 50–80 подклассов, pendingSubclassChoice) — цикл 3.4. Перечисление подклассов PHB — данные, не архитектура (сокращённый scope).

    Proposed Options¶

    A. Место хранения. - A1: новый subclass-features.yml — второй источник при живом YAML. - A2: subclasses: + расширение SubclassRegistry — рекомендация архитектора. Реестр жив (факт #3); getForClass — единый источник связи (факт #10 не дублируем). - A3: фичи подклассов в classes.yml — смешение уровней (класс vs подкласс), файл и так ~1220 строк.

    B. Форма Subclass. - B1: data class + SubclassId/level/features/choices — рекомендация архитектора. level покрывает разный уровень выбора. - B2: sealed-по-подклассам — 31 тип сейчас, 80 потом. - B3: плоский Subclass без level/choices — уровень выбора хардкодится («3»), choices теряются.

    C. Форма фич подкласса. - C1: SubclassFeature = ClassFeature (исполнение 0023 I1) — рекомендация архитектора. Форма готова (факт #4); хардкоды мигрируют в шаблоны; связки — через resourceId. - C2: отдельный SubclassFeature-sealed — параллельная иерархия, дублирование 0023. - C3: оставить текст (как сегодня) — новые фичи = новые if.

    D. Выборы подкласса. - D1: ClassChoice (0025 B1), код :141-147 начинает работать — рекомендация архитектора. - D2: отдельная форма выборов подкласса — дубль 0025. - D3: выборы строками в description — механики нет.

    E. Идентификатор. - E1: SubclassId enum (симметрия RaceId/BackgroundId) — рекомендация архитектора. Breaking, сессии тестовые. - E2: оставить String? — опечатки в id, валидация строками. - E3: String non-null — ломает создание до выбора.

    F. Контракт выбора. - F1: pendingSubclassChoice + остановка по Subclass.level + allocateSubclass — рекомендация архитектора. Третья очередь, но по тому же контракту (митигация — как 0022 G1b). - F2: оставить жёсткое требование (факт #6) — каскад падает исключением на уровне выбора навсегда. - F3: выбор только ручным levelUp без pending — каскад и preview (subclassChoice) висят без резюме.

    G. Допарсинг. - G1: парсинг всех полей ClassFeature — рекомендация архитектора. Предусловие C1/D1/H1. - G2: парсить частично (только choice) — resourceId/actionType теряются дальше. - G3: не допарсивать — C1/D1 не исполнимы, факт #3 из 0023 живёт.

    H. Валидация parent. - H1: новый stateless SubclassResolver.apply (проверка + применение); ClassChoiceResolver не трогаем — рекомендация архитектора. - H2: валидация в ClassChoiceResolver — чужой домен (урок 0022 E1). - H3: оставить проверку в levelUp (:129) — логика в сервисе, резолвер-паттерн нарушен (Race/Background уже вынесены).

    I. Multiclass. - I1: не поддерживать (post-MVP) — рекомендация архитектора. Пересечений в коде нет. - I2: второй подкласс при multiclass — PHB-optional, форма не готова. - I3: умолчать — реализатор угадывает.

    J. Дубль. - J1: регистрировать (#11, Resolved in ADR-0026, запись после реализации) — рекомендация архитектора. - J2: не регистрировать — нарушение правила ADR-0011. - J3: резолвить записью сейчас — преждевременно, расширения нет.

    K. Объём. - K1: только ADR; реализация + данные — 3.4 — рекомендация архитектора. - K2: ADR + допарсинг без данных — парсер без наполненных полей. - K3: полный цикл с 50–80 подклассами — нарушает «один цикл = один фокусный шаг» и сокращённый scope.

    Consequences¶

    Плюсы¶

    • Subclass формализуется (одна форма для всех 12 классов × N подклассов).
    • SubclassFeature = ClassFeature (0023 I1) — единая форма, без параллельной иерархии.
    • SubclassChoice = ClassChoice (0025 B1) — Maneuvers, Domain-spells, Totem-варианты через общую форму; код :141-147 оживает без изменений.
    • Симметрия: pendingSubclassChoice — зеркало pendingASI/pendingChoices; SubclassResolver — зеркало RaceResolver/BackgroundResolver.
    • Допарсинг устраняет факт #3 из ADR-0023 (потери реестра).
    • Parent-валидация уже есть (:129) — переносится, не пишется заново.
    • Все формы проекта (Race / Background / Feat / ClassFeature / ClassResource / ClassChoice / Subclass) — зафиксированы ADR. Мини-ФАЗА 0 закрыта.

    Минусы¶

    • Расширение SubclassRegistry (не создание) + миграция subclasses.yml.
    • 50–80 подклассов — наполнение данных цикла 3.4 (объём).
    • SubclassId enum — breaking change.
    • SubclassResolver — девятый реестр/резолвер по паттерну.
    • CharacterClass.subclasses (факт #10) — мёртвый задел до 3.4 (либо чистка, либо синхронизация с getForClass).

    Риски¶

    • 50–80 подклассов — большой объём данных; риск неполного subclasses.yml (как backgrounds.yml). Митигация: G1 — сверка с PHB при миграции (31/12 уже зафиксировано, факт #1); форма сейчас, данные — 3.4.
    • Полиморфизм подклассов (Champion — пассив, Battle Master — choices, Wild Magic — триггеры): data class достаточно, потому что sealed ClassFeature уже покрывает все подвиды. Митигация: C1.
    • Уровень выбора разный (канон 1/2/3; факт #2 — униформа «3», wizard — «2»). F1 (pending) должен знать уровень из Subclass.level. Митигация: поле level в B1; канон возвращается в 3.4.
    • Multiclass subclasses (I1) — отказ; второй подкласс невозможен. Продуктовое решение (PHB multiclass — optional).
    • Три pending-очереди (ASI/choices/subclass) — риск путаницы. Митигация: единый контракт (зеркала 0018/0025); очереди не смешиваются (разные уровни-триггеры).

    Отложено¶

    • Реализация (расширение SubclassRegistry, SubclassResolver, SubclassId, pendingSubclassChoice + allocateSubclass) — цикл 3.4.
    • Данные 50–80 подклассов (subclasses.yml наполнение + канон уровней выбора) — цикл 3.4.
    • Multiclass subclasses — post-MVP (I1).
    • Судьба CharacterClass.subclasses (факт #10) — 3.4.
    • Frontend (wizard выбора подкласса) — ФАЗА 6.
    • Запись дубля #11 в ADR-0011 — после реализации (J1).

    Чек-лист решений A–K¶

    • A = A2 — subclasses: + расширение SubclassRegistry; CharacterClass.subclasses не дублируем.
    • B = B1 — data class Subclass (НЕ sealed; SubclassId/parentClassId/ level 1-2-3/features/choices).
    • C = C1 — SubclassFeature = ClassFeature (исполнение 0023 I1); хардкоды → шаблоны; связки → resourceId.
    • D = D1 — подклассовые выборы = ClassChoice (код :141-147 оживает).
    • E = E1 — SubclassId enum (симметрия RaceId/BackgroundId); breaking.
    • F = F1 — pendingSubclassChoice + остановка по Subclass.level + allocateSubclass; проверок новых нет (:129 уже есть).
    • G = G1 — допарсинг всех полей ClassFeature; данные — 3.4.
    • H = H1 — новый stateless SubclassResolver.apply (parent-валидация там).
    • I = I1 — multiclass-подклассы не поддерживаем (post-MVP).
    • J = J1 — дубль #11 (Resolved in ADR-0026), запись после реализации.
    • K = K1 — только ADR; реализация + данные — 3.4.

    Untouched in this ADR¶

    • Код (SubclassRegistry.kt, LevelUpService.kt, LevelUpApplier.kt, SessionService.kt, CharacterState.subclassId) — цикл 3.4.
    • Данные 50–80 подклассов — цикл 3.4 (K1; перечисления нет).
    • Multiclass subclasses — post-MVP (I1).
    • ADR-0011 — запись дубля #11 после реализации (J1; в этом цикле НЕ правим).
    • Frontend — ФАЗА 6.
