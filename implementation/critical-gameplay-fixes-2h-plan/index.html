    План исправления критических игровых уязвимостей на 2 часа¶

    Статус: основные исправления и идемпотентность реализованы; полная backend- и frontend-проверка пройдена.

    Цель: за 120 минут закрыть наиболее опасные эксплойты, не затрагивая чужую параллельную работу и не начиная изменения, которые невозможно безопасно закончить за этот срок.

    Отдельное требование: разные аккаунты и их параллельные сессии не должны влиять друг на друга. В основной блок входит отключение удалённого запуска selflearn в обычном JVM: сейчас он мутирует глобальный BalanceRegistry для всех пользователей.

    1. Жёсткие правила исполнения¶

    1. Перед началом дождаться завершения параллельного агента.
    2. Выполнить git status --short и записать исходный список изменений. Не делать reset, checkout, clean, stash и не перезаписывать чужие файлы.
    3. Работать маленькими независимыми порциями в порядке из раздела 3. После каждой порции проверять diff только ожидаемых файлов.
    4. Не добавлять зависимости, новые подсистемы и рефакторинг «заодно».
    5. API менять только после api-specification/openapi.yaml. В основном блоке спецификация нужна для ответа 404 при создании сессии в недоступном мире.
    6. Не коммитить автоматически: перед каждым коммитом показать результат и получить подтверждение пользователя.
    7. Если шаг превысил свой таймбокс, остановиться на последнем рабочем состоянии, зафиксировать ошибку и не начинать следующий рискованный шаг.
    8. Не объявлять шаг завершённым, если его новые тесты не написаны/не пройдены или старые тесты сломаны без разобранной причины.
    9. После изменения поведения обновить рядом стоящие устаревшие комментарии и тесты, которые прямо закрепляют уязвимое поведение.
    10. Не запускать полный интеграционный прогон вместо точечных тестов в середине работы. Сначала узкие тесты, полный прогон — только после основного блока и при наличии времени.

    Известный исходный фон: в предыдущем прогоне SessionIntegrationTest давал 19 падений, преимущественно 401 на createWorld; остальные 30 выбранных тестов прошли. Эти падения нельзя автоматически приписывать новым исправлениям и нельзя называть интеграционную базу зелёной.

    2. Область работ¶

    Основной блок P0/P1 — обязательно¶

    Порядок Проблема Минимально достаточное исправление Таймбокс
    0 Подготовка Зафиксировать исходный diff и тестовую базу 5 мин
    1 Межаккаунтное изменение баланса Убрать selflearn HTTP endpoint из обычного/production контекста 10 мин
    2 Создание сессии в чужом мире Проверить владельца мира до обеих веток создания 15 мин
    3 Произвольные и повторные реакции Принимать только реакцию из последнего хода; перепроверить spell reaction 15 мин
    4 Чужие/неизученные заклинания и любые заговоры Централизовать проверку доступности в SpellService.canCast 20 мин
    5 Бесплатное примирение врага Не выставлять isAlly по свободному тексту игрока или Narrator 10 мин
    6 Действие после смертельного первого удара врага Не разрешать действие игрока, если preStrike сделал его недееспособным 15 мин
    7 Проверка Точечные тесты, исправление только связанных ошибок, финальный diff 20 мин
    8 Резерв Разбор результатов и отчёт 10 мин

    Итого: 120 минут.

    Не начинать в двухчасовом блоке¶

    • полноценную идемпотентность ходов;
    • перенос и синхронизацию side effects SpineService;
    • redesign write-through снимка одного героя, используемого параллельными сессиями;
    • глобальную изоляцию BalanceRegistry для одновременных selflearn-прогонов;
    • переработку всей ресурсной экономики.

    Это не отказ от исправлений: для них есть отдельные этапы в разделе 7.

    3. Пошаговый основной план¶

    Шаг 0. Подготовка — 5 минут¶

    1. Убедиться, что параллельный агент завершил работу.
    2. Сохранить список исходно изменённых файлов из git status --short.
    3. Для каждого целевого файла, уже изменённого другой задачей, сначала прочитать актуальный diff. Не заменять файл целиком.
    4. Использовать только точечные правки. Новые тесты добавлять в уже существующие тестовые классы, если там есть подходящие fixtures; отдельный класс создавать только для отсутствующего сценария.

    Контроль: есть список исходных изменений, чужая работа не затронута.

    Шаг 1. Закрыть удалённый selflearn в обычном JVM — 10 минут¶

    Почему первым: любой авторизованный пользователь может запустить длительную операцию, которая вызывает balanceRegistry.reset() и applyFixes(). Это меняет правила параллельных игр других аккаунтов.

    Файлы:

    • backend/app/src/main/kotlin/com/yorva/sim/selflearn/SelfLearnController.kt
    • при наличии подходящей инфраструктуры — профильный тест контекста рядом с существующими тестами.

    Действия:

    1. Пометить только HTTP-контроллер профилем @Profile("selflearn").
    2. Не включать профиль selflearn в обычные dev/production настройки.
    3. Не менять SelfLearnOrchestrator и BalanceRegistry на этом шаге: их полная изоляция — отдельная задача.
    4. Обновить KDoc контроллера: ручной запуск доступен только в отдельном JVM с явно включённым профилем selflearn.
    5. Зафиксировать эксплуатационное ограничение: профиль selflearn запрещено включать в JVM, где идут реальные игровые сессии.

    Почему этого достаточно для hotfix: в обычном приложении endpoint перестаёт регистрироваться и удалённый пользователь больше не может мутировать глобальный баланс. При явном включении профиля риск остаётся, поэтому это containment, а не полный refactor.

    Проверка позже:

    • без профиля selflearn бин SelfLearnController отсутствует, POST /api/v1/sim/selflearn/run возвращает 404;
    • с профилем selflearn контроллер доступен только в изолированном запуске;
    • обычные игровые сессии не меняют BalanceRegistry.current после попытки вызова endpoint.

    Стоп-условие: если профильная конфигурация требует изменения общей security-цепочки, не расширять работу; перейти к шагу 2 и оставить явную запись о незавершённой проверке.

    Шаг 2. Запретить создание сессии в чужом/удалённом мире — 15 минут¶

    Сначала спецификация:

    • api-specification/openapi.yaml, операция startSession (POST /api/v1/sessions).
    • Добавить 404: мир не найден или недоступен текущему пользователю.
    • В x-pipe первой содержательной операцией указать поиск мира по (worldId, userId) и отказ до создания героя/сессии.

    Код:

    • backend/app/src/main/kotlin/com/yorva/sessions/SessionService.kt
    • backend/app/src/main/kotlin/com/yorva/sessions/SessionController.kt
    • backend/app/src/main/kotlin/com/yorva/worlds/WorldRepository.kt — использовать существующий метод, не добавлять новый без необходимости.

    Действия:

    1. В самом начале SessionService.create, до ветки request.characterId != null, вызвать: worldRepository.findByIdAndUserIdAndDeletedAtIsNull(request.worldId, userId).
    2. Если результата нет, выбросить отдельное WorldNotFoundException с нейтральным сообщением World not found.
    3. Не различать в ответе чужой, удалённый и несуществующий мир: все дают одинаковый 404.
    4. Добавить обработчик этого исключения в SessionController.create со статусом 404 и существующим форматом { "error": ... }.
    5. Переиспользовать уже загруженный world.genre вместо повторного небезопасного чтения только по worldId в ветке нового героя.
    6. Не полагаться на CharacterService.loadForResume: он проверяет героя, но не заменяет проверку владения миром.

    Тесты:

    • владелец создаёт сессию нового героя — успех;
    • владелец создаёт сессию с существующим героем — успех;
    • пользователь B подставляет worldId пользователя A в обеих ветках — 404;
    • удалённый/несуществующий мир — 404;
    • после отказа не появилось ни новой сессии, ни нового героя.

    Шаг 3. Закрыть произвольные и повторные реакции — 15 минут¶

    Файлы:

    • backend/app/src/main/kotlin/com/yorva/sessions/SessionService.kt
    • backend/app/src/test/kotlin/com/yorva/rules/ReactionResolverTest.kt — только для чистой механики, если потребуется;
    • тест сервисного контура реакций: использовать существующий подходящий класс либо создать SessionReactionTurnTest, потому что текущий AvailableReactionsGateTest проверяет только генерацию предложений.

    Действия:

    1. В processReactionTurn нормализовать код: request.reaction?.trim()?.uppercase(); пустое значение отклонить.
    2. Требовать наличие предыдущего хода и непустого availableReactions.
    3. Заменить текущее условие «проверять, только если список не пуст» на безусловное: разрешить только offered.any { it.reaction == normalizedReaction }.
    4. Использовать нормализованный код при вызове ReactionResolver.resolve.
    5. После реакции оставить availableReactions = emptyList(): благодаря строгой проверке повторный RETALIATION на следующем follow-up будет отклонён.
    6. Для реакций-заклинаний (SHIELD, HELLISH_REBUKE, ABSORB_ELEMENTS, FEATHER_FALL) перед резолвом повторно проверить заклинание через SpellService.canCast. Добавить SpellService? = null в конструктор SessionService рядом с SpellRegistry, если инъекции ещё нет; в production отсутствие сервиса для spell reaction должно означать отказ, а не обход проверки.
    7. Не добавлять самостоятельный enemy turn после RETALIATION: задача — закрыть бесконечный follow-up, а не менять боевую модель.

    Обязательные тесты:

    • пустой availableReactions + вручную подставленный RETALIATION → отказ, HP/XP/состояние не меняются;
    • непредложенная реакция → отказ;
    • вторая одинаковая реакция после первой → отказ;
    • предложенная реакция → ровно одно применение;
    • spell reaction без знания/подготовки или без подходящего слота → отказ без списания и эффекта;
    • реакция в сессии A не использует предложения из сессии B.

    Шаг 4. Проверять право на заклинание в SpellService.canCast — 20 минут¶

    Файлы:

    • backend/app/src/main/kotlin/com/yorva/spells/SpellService.kt
    • backend/app/src/test/kotlin/com/yorva/spells/SpellServiceTest.kt
    • при необходимости SpellServiceUpcastTest, PactMagicTest, UtilityCantripTest — только обновление fixtures, которые сейчас создают «пустого» персонажа со слотами.

    Правило доступности:

    1. Сохранить текущие запреты: incapacitated, rage, wild shape.
    2. Нормализовать spell.id и списки персонажа через trim().lowercase().
    3. Для заговора (level == 0) требовать spell.id in spellsKnown; слот не нужен.
    4. Для wizard/mage требовать заклинание одновременно в spellbook и preparedSpells; заговоры — по пункту 3.
    5. Для cleric/druid/paladin требовать preparedSpells; доменные заклинания уже добавляются туда отдельно и должны продолжить работать.
    6. Для остальных заклинателей требовать spellsKnown либо явно выданное preparedSpells.
    7. Только после проверки доступности выполнять существующие проверки pact/slot и upcast.
    8. Не делать грубую универсальную проверку spell.classes.contains(classId): она сломает доменные и патронные заклинания, законно присутствующие в preparedSpells/spellsKnown. Класс и источник выбора уже учитываются при создании и prepareSpells; canCast должен проверять фактическую доступность конкретного spell.id.
    9. Оба пути каста уже проходят через TurnResolver.executeCastSpell: текстовый и structured intent. Не вставлять вторую расходящуюся проверку в resolveStructuredCast.

    Тесты:

    • персонаж без списков заклинаний не кастует заговор даже со свободными слотами;
    • известный заговор кастуется без слота;
    • заклинание другого класса, отсутствующее во всех списках персонажа, отклоняется;
    • wizard не кастует заклинание, которое есть только в книге, но не подготовлено;
    • подготовленное заклинание из книги доступно;
    • доменное/патронное заклинание из соответствующего списка доступно;
    • неизвестное заклинание отклоняется до списания слота;
    • валидные pact/upcast сценарии сохраняются.

    Важно: существующий тест canCast returns true when conditions met и похожие fixtures нужно наполнить классом и корректными списками заклинаний, а не ослаблять новые проверки ради старого пустого fixture.

    Шаг 5. Убрать бесплатное примирение по текстовому маркеру — 10 минут¶

    Файлы:

    • backend/app/src/main/kotlin/com/yorva/sessions/SessionService.kt
    • backend/app/src/test/kotlin/com/yorva/sessions/SessionServiceAllyFlagTest.kt

    Действия:

    1. Удалить автоматическую установку Enemy.isAlly из блока allyScanInput/detectAllyMarker.
    2. Не сканировать ни request.action, ни свободную прозу Narrator для изменения боевого состояния. Удаление только сканирования request.action недостаточно: Narrator может повторить prompt injection игрока.
    3. Примирение/завершение боя оставить только через существующий проверяемый END_COMBAT контур с EffectValidator.validateEndCombat.
    4. Поле Enemy.isAlly не удалять: оно может использоваться доверенными детерминированными сценариями. Убрать только небезопасный источник изменения.
    5. Обновить комментарии около applyEnemyTurn: свободный текст больше не является источником флага.
    6. Переписать старые тесты, которые прямо требуют ally-флаг по фразам «не враг»/«союзник»: теперь они должны требовать отсутствие смены состояния. Не удалять негативные сценарии.

    Тесты:

    • игрок пишет «они не враги мне» → враг не становится союзником и бой не прекращается;
    • Narrator возвращает «сложил оружие, союзник» без валидного эффекта → isAlly не меняется;
    • валидный существующий END_COMBAT сценарий продолжает работать;
    • следующий вражеский ход не подавляется одной текстовой фразой.

    Шаг 6. Запретить действие после недееспособности от preStrike — 15 минут¶

    Файл:

    • backend/app/src/main/kotlin/com/yorva/sessions/SessionService.kt
    • новый сервисный тест только если нет подходящего существующего класса для enemy-first хода.

    Действия:

    1. После вычисления preStrike, но до turnResolver.resolve(...) для действия игрока вычислить предварительное состояние, применив только preStrike.stateChanges через существующий applyStateChanges.
    2. Не сохранять это предварительное состояние отдельно и не применять изменения второй раз к итоговому состоянию. Оно нужно только для gate.
    3. Если после preStrike персонаж имеет hp <= 0, unconscious/dead или incapacitated, заменить действие игрока на TurnMechanics(action = "no_roll", stateChanges = emptyList(), ...) с понятным описанием пропуска.
    4. Сохранить текущую схему объединения: preStrike должен попасть в журнал и итоговое состояние ровно один раз.
    5. Не бросать CharacterDeadException до сохранения самого вражеского удара: это потеряет факт смерти/падения. Смертельные правила дальше обрабатывают итоговое состояние.
    6. Не менять обычный порядок ходов, где игрок ходит первым.

    Тесты:

    • враг ходит первым и снимает все HP → атака/лечение/каст игрока не применяются;
    • preStrike накладывает unconscious/incapacitated → действие игрока пропущено;
    • несмертельный preStrike → действие игрока выполняется;
    • урон врага, статусы и броски записаны один раз, без двойного применения;
    • ход игрока первым не изменился.

    4. Проверка основного блока — 20 минут¶

    Команды ниже предназначены для этапа исправлений; в рамках составления этого плана они не запускались.

    4.1. Сначала узкие тесты¶

    Из backend/:

  --tests 'com.yorva.sessions.AvailableReactionsGateTest' \

    Добавить в команду новые классы тестов реакций, ownership и enemy-first, если они были созданы.

    Они не доказывают многоинстансную безопасность, но должны остаться зелёными.

    4.3. Ручная матрица изоляции¶

    Если есть работающая локальная среда:

    1. Создать пользователей A и B, разные миры и по две параллельные сессии.
    2. B пытается создать сессию в мире A → 404, записей нет.
    3. B вызывает selflearn без специального профиля → 404; правила сессии A не меняются.
    4. A и B делают чередующиеся ходы → HP, враг, XP, лут и availableReactions остаются привязанными к своим sessionId.
    5. Повторить exploit-сценарии из шагов 3–6 и убедиться, что отказ не создаёт скрытых изменений.

    4.4. Финальный контроль¶

    • git status --short и git diff -- <каждый целевой файл>;
    • в diff нет изменений параллельной auth-задачи;
    • нет незапрошенных миграций, зависимостей и новых API-полей;
    • OpenAPI и реализация 404 совпадают;
    • все новые тесты зелёные;
    • оставшиеся старые падения перечислены отдельно с точной причиной;
    • в отчёте явно перечислены незакрытые высокие риски из раздела 7.

    5. Правила таймбокса и точки остановки¶

    • T+30: должны быть закрыты selflearn и ownership. Если нет — продолжать только их, не начинать реакции.
    • T+65: должны быть закрыты реакции и заклинания. Если spell-gate ломает много старых fixtures, сначала исправлять fixtures; не расширять предметную модель.
    • T+90: должны быть закрыты ally-marker и preStrike.
    • T+105: новый код больше не писать, кроме исправлений ошибок, найденных точечными тестами.
    • T+110: прекратить отладку некритичных/старных инфраструктурных проблем, собрать diff и результаты.
    • T+120: выдать отчёт: исправлено/проверено/не исправлено/блокеры.

    Если времени не хватает, приоритет незавершённых работ: сначала довести до зелёного состояния уже начатый security-fix, затем остановиться. Не оставлять полурабочую идемпотентность или миграцию БД ради количества закрытых пунктов.

    6. Критерии готовности двухчасового блока¶

    Работа считается завершённой только если одновременно выполнено:

    • selflearn недоступен в обычном/production JVM;
    • обе ветки создания сессии проверяют владельца мира;
    • произвольная/повторная реакция отклоняется сервером;
    • текстовый и structured cast не могут использовать неизученное/неподготовленное заклинание;
    • свободный текст не меняет isAlly;
    • смертельный/обездвиживающий preStrike не позволяет игроку действовать;
    • на каждый пункт есть негативный регрессионный тест;
    • точечные тесты и существующие concurrency-тесты пройдены;
    • известные незакрытые риски не выданы за исправленные.

    7. Высокие риски после двухчасового блока¶

    7.1. Идемпотентность ходов — отдельный spec-first этап¶

    Статус: реализовано и проверено. Миграция 0051-turn-request-idempotency; ограничение — жёсткий crash JVM может оставить IN_PROGRESS без автоматического истечения.

    Проблема: повтор после timeout создаёт новый ход и повторяет урон, расход ресурсов, XP и лут. Дедуп ловушки не решает общую проблему.

    Порядок:

    1. В OpenAPI добавить clientRequestId в TurnRequest и описать: клиент создаёт UUID на одно пользовательское действие; сетевые retry используют тот же UUID; новое действие — новый UUID.
    2. Обновить frontend retry-логику: автоматический retry не меняет UUID; повторный клик после полученного ответа создаёт новое действие только по явному выбору пользователя.
    3. Добавить отдельную таблицу запросов ходов с уникальным (session_id, actor_user_id, client_request_id), статусом, хешем запроса и сохранённым ответом. Не хранить только turn_id: для точного replay нужен исходный TurnResponse.
    4. Атомарно зарезервировать ключ до LLM. Повтор DONE возвращает сохранённый ответ без механики и side effects; параллельный IN_PROGRESS получает 409; тот же ключ с другим action/intent/reaction — 409.
    5. Ошибку до начала механики разрешить повторять по явному правилу; после начала записи не делать второй расчёт. Все переходы статуса и запись ответа должны быть транзакционными.
    6. Проверить два параллельных одинаковых запроса, retry после commit/timeout, разные аккаунты с одинаковым UUID и разные сессии одного аккаунта.

    Не реализовывать упрощённый in-memory cache: он не работает после рестарта и между инстансами.

    7.2. SpineService: side effect без freshness-check¶

    Проблема: applyEffects и tickStall сохраняются до финальной проверки сессии. Ход может завершиться 409, а сюжет уже изменится. Параллельные инстансы также могут перезаписать канву.

    Порядок:

    1. Сделать spine-изменения частью финальной короткой транзакции после lockSession и всех freshness-check.
    2. До этой транзакции только вычислить pending-эффекты, ничего не сохранять.
    3. Добавить блокировку строки spine (FOR UPDATE) либо @Version; выбранный вариант должен работать между разными JVM.
    4. Перенести начисление spineXpGranted и обновление описания/состояния в тот же согласованный коммит, чтобы XP соответствовал реально применённым битам.
    5. При SessionConcurrentModificationException не должно быть ни хода, ни spine, ни XP, ни лута.
    6. Тестировать двумя независимыми сервисными экземплярами/транзакциями, а не только in-memory lock одного singleton.

    7.3. Общий герой в параллельных сессиях¶

    Проблема: CharacterService.syncHero перезаписывает весь characterJson и lastSessionId по last-write-wins.

    Порядок:

    1. Сначала выбрать продуктовую модель: запретить одному герою одновременные активные сессии либо создавать независимый snapshot/fork на сессию.
    2. Для запрета — атомарная проверка/захват активной сессии в БД и понятный 409.
    3. Для fork — не делать write-through поверх общего героя из каждой сессии; явная операция выбора итогового прогресса после завершения.
    4. Добавить optimistic version для защиты от незаметной перезаписи, но не считать одну @Version решением доменного конфликта.
    5. Проверить параллельные ходы одного героя в двух сессиях и независимость героев разных аккаунтов.

    Не пытаться решить это простым сравнением lastSessionId: это лишь скроет часть перезаписей и может потерять прогресс.

    7.4. Повторный milestone XP при возврате в сцену¶

    Минимальное исправление:

    • в обработчике StateChange.ClearXpTriggers удалять только временные per-location триггеры;
    • сохранять ключи milestone@...;
    • не менять остальную последовательность sceneTransitions/milestoneChanges.

    Тест: scene_1 → scene_2 → scene_1: XP выдаётся за первое посещение каждой сцены, но повторное посещение scene_1 не даёт XP. Существующий тест повтора подряд оставить.

    7.5. Произвольный TAKE_LOOT и legacy-обходы валидатора¶

    Порядок:

    1. В structured и legacy TAKE_LOOT требовать, чтобы itemId принадлежал именно текущей витрине данной сессии, а не просто существовал в каталоге.
    2. Отклонять ID из issuedLootItemIds, дубли в одном ходу и повторную выдачу; количество ограничить доступным остатком витрины.
    3. Вынести общую проверку в один helper, чтобы structured/legacy пути не разошлись.
    4. Для legacy SPAWN_ENEMY и DROP_ITEM применять те же EffectValidator/rate-limit/whitelist, что и для structured effects; при невозможности валидировать legacy — консервативно отклонять тег.
    5. Тесты: чужой/произвольный catalog ID, ID из старой витрины, повторный ID, prompt injection через Narrator, превышение количества, параллельные сессии с разными витринами.

    7.6. Полная изоляция selflearn¶

    После hotfix с профилем:

    1. Не использовать production singleton BalanceRegistry как изменяемый рабочий лист симуляции.
    2. Передавать отдельный BalanceRegistry/snapshot в контекст каждого selflearn-run и каждой симулированной сессии.
    3. Не публиковать итоговые overrides автоматически в игровой движок; применять только через явный reviewed deployment/config change.
    4. Проверить два параллельных selflearn-run и одновременную обычную игру: ни один не меняет правила другого.

    8. Что не входит даже в ближайший hotfix¶

    Эти проблемы из ревью важны, но имеют меньший приоритет относительно перечисленных выше: бесплатный generic heal, неограниченные короткие отдыхи, боеприпасы и владение каталожным оружием, prepareSpells без long rest/во время боя, свиток без урона, один attack roll для multiattack. Их нельзя смешивать с двухчасовым security-блоком.
