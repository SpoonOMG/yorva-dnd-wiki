    YORVA — Scene Registry. План работ.¶

    Контекст¶

    Yorva — текстовый движок DnD-подобной RPG. - Backend: Kotlin + Spring Boot 3.4, PostgreSQL (5433, БД dnd), Liquibase. - Frontend: Next.js + React + TypeScript. - LLM: DeepSeek V4 Flash (Narrator, Anchor, Archivist, Classifiers), NordRouter. - Репозиторий: ~/IdeaProjects/dnd.

    Роли: - LLM (Narrator) = DM. Описывает мир, эмитит structured effects. - catalog_classifier = LLM, определяет intent игрока + target предмета. - Движок = правила. Хранит state, валидирует, применяет. - EffectValidator = валидирует structured effects перед применением.

    Проблема, которую решаем¶

    Истина о том, что лежит в сцене, живёт в 4 местах: 1. Проза Narrator'а. 2. Effects Narrator'а (GRANT_ITEM/DROP_ITEM). 3. Regex-проверка движка (lootGrantJustified). 4. catalog_classifier (target=null при truncated JSON).

    Они не синхронизированы → рассинхрон → «Рядом нет предметов для подбора» при существующем предмете, или наоборот — галлюцинированные предметы.

    Решение: единый источник истины — Scene Registry. Все остальные слои ссылаются на него по ID.

    Архитектура: Scene Registry¶

    Три понятия¶

    Локация (Scene). Место, где находится игрок. - id — уникальный (генерируется Narrator'ом), например hotel_room_47. - name — человекочитаемое.

    Предмет (Item). - id — уникальный (генерирует движок). - name — человекочитаемое. - category — MISC / MELEE_WEAPON / POTION / ... - location_id — ID локации ИЛИ: - @player — в инвентаре игрока - @npc:<id> — у NPC - @destroyed — уничтожен - takeable — boolean (default true)

    Игрок. - current_location_id — где сейчас.

    Три новых effect'а¶

    ENTER_SCENE(id, name) - Narrator объявляет перемещение. - Движок обновляет current_location_id. - Если ID новый — создаёт локацию. - Если ID существующий — «возврат».

    REGISTER_ITEM(name, category, location_id, source_quote?, takeable?) - Narrator регистрирует предмет. - Идемпотентно через (location_id, normalized_name). - source_quote обязателен при retry (см. раздел Retry).

    TAKE_ITEM(item_id) - Проверяет item.location_id == player.current_location_id. - Если совпадает → location_id = "@player". - Если @player → «У тебя уже есть». - Если другая локация → «Не здесь». - Если takeable=false → «Не получается».

    Что удаляется¶

    • lootGrantJustified целиком + все reason'ы (scene_mentioned, misc_prose_mention, giver_event, ...).
    • [LOOT_GATE] лог.
    • resolveLoot старая логика.
    • fallback_regex в catalog_classifier.
    • GRANT_ITEM, DROP_ITEM как самостоятельные effect'ы (заменяются на REGISTER_ITEM + location change).

    Что сохраняется¶

    • NarratorOutputParser (Коммит 1).
    • stripMetaCommentary (Коммит 2).
    • SHOW_CLASSIFIER_REASONING флаг (Коммит 2.5).
    • ActionParser physical-verb guard (Коммиты 3, 3.1).

    Ключевые инварианты (защита)¶

    Защита 1: дубликаты при leave-and-return¶

    • TAKE_ITEM при location_id="@player" → явный ответ «У тебя уже есть».
    • TAKE_ITEM при @destroyed или @npc → «Не находишь».
    • Narrator видит полный state и не должен повторно регистрировать.

    Защита 2: фабрикация предметов игроком¶

    Retry триггерится ТОЛЬКО при gap между прозой Narrator'а и registry. - Если Narrator описал предмет в прозе, но не зарегистрировал — retry разрешён. - Если проза «чистая» (нет неописанных объектов) — retry не запускается, немедленный отказ. - Retry-промпт: «Вот твоя проза прошлого хода: . Игрок пытается взять . Найди в своей прозе этот предмет.» - Retry-ответ обязан содержать source_quote — фрагмент прозы, где предмет упомянут. - Движок валидирует source_quote против реальной прозы. Не совпало — [FABRICATION_ATTEMPT].

    Идемпотентность через (location_id, normalized_name): - При REGISTER_ITEM проверка: есть предмет с таким нормализованным именем? - Уникальные категории (MISC, документы, ключи) — не дублировать в другой локации. - Расходники (POTION, SCROLL, патроны) — разрешать дубликаты.

    Защита 3: использование несуществующих предметов¶

    • Classifier: USE_ITEM при отсутствии target в доступных → target_id=null.
    • Narrator: расширенное правило в промпте — «не описывай использование предмета, которого нет в инвентаре. Обыгрывай внутримира».
    • Метрика [USE_GAP] — норма < 10%.

    Защита 4: селективная регистрация (мебель vs предметы)¶

    • Narrator регистрирует только нарративно/механически значимое.
    • Мебель, архитектура, массовка — НЕ регистрируются.
    • Неоднозначные (картина, чашка, книга) — Narrator решает. По умолчанию НЕ регистрирует.
    • Если игрок пытается взять неоднозначное — retry с просьбой зарегистрировать, если считает нужным.
    • ACTION-интенты (ATTACK, CHECK) не требуют registry. Импровизированное оружие работает без ID.

    Этапы внедрения¶

    Этап 1. Scene Registry как структура данных¶

    • Добавить в GameState: current_location_id, locations: Map<String, Scene>, items: Map<String, Item>.
    • Item получает поля location_id, category, takeable.
    • Никаких изменений в эффектах и логике. Только структура.
    • Миграция: удалить все существующие сессии в БД. Стартуем чисто.
    • Критерий: unit-тесты на структуру, существующие тесты не сломаны.

    Этап 2. ENTER_SCENE + REGISTER_ITEM¶

    • Новые effect'ы в EffectValidator.
    • Промпт Narrator'а: инструкции по эмиту.
    • Логи [SCENE_ENTER], [ITEM_REGISTERED].
    • catalog_classifier пока не трогаем.
    • Критерий: на живой сессии Narrator стабильно эмитит оба effect'а (> 85% ходов). NARRATOR_GAP < 30%.

    Этап 3. catalog_classifier возвращает ID¶

    • Промпт: получить список доступных предметов [(id, name, category)].
    • Возвращает target_id, не имя.
    • fallback_regex удалить.
    • Логи [ITEM_RESOLVE].
    • Критерий: target_id попадает в registry > 90%. target_id=null при наличии предмета < 10%.

    Этап 4. TAKE_ITEM + удаление lootGrantJustified¶

    • Новый effect TAKE_ITEM(item_id).
    • Проверка location + takeable.
    • Удаляем lootGrantJustified, [LOOT_GATE], все reason'ы.
    • Критерий: LOOT работает без regex. Ноль случаев «взял то, чего нет». Ноль случаев «не смог взять то, что Narrator описал».

    Этап 5. Retry + защита от фабрикации¶

    • Retry при LOOT-промахе, если в прозе есть gap.
    • Retry-промпт с показом прозы Narrator'а.
    • Валидация source_quote.
    • Логи [FABRICATION_ATTEMPT], [REGISTERED_FROM_PROSE], [NARRATOR_RETRY].
    • Критерий: [FABRICATION_ATTEMPT] близко к 0 в нормальной сессии. [REGISTERED_FROM_PROSE] < 30%.

    Этап 6. Очистка¶

    • Удалить старую логику resolveLoot.
    • Обновить ContextBuilder — state из registry.
    • Удалить все regex-fallback'и для предметов.

    Метрики (целевые)¶

    Лог Цель
    [SCENE_ENTER] INFO, все перемещения
    [ITEM_REGISTERED] INFO, все регистрации, idempotent true/false
    [ITEM_RESOLVE] target_id=X found=true/false location_match=true/false INFO, все LOOT
    [NARRATOR_GAP] < 30% ходов
    [NARRATOR_OVERREG] < 5% (мебель зарегистрирована)
    [FABRICATION_ATTEMPT] ~0
    [REGISTERED_FROM_PROSE] < 30% предметов
    [NARRATOR_RETRY] < 20% ходов
    [RETRY_COST] < 10% токенов
    [USE_GAP] < 10% USE_ITEM-попыток
    [SCENE_DUPLICATE] < 10% возвратов

    Критерии успеха всей серии¶

    1. Ноль случаев «взял предмет, которого не было».
    2. Ноль случаев «не смог взять предмет, который Narrator описал».
    3. [FABRICATION_ATTEMPT] ~0.
    4. [NARRATOR_GAP] < 15% (после итерации промпта).
    5. LOOT работает без regex вообще.

    Что НЕ делаем¶

    • Не строим глобальную карту мира. Локации создаются Narrator'ом по мере надобности.
    • Не синхронизируем с D&D-каталогом. Предметы — свободные имена.
    • Не блокируем игрока при промахе Narrator'а — метрика, не отказ.
    • Не тащим NPC-инвентари (только @player и локации). Отдельный тикет.
    • Не трогаем боевую систему.
    • Не делаем миграцию БД — wipe sessions.

    Продуктовые решения (приняты)¶

    • ✅ Retry при gap — один, с идемпотентностью и source_quote.
    • ✅ Миграции нет — wipe sessions.
    • ✅ Hybrid-перемещение — Narrator старается, движок логирует gap, игрок может помочь явно.
    • ✅ Идемпотентность через (location_id, normalized_name).
    • ✅ Селективная регистрация — Narrator решает, мебель не регистрируется.
    • ✅ Defensive: retry только при gap в прозе, иначе немедленный отказ.

    Процесс работы¶

    Итеративный: 1. Я даю промпт для агента на очередной этап. 2. Пользователь передаёт агенту. 3. Агент отчитывается (разведка → diff → тесты → hash). 4. Я принимаю или отправляю на доработку. 5. Принят — переходим к следующему этапу.

    Один этап = один коммит. Между этапами — живой прогон или unit-тесты. Если метрики этапа плохие — НЕ идём дальше, чиним промпт.

    Ограничения, которые надо принять¶

    1. LLM нестабилен. 5–15% промахов неизбежны даже с сильным промптом.
    2. Семантические дубликаты («ога-рок» vs «свечка») — только промптом, не движком.
    3. Стоимость токенов растёт: retry + список предметов в промпте классификатора.
    4. Сложные сценарии (NPC отдаёт предмет обратно, кража) — упрощённая модель.
