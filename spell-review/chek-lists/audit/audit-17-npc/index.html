    Фактура из кода¶

    17.1 Модель NPC¶

    Где: backend/app/src/main/kotlin/com/yorva/rules/GameState.kt:887-943. Что: NpcState описывает одного NPC текущей сцены (id/name/factionId/disposition/hp/maxHp/statuses/charisma/isImmortal) с валидацией в init. Поля хранения NPC в CharacterState/SessionEntity нет; enemyJson хранит Enemy, не NpcState. Пример: 

    data class NpcState(
    val id: String,
    val name: String,
    val factionId: String? = null,
    val disposition: NpcDisposition = NpcDisposition.NEUTRAL,
    val hp: Int = 10,
    val maxHp: Int = 10,
    val statuses: List<String> = emptyList(),
    val charisma: Int = 10,
    val isImmortal: Boolean = false,
)
    Создание NpcState в product-коде не найдено (grep: упоминания только в TurnResolver.kt и GameState.kt).

    17.2 Диспозиция и DC переговоров¶

    Где: GameState.kt:876-942. Что: NpcDisposition — 5 уровней (HOSTILE/WARY/NEUTRAL/FRIENDLY/ALLIED). negotiationDc() = 10 + chaMod + dispositionOffset, зажимается [5, 25]. Пример: 

    fun negotiationDc(): Int {
    val chaMod = (charisma - 10) / 2
    val dispositionOffset = when (disposition) {
        NpcDisposition.HOSTILE   -> +8
        NpcDisposition.WARY      -> +4
        NpcDisposition.NEUTRAL   ->  0
        NpcDisposition.FRIENDLY  -> -3
        NpcDisposition.ALLIED    -> -6
    }
    return (10 + chaMod + dispositionOffset).coerceIn(5, 25)
}
    Вызов negotiationDc() — только в TurnResolver.resolveNpcInteraction (:2859).

    17.3 resolveNpcInteraction¶

    Где: backend/app/src/main/kotlin/com/yorva/rules/TurnResolver.kt:2826-2930. Что: DC = negotiationDc() + reputationMod (модификатор тира репутации с фракцией NPC, :2853-2859); бросок d20 + chaMod + profBonus; исходы CRITICAL_SUCCESS/SUCCESS/FAILURE/CRITICAL_FAILURE. State changes: ChangeReputation (±15/±5/−2/−10), ChangeNpcDisposition, GainXp с разовым тегом npc_xp:<id>. Возвращает NpcInteractionResult (GameState.kt:1241-1251). Пример: 

    val npcXpTag = "npc_xp:${npc.id}"
val npcXpAvailable = npcXpTag !in character.xpTriggers
when (outcome) {
    NpcInteractionOutcome.CRITICAL_SUCCESS -> {
        npc.factionId?.let { stateChanges += StateChange.ChangeReputation(it, +15) }
        updatedNpc = npc.copy(disposition = NpcDisposition.FRIENDLY)
        stateChanges += StateChange.ChangeNpcDisposition(npc.id, NpcDisposition.FRIENDLY)
        if (npcXpAvailable) { stateChanges += StateChange.GainXp(nonCombatXp(75, character)); stateChanges += StateChange.AddXpTrigger(npcXpTag) }
    }
    ...
}
    Ветка NpcInteractionOutcome.TRADE пуста (:2905). Enum NpcInteractionOutcome (GameState.kt:948-959) содержит TRADE, но код нигде не выбирает эту ветку.

    17.4 Вызовы и маршрутизация NPC_INTERACTION¶

    Где: ActionType.kt:47-48; TurnResolver.kt:404,558-564. Что: при действии NPC_INTERACTION резолвер уходит в resolveNoRoll (тот же блок, что QUEST_PROGRESS/NO_ROLL), предварительно проверяя упоминание отсутствующего предмета. resolveNpcInteraction в product-коде не вызывается (grep: определение + KDoc-ссылка в GameState.kt:1239, остальное — тесты). Пример: 

    ActionType.NPC_INTERACTION,
ActionType.QUEST_PROGRESS,
ActionType.NO_ROLL -> {
    checkConsumedItemInInventory(actionLower, character) ?: resolveNoRoll(action)
}
    Трата действия: NPC_INTERACTION требует свободного основного действия (TurnResolver.kt:404-405), хотя фактически ничего не резолвит.

    17.5 Каталог social_checks¶

    Где: backend/app/src/main/resources/db/changelog/changes/0033-social_checks.yaml; catalog/CatalogService.kt:168-221. Что: таблица social_checks (code/name_ru/attribute/skill/dc_medium/success_disposition/failure_disposition/success_rep_delta/failure_rep_delta/description/keywords), 12 записей (persuade, intimidate, deceive, haggle, gather_information, recruit_ally, interrogate, flatter, perform, impersonate, calm_animal, insight_check). SocialCheckRow читается по ключевым словам (findSocialCheck) и по коду (findSocialCheckByCode). Пример: 

    ('persuade', 'Убеждение', 'cha', 'persuasion', 15, 'FRIENDLY', 'NEUTRAL', 5, -2, 'Убедить NPC действовать...', 'убежд\w*,уговор\w*,...')
    Поля successDisposition/failureDisposition/successRepDelta/failureRepDelta читаются в SocialCheckRow, но в резолверах не используются (см. 17.6).

    17.6 resolveSocialCheck¶

    Где: TurnResolver.kt:1150-1209; парсинг ActionParser.kt:240-247 (SOCIAL_CHECK их social_checks), dispatch TurnResolver.kt:533-536; fallback на generic CHECK — TurnResolver.kt:2237-2245 (соцпаттерн → Харизма). Что: из SocialCheckRow используются только attribute, dcMedium, nameRu, code. При успехе начисляется XP через addExplorationXp(sceneTag("social:${sc.code}", character, target), xpBase, ...). Disposition/rep-delta из каталога не применяются; целевой NPC не идентифицируется (кроме опционального target). Пример: 

    val sc = catalogService?.findSocialCheckByCode(code) ?: return resolveNoRoll(action)
...
val dc = (sc.dcMedium + profile.mechanics.dcOffset).coerceIn(5, 30)
...
if (success) {
    val xpBase = when { dc >= 20 -> 75; dc >= 15 -> 50; else -> 25 }
    addExplorationXp(sceneTag("social:${sc.code}", character, target), xpBase, character, stateChanges)
}
    Ни StateChange.ChangeReputation, ни StateChange.ChangeNpcDisposition здесь не эмитятся.

    17.7 Репутация¶

    Где: GameState.kt:823-874,1183; SessionService.kt:2286-2289,2043-2044,2442; ContextBuilder.kt:275-281. Что: ReputationTier (HOSTILE/UNFRIENDLY/NEUTRAL/FRIENDLY/ALLIED с dcModifier), FactionReputation (score в [-100,100], applyDelta с зажимом), StateChange.ChangeReputation(factionId, delta). Применяется в applyStateChanges к CharacterState.reputations; репутации выводятся в промпт через buildStateSummary. Пример: 

    is StateChange.ChangeReputation -> {
    val existing = reputations[change.factionId]
        ?: FactionReputation(factionId = change.factionId, name = change.factionId)
    reputations[change.factionId] = existing.applyDelta(change.delta)
}
    Эмиттеров ChangeReputation в product-коде нет: resolveNpcInteraction не вызывается (17.4), resolveSocialCheck rep-delta не использует (17.6). Отдельной таблицы репутаций в БД нет — хранится в JSON CharacterState.

    17.8 ChangeNpcDisposition¶

    Где: GameState.kt:1184-1185; SessionService.kt:2291-2293. Что: StateChange объявлен и эмитится только resolveNpcInteraction, но обработчик в applyStateChanges ничего не делает. Пример: 

    is StateChange.ChangeNpcDisposition -> {
    // NpcDisposition применяется на уровне сессии, не CharacterState
    // CharacterState не хранит состояние NPC — обрабатывается выше по стеку
}

    17.9 Визуальные якоря NPC¶

    Где: anchors/NpcVisualAnchorService.kt, NpcVisualAnchorEntity.kt, NpcVisualAnchorAsyncRunner.kt, NpcVisualAnchorRequestedEvent.kt, NpcVisualAnchorRepository.kt; миграция 0041-npc-visual-anchors.yaml; публикация — SessionService.kt:1540-1552; чтение — :1523,2793-2797. Что: таблица npc_visual_anchors (unique session_id, npc_key). Сервис генерирует описание внешности через AnchorLlmClient и сохраняет; async-раннер слушает событие AFTER_COMMIT. Событие публикуется только для enemyForScene (Enemy — враг/заспавненный архетип), именованные NPC без Enemy якорь не получают. npcKey = archetypeCode или slug имени (SessionService.kt:2855-2856). Пример (баг): 

    val world = worldRepository.findByWorldId(com.yorva.shared.domain.WorldId(sessionId.value)) // NpcVisualAnchorService.kt:24
    В findByWorldId передаётся sessionId.value вместо worldId — world-контекст (genre/description) не подтягивается. Для сравнения: корректный вызов — worldRepository.findByWorldId(session.worldId) (SessionService.kt:987).

    17.10 Известные NPC и атака именованного NPC¶

    Где: SessionService.kt:2785-2797 (определения), :849 (вызов). Что: knownNpcNames строит множество имён из npc_visual_anchors.displayName; detectNpcAttackTarget при атакующем действии вне боя ищет имя цели в лексиконе угроз или среди известных NPC (атака именованного NPC). Опирается только на NPC, для которых есть визуальный якорь (то есть в основном враги/заспавненные архетипы). Пример: 

    private fun knownNpcNames(sessionId: SessionId): Set<String> =
    (npcVisualAnchorService?.findBySessionId(sessionId) ?: emptyList())
        .mapNotNull { it.displayName?.trim()?.lowercase() }
        .toSet()

    17.11 Память и факты¶

    Где: memory/NordRouterArchivist.kt:46-93; memory/MemoryBackgroundService.kt:28-33; sessions/SessionService.kt:38-56,984-991,1151. Что: после каждого хода MemoryBackgroundService.afterTurn запускает архивариуса; NordRouterArchivist LLM-вызовом извлекает факты {factKey, factValue} и делает upsert в facts по (sessionId, factKey). Факты попадают в LLM-контекст через TurnContext.facts: выборка prioritizedFacts() — сначала по ключам HIGH_PRIORITY_FACT_KEYS (npc_, boss_, villain_, ally_, quest_, faction_, betrayal, death_, secret_), затем по свежести, лимит TOP_FACTS = 20. Специального извлечения именно NPC-фактов нет — только ключи-префиксы. Пример: 

    private fun List<FactEntity>.prioritizedFacts(): List<FactEntity> {
    val (priority, rest) = partition { f ->
        HIGH_PRIORITY_FACT_KEYS.any { key -> f.factKey.startsWith(key) || f.factKey.contains(key) }
    }
    return (priority.sortedByDescending { it.updatedAt } + rest.sortedByDescending { it.updatedAt }).take(TOP_FACTS)
}

    17.12 XP за социальные взаимодействия¶

    Где: TurnResolver.kt:1177-1185 (соцпроверка), :2874-2893 (resolveNpcInteraction), :1009-1038 (nonCombatXp, sceneTag, addExplorationXp); rules/XpRules.kt. Что: resolveSocialCheck выдаёт XP по DC (25/50/75) с разовым тегом social:<code>@<scene>[:target]. resolveNpcInteraction задуман с разовым тегом npc_xp:<id> (без привязки к сцене). nonCombatXp масштабирует базу по уровню. Фактически работает только путь соцпроверки. Пример: 

    private fun nonCombatXp(base: Int, character: CharacterState): Int =
    (base * (1.0 + character.level / 4.0)).toInt().coerceAtLeast(1)

    Открытые вопросы¶

    1. resolveNpcInteraction не вызывается из рантайма — является ли это незавершённой интеграцией (планируется вызов при ActionType.NPC_INTERACTION) или NPC-механика намеренно отложена?
    2. NpcState нигде не создаётся и не персистится — где предполагалось хранить состояние NPC (отдельная таблица / enemyJson / ledger)?
    3. Поля social_checks.success_disposition/failure_disposition/success_rep_delta/failure_rep_delta читаются, но не применяются — планировалось ли применение в resolveSocialCheck или каталог носит справочный характер?
    4. ChangeNpcDisposition — обрабатывается ли он «выше по стеку» где-либо (в коде обработчика нет); требуется подтверждение intended-поведения.
    5. NpcVisualAnchorService.kt:24 передаёт sessionId.value в findByWorldId — это баг или временное решение до появления worldId в контексте?
    6. Событие NpcVisualAnchorRequestedEvent публикуется только для enemyForScene — должны ли именованные NPC (не Enemy) получать якоря?
    7. resolveNpcInteraction использует тег npc_xp:<id> без привязки к сцене (в отличие от social:*@scene), а XpRules описывает привязку к сцене — какое поведение считать эталонным?

    Сводка¶

    • Реализовано: каталог social_checks (12 записей) с чтением и матчингом по ключевым словам; модель NpcState/NpcDisposition/negotiationDc(); механика resolveNpcInteraction; модель репутации (ReputationTier/FactionReputation/ChangeReputation) с применением и выводом в контекст; визуальные якоря NPC (таблица, сервис, async-раннер, чтение в сцене); извлечение и приоритизация фактов (NordRouterArchivist, TOP-20); XP за успешные соцпроверки.
    • Частично: resolveSocialCheck (нет применения disposition/rep-delta из каталога, нет идентификации NPC-цели); репутация (применение есть, эмиссия в рантайме отсутствует); визуальные якоря (только для врагов, баг world-контекста); NpcState (модель есть, создание/хранение отсутствует); XP за NPC-взаимодействие (путь resolveNpcInteraction не задействован).
    • Отсутствует: вызов resolveNpcInteraction в рантайме (маршрут NPC_INTERACTION → resolveNoRoll); персистенция состояния/диспозиции NPC; обработчик StateChange.ChangeNpcDisposition; применение success_disposition/failure_disposition/*_rep_delta из social_checks; ветка NpcInteractionOutcome.TRADE; эмиттеры ChangeReputation в product-коде; корректный worldId при генерации якоря NPC.
