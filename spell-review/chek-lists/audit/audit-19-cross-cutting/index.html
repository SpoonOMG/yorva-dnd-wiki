    Фактура из кода¶

    19.1 Трёхуровневая валидация действия¶

    Где: rules/ActionParser.kt:35-289; sessions/SessionService.kt:926-946; dsl/ActionWhitelist.kt; dsl/DslValidator.kt.

    • Уровень 1 — ActionParser.parse: 30 гейтов (hard-override + whitelist → DSL LLM → SemanticActionNormalizer → regex-манёвры → каталоги → CatalogClassifier → regex-fallback → NO_ROLL).
    • Уровень 2 — валидатор цели: ActionParser разрешает сущности по каталогам (lookup), а не substring-матчем (intent/ActionIntent.kt:46-47); замкнутые enum-ы HazardCode/ObjectCategory/ActionType (ActionIntent.kt:10-41).
    • Уровень 3 — ActionWhitelist (YAML-whitelist; в комментарии кода — «YAML 150», фактически 417 уникальных id в 5 файлах; маппинг 25↔150): 
      val canExec = actionWhitelist.canExecuteWithMapping(mechanics.dslId, mechanics.dslParam, request.action, ctx) // :940
if (!canExec) { mechanics = TurnMechanics(action = "no_roll", ..., description = "Действие невозможно в контексте") } // :944
    • Контекст whitelist — Map из 8 флагов (:929-939): hasEnemy, enemy, hasSpellSlots, hasRangedWeapon, inCombat, hasSpell, isConcentrating, hasReaction.
    • Файлы whitelist (уникальных id на файл): action-whitelist-core.yaml — 77, -skills — 73, -exploration — 106, -objects — 89, -magic — 114; уникальных id по всем 5 файлам — 417 (сумма 459, есть пересечения).
    • dsl-registry.yml объявляет 153 команды под ключом commands: (dsl-registry.yml:4).

    19.3 Применение StateChange¶

    Где: sessions/SessionService.kt:2025-2460 (applyStateChanges), when — :2085-2424. - when (change) без else, покрывает все 44 подтипа. - Подтипы-заглушки: ChangeNpcDisposition (:2291 — «применяется на уровне сессии»), UseInventoryItem (:2346 — «применяется через ConsumeItem + Heal/Damage»), RestoreCheckpoint (:2349 — «обрабатывается на уровне SessionService»). - Damage: тело выполняется только при change.target == StateTarget.PLAYER (:2086); ENEMY-урон в CharacterState не применяется, а сумируется для MechanicsBlock.damage (:1407-1410). - Потолок восстановления HP — state.maxHp (:2095,2126), мутируемая локальная maxHp (меняется при level-up :2198-2200) для клампа не используется. - Milestone XP: SetScene → milestone@<scene> + GainXp добавляются к changes до цикла (:2068-2082), отдельно от mechanics.stateChanges. - Концентрация: проверка спасброска при уроне — Dice() создаётся внутри цикла (:2111), внедрённый dice не переиспользуется.

    19.6 Дублирование логики¶

    • Отдых: ClassResourceHelper.restore (classes/ClassResourceHelper.kt:128-144) вызывается из applyStateChanges (:2266,2282), но HP/HitDice/spellSlots пересчитываются в applyStateChanges заново (:2272-2274), т.к. RestService.applyShortRest/applyLongRest возвращает Pair, а вызывающие берут только result (см. audit-11 §11.3, §11.5).
    • Классовые ресурсы: applyStateChanges использует собственные spendClassResource (:2462-2478), restoreClassResource (:2480-2496), activateFeatureResource (:2498-2503) вместо методов ClassResourceHelper; имена ресурсов перечислены в двух местах.
    • Экономия действий: ActionEconomy (GameState.kt:1282) и CombatState (GameState.kt:1405) хранят разные флаги и сбрасываются в разных местах (SessionService.kt:822 сбрасывает actionEconomy; CombatState — в блоке инициативы :1329-1363) (devlog/136).
    • Регистрация экономии: ActionEconomyRegistry (YAML action_economy.yml, приоритет class_bonus_dsl > dsl > action_types > default) + встроенные дефолты в TurnResolver + simulateEconomy (TurnResolver.kt:331).
    • Смена сцены: computeSceneTransition (SessionService.kt:2014-2023) для врага и [SCENE:]-маркер (:1365-1380) для локации — два независимых источника SetScene.
    • Инвентарь-экипировка: единственная реализация applyEquipToInventory (SessionService.kt:3149), вызывается из applyStateChanges (:2322); дублей не найдено.
    • Мёртвый код: if (false && ...) (SessionService.kt:998); неконструируемые ActionType.NPC_INTERACTION/QUEST_PROGRESS; токены MOD_*/PREP_*, секции modifiers/prepositions, findActionTemplate, classifyFallback, conditionFor/isAlways/isNever (devlog/136).

    Открытые вопросы¶

    1. Damage(ENEMY) не применяется в applyStateChanges — источник истины по HP врага находится в TurnResolver/Enemy; связь StateChange-суммы и фактического HP врага требует подтверждения.
    2. Кламп HP в applyStateChanges использует state.maxHp вместо локальной maxHp (:2095,2126) — поведение при level-up в том же changes списке требует уточнения (намеренно или нет).
    3. Ранний выход trap-repeat (:862-906) не проходит whitelist, applyStateChanges, tickDurations и milestone — требуется подтвердить, что это intended.
    4. allStateChanges вычисляется дважды (:958 и :1382); первый результат влияет на stateAfterChanges, второй — на итоговое состояние и MechanicsBlock — какое считается финальным, требует уточнения.
    5. Две модели экономии действий (ActionEconomy и CombatState) — какая источник истины, не зафиксировано.
    6. ActionParser.kt использует Dice() внутри applyStateChanges (:2111) вместо внедрённого — детерминизм/сид не проверены.

    Сводка¶

    • Реализовано: трёхуровневая валидация (parser → whitelist → validator); sealed interface StateChange из 44 подтипов с исчерпывающим when; пайплайн processTurn из 33 шагов с file:line; 5 типов событий (6 вызовов) через @TransactionalEventListener(AFTER_COMMIT); единый сборщик MechanicsBlock; единственная реализация applyEquipToInventory.
    • Частично: применение StateChange (3 no-op подтипа, ENEMY-урон вне CharacterState); ранние выходы обходят часть пассов; allStateChanges считается дважды; дублирование отдыха/классовых ресурсов/экономии действий.
    • Отсутствует: единый источник истины по HP врага в StateChange; единый источник по экономии действий; консолидация ClassResourceHelper ↔ SessionService.spendClassResource/restoreClassResource.
