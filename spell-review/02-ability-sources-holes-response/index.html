    Блок 2.1 — Ответ: сверка 11 дыр ревью с кодом¶

    Проверка дыр 2.1.1–2.1.11 по репозиторию. Формат: вердикт → факты (пути/строки) → варианты закрытия. 4 из 11 формулировок ревью неточны (2.1.5, 2.1.6, 2.1.7, 2.1.11) — см. пометки «УТОЧНЕНО».

    2.1.1 skillChoices отсутствует — ✅ ПОДТВЕРЖДЕНО¶

    Факты: - Поля выбора навыков в CharacterClass нет; есть только фиксированный Proficiencies.skills — CharacterClass.kt:29. - Запрос создания персонажа (CreateCharacterRequest) поля навыков не имеет — SessionDtos.kt:16-39. - При создании все классовые навыки выдаются сразу, без выбора — SessionService.kt:354-360 (it.proficiencies.skills + it.proficiencies.savingThrows), фон добавляет ещё (bgSkills). - Механизм выбора есть только у фич FeatureChoice и обрабатывается resolveL1Choices (SessionService.kt:184-246), но навыков не касается.

    Варианты: - A. Добавить skillChoices: SkillChoice (count: Int, from: List<String>) в CharacterClass + ключ в classes.yml + поле в CreateCharacterRequest; валидация в resolveL1Choices. - B. Смоделировать как ClassFeature c choice (options = пул навыков, maxChoices = count), переиспользуя существующий механизм. - C. Оставить фиксированный список (текущее поведение).

    2.1.2 startingEquipment не применяется — ✅ ПОДТВЕРЖДЕНО¶

    Факты: - Парсится: ClassRegistry.kt:63-69, :122. - В коде, кроме определения/парсинга, не используется (grep по репо — только CharacterClass.kt, ClassRegistry.kt). - Инвентарь при создании жёстко пустой: SessionService.kt:397 (inventory = emptyList()).

    Варианты: - A. Применять при создании персонажа в SessionService (собрать inventory из StartingItem). - B. Отдельный EquipmentService. - C. Отложить.

    2.1.3 multiclassRequirements отсутствует — ✅ ПОДТВЕРЖДЕНО¶

    Факты: - Поля/ключа в YAML нет (grep — пусто). - Есть каркас мультикласса: CharacterState.classLevels, ClassLevelEntry (GameState.kt), заполняется в LevelUpService.kt:207-213; комментарий-задел LevelUpService.kt:206. - Проверки требований (13 в характеристике) нет нигде.

    Варианты: - A. Добавить multiclassRequirements в CharacterClass + YAML. - B. Хардкод-таблица в коде. - C. Отложить (мультикласс пока не поддержан).

    2.1.4 startingEquipment без выбора — ✅ ПОДТВЕРЖДЕНО¶

    Факты: - Модель — плоский список: startingEquipment: List<StartingItem> (CharacterClass.kt:15,32-35). - Групп/опций («(a) … или (b) …») в модели нет; в classes.yml — один набор на класс.

    Варианты: - A. Ввести StartingEquipmentChoice { options: List<List<StartingItem>> }. - B. Оставить плоский список, брать вариант по умолчанию. - C. Отложить.

    2.1.5 spellList не используется — ⚠️ УТОЧНЕНО: используется, но частично¶

    Факты (использование есть): - Валидация подготовки заклинаний (не-wizard): SessionService.kt:1279-1284 (cls.spellList). - Валидация книги волшебника на level-up: LevelUpService.kt:229 (хардкод getClass("wizard")). - Реверс-поиск getClassesForSpell(spellId) — ClassRegistry.kt:50-51 (использований нет, определён, но не вызывается).

    Где НЕ используется: - При стартовом выборе заклинаний (resolveSpellSelection, SessionService.kt:372-379) — spellList не передаётся. - На level-up known-кастеров (sorcerer/bard/warlock) — фильтр по списку класса отсутствует (LevelUpService.kt:238-244).

    Вердикт: дыра в части валидации существует, но тезис «не используется» неверен.

    Варианты: - A. Прокинуть spellList в resolveSpellSelection и в known-кастер ветку level-up. - B. Оставить как есть, признав списки неполными. - C. Полные SRD-списки в данных + единая валидация.

    2.1.6 Прогрессия слотов по casterType — ⚠️ УТОЧНЕНО: реализована на level-up¶

    Факты (реализовано): - LevelUpService.spellSlotsFor(classId, level) — LevelUpService.kt:310-357: - "FULL" -> SpellSlots.forLevel(level) (:314); - "HALF" -> halfSlotsFor(level) (:321-342); - "PACT" -> pactSlotsFor(level) (:345-357); - else -> SpellSlots(). - Таблицы: SpellSlots.forLevel (full caster) — GameState.kt:907-931; PactSlots.forWarlockLevel — ClassResourceHelper.kt:59. - Level-up применяет: LevelUpService.kt:204,268-269.

    Найденный дефект: - При создании персонажа слоты считаются как full caster для всех заклинателей: SessionService.kt:367 (SpellSlots.forLevel(1)), а не через casterType. Для warlock (PACT L1 = 1 слот) и paladin/ranger (HALF L1 = 0 слотов) — неверно.

    Варианты: - A. Заменить :367 на spellSlotsFor(casterType, 1) (вынести метод в общий хелпер). - B. Выдавать слоты только при первом level-up. - C. Оставить.

    2.1.7 asiLevels — default для всех — ❌ НЕВЕРНО: значения заданы по классам¶

    Факты: - В classes.yml ASI заданы явно и по классам: - warrior — [4, 6, 8, 12, 14, 16, 19] (classes.yml:110-116); - rogue — [4, 8, 10, 12, 16, 19] (:353-359); - остальные — якорь *id001 = [4, 8, 12, 16, 19] (:227-232). - Парсер читает asiLevels из YAML; default listOf(4,8,12,16,19) — только фолбэк (CharacterClass.kt:20). - Level-up использует cls.asiLevels — LevelUpService.kt:100-101.

    Вердикт: дыры нет; замечание о «меньше ASI» к данным неприменимо.

    2.1.8 subclassLevel не зафиксирован — ✅ ПОДТВЕРЖДЕНО (жёстко = 3)¶

    Факты: - Уровень выбора подкласса захардкожен: nextLevel == 3 — LevelUpService.kt:63,126. - Поля subclassLevel у CharacterClass нет; в YAML ключа нет. - Канон 5e (клирик/сорк/варлок — 1, друид/волшебник — 2) не учтён. - CharacterClass.subclasses всегда [] (см. 2.1), выбор идёт через SubclassRegistry.getForClass(...) — LevelUpService.kt:64.

    Варианты: - A. Добавить subclassLevel: Int в CharacterClass + YAML, заменить == 3. - B. Хардкод-map classId → level в коде. - C. Оставить общий 3-й уровень.

    2.1.9 Armor/Weapon proficiency не проверяются — ✅ ПОДТВЕРЖДЕНО¶

    Факты: - Атака оружием всегда получает proficiency bonus, без проверки владения: TurnResolver.kt:1413 (+ proficiencyBonus(character.level)). - Броня: isWearingArmor (TurnResolver.kt:49-50) используется только для боевого стиля defense (:2253); проверки владения, помехи (disadvantage) и запрета каста нет. - character.features для armor_heavy (:553,1428) — отдельный флаг, не про владение. - character.proficiencies применяется для навыков/спасбросков/заклинаний, не для оружия/брони. Меток Simple/Martial у предметов нет.

    Варианты: - A. Добавить проверку владения оружием (поле типа оружия у item) + штрафы брони. - B. Только учёт в расчёте атаки (без штрафов брони). - C. Оставить (упрощение).

    2.1.10 31 фича-заглушка «(задел)» — ✅ ПОДТВЕРЖДЕНО; обработка выяснена¶

    Факты: - Заглушек — 31 (напр. classes.yml:75,205,314,515,616,703,775,879,970,1104,1196). - На level-up в ответ попадают все фичи уровня, включая заглушки: LevelUpService.kt:61 (featuresGained), возвращаются в DTO (:82). - Ввод требуется только для фич с choice (LevelUpService.kt:141-173); заглушки без choice проходят без ввода. - CharacterState.features не заполняется для игрока: поле есть (GameState.kt:567), но в LevelUpService.state.copy (:258-276) и при создании не проставляется (записывается только у Enemy, TurnResolver.kt:1047). Сохраняются лишь l1Choices. - При создании фичи L1 фильтруются (SessionService.kt:189), но в состояние не пишутся.

    Вердикт: заглушки = «мёртвый» текст в ответе level-up; механического эффекта и персистентности нет.

    Варианты: - A. Пометить placeholder: true и исключать из ответа/логики. - B. Пропускать фичи без реализации. - C. Оставить как есть.

    2.1.11 classResources инициализация — ⚠️ УТОЧНЕНО: реализована¶

    Факты (реализовано): - ClassResourceHelper.initialResources(...) — ClassResourceHelper.kt:10-66: rage, bardicInspiration, channelDivinity, wildShape, secondWind/actionSurge, ki, layOnHands, sorceryPoints, pactSlots, arcaneRecoveryUsed. - Вызывается при создании: SessionService.kt:380-384. - Обновляется на level-up: LevelUpService.kt:254-256 → resourcesForLevelUp (ClassResourceHelper.kt:68-121). - Восстанавливается на отдыхе: SessionService.kt:1698,1711 → restore (ClassResourceHelper.kt:128-144).

    Найденное замечание: - ranger и rogue возвращают пустой ClassResources() (:52-53), хотя у следопыта/плута в 5e есть ресурсные подклассовые способности (в заглушках).

    Вердикт: дыра в инициализации не подтверждена; ресурсы инициализируются. Открыт вопрос наполнения ranger/rogue.

    Варианты: - A. Оставить пустыми до реализации подклассов. - B. Добить ресурсы (нужны данные).
