    Ответ на ревью Блока 1 — Модель данных умений¶

    Роль: технический аудитор. Ниже — сверка утверждений ревью с кодом и предлагаемые варианты закрытия. Финальные решения по архитектуре помечены ⚠️ и требуют подтверждения (изменения контракта — только после апдейта api-specification/openapi.yaml).

    Поправки к фактуре ревью (важно до обсуждения)¶

    Перед ответами по дырам — 3 уточнения, где утверждения ревью расходятся с кодом:

    1. Concentration НЕ отсутствует. Поле есть у эффектов баффа/дебаффа: Spell.kt:92, Spell.kt:102; парсится в SpellRegistry.kt:56,68; отдаётся в DTO SpellDto.kt:84-86; используется в исполнении SpellService.kt:208 (requiresConcentration) и в SessionService.kt:1519-1554 (спасбросок концентрации max(10, dmg/2), обрыв при провале). То есть это не «❌ Нет», а «⚠️ частично»: есть стаб-ветка SessionService.kt:1796 («MVP: заглушка, концентрация не реализована полностью»).
    2. Duration частично есть. durationRounds у Buff/Debuff (Spell.kt:91,101) и StatModifier (Spell.kt:123), тиканье — SessionService.tickDurations (SessionService.kt:1938-1951), statusDurations (GameState.kt). Нет семантики канона (Instant / 1 min / 1 hour / Until dispelled) — только раунды.
    3. Дыры 1.3/1.4 подтверждены жёстко: grep по id черт (great_weapon_master, sharpshooter, war_caster, polearm_master, sentinel) и id подклассов (champion, assassin, life_domain…) в коде Kotlin — 0 совпадений. При этом черты в feats.yml реально есть (все 5 примеров ревью присутствуют, + lucky, magic_initiate, ritual_caster и т.д.).

    Дополнительный нюанс к 1.1: не «всё не работает». Движок классовых фич есть — ClassFeatureHelper (ClassFeatureHelper.kt:22-85): поиск фичи в тексте действия, проверка экономии действий и ресурса, трата. Spell имеет свой движок (SpellService). Не работают именно Feat / Subclass feature / SkillDef.

    ДЫРА 1.1 — Пять независимых моделей¶

    Вердикт по утверждению: подтверждаю (5 моделей), с уточнением выше.

    Факты: - Spell (Spell.kt:9-23), ClassFeature (CharacterClass.kt:51-65), Feat (FeatRegistry.kt:9-15), Subclass (SubclassRegistry.kt:9-15), SkillDef (SkillRegistry.kt:9-16). - Общего интерфейса/sealed типа нет (grep: совпадений нет). - Единая ось — FeatureActionType (GameState.kt:1151-1157), но она применяется только к ClassFeature. - CastingTime (Spell.kt:37-41) — отдельный enum, маппинга CastingTime → FeatureActionType нет.

    Предлагаемое закрытие (вариант B+): не «один тип на всё» — у Spell слишком другая форма (школа, компоненты, спасбросок, дальность). Ввести общий контракт метаданных активации:

    interface Activatable {
    val id: String
    val actionType: FeatureActionType
    val resourceId: String?
    val usesPerLevel: Map<Int, Int>?
    val recharge: RestType?
}

    Реализуют: ClassFeature, Feat, SubclassFeature, RacialTrait. Для Spell — адаптер Spell.toActivatable() (CastingTime → FeatureActionType), сам Spell не трогаем. Далее AbilityResolver — единая точка «понять, что игрок активирует» вместо ClassFeatureHelper.detectFeature, чтобы фичи/черты/заклинания шли одним путём.

    ⚠️ Требует подтверждения: выбор между «единый интерфейс», «адаптер» и «только адаптер без рефакторинга ClassFeatureHelper».

    ДЫРА 1.2 — Spell-модель не покрывает канон¶

    Вердикт по утверждению: частично. Из таблицы ревью: - Duration — есть частично (durationRounds), нет семантики канона. - Concentration — есть частично (см. поправку 1). - Area — подтверждаю, нет (grep по cone/cube/sphere/cylinder/line — 0 в модели заклинаний; range есть). - Ritual — подтверждаю, нет (CastingTime только ACTION/BONUS_ACTION/REACTION). - Upcast / At Higher Levels — подтверждаю, нет. - MaxTargets — подтверждаю: в spells.json есть ("maxTargets": 1), в модели Spell и парсере SpellRegistry.kt:91-104 — нет.

    Предлагаемое закрытие: расширить Spell до SpellDefinition:

    enum class SpellDuration { INSTANT, ROUNDS, MINUTES, HOURS, UNTIL_DISPEL, SPECIAL }
data class Area(val shape: AreaShape, val size: Int) // CONE/CUBE/CYLINDER/LINE/SPHERE
val duration: SpellDuration
val durationRounds: Int?      // для ROUNDS
val concentration: Boolean    // поднять с эффекта на уровень заклинания
val ritual: Boolean
val upcast: UpcastRule?       // +dice/level, +targets/level, scale by slot
val maxTargets: Int?

    concentration сейчас «размазана» по Buff/Debuff — стоит вынести на Spell, оставив fallback для совместимости. Требуется пересборка spells.json (89 записей) и обновление openapi.yaml.

    ⚠️ Требует подтверждения: сознательно ли maxTargets не парсится (упрощение MVP) или это недоделка; и делать ли school enum вместо String.

    ДЫРА 1.3 — Feat без механики¶

    Вердикт по утверждению: подтверждаю полностью. Feat (FeatRegistry.kt:9-15) хранит только id/name/description/prerequisite/repeatable. Ни один id черты не встречается в Kotlin-коде. Все 41 черта — текст.

    Предлагаемое закрытие: ввести FeatEffect (sealed), по аналогии со SpellEffect:

    sealed class FeatEffect {
    data class PassiveModifier(val stat: String, val value: Int, val type: ModifierType) : FeatEffect()
    data class ResourcePool(val resourceId: String, val maxUses: Int, val recharge: RestType) : FeatEffect()
    data class TriggeredAction(val trigger: Trigger, val actionType: FeatureActionType, ...) : FeatEffect()
    data class Choice(val options: List<FeatureOption>, val maxChoices: Int) : FeatEffect()
}

    Проблема: многие черты — реактивные триггеры (Sentinel — opportunity attack, GWM — бонусная атака при крите, Polearm Master — вход в зону). Для них нужен event-hook в TurnResolver/SessionService, которого сейчас нет.

    Фазово: - Фаза 1 — пассивные модификаторы (Tough, Observant, Resilient) — дёшево, исполняется модификатором состояния. - Фаза 2 — ресурсы (Lucky, Healer). - Фаза 3 — триггеры (нужен event-механизм).

    ⚠️ Требует подтверждения: объём — делаем все три фазы или MVP только Фаза 1.

    ДЫРА 1.4 — Subclass features усечены¶

    Вердикт по утверждению: подтверждаю. SubclassRegistry.kt:41-47 заполняет только name/level/description; поля actionType/resourceId/usesPerLevel/recharge/choice не читаются. Реализаций подклассов в коде нет.

    Предлагаемое закрытие: переиспользовать парсер ClassRegistry (там поля уже поддержаны, ClassRegistry.kt:58-90 включительно) вместо ручного маппинга в SubclassRegistry. Расширить схему subclasses.yml до полной ClassFeature.

    Ограничение: часть подклассов требует новых ресурсов (superiority dice для Battle Master) — их нет в ClassResources (GameState.kt), потребуется дополнить hasResource (ClassFeatureHelper.kt:54-68).

    ⚠️ Требует подтверждения: достаточно ли «распарсить все существующие поля» или сразу добавляем новые ресурсы.

    ДЫРА 1.5 — Racial traits отсутствуют¶

    Вердикт по утверждению: подтверждаю. Каталога рас нет; origin — свободный текст (BackstoryService.kt:33, GameState.kt:700).

    Предлагаемое закрытие: RaceRegistry + RacialTrait : Activatable по той же схеме, что ClassFeature. Плюс согласование: CharacterState.origin (текст) → raceId. Иначе темный/дварфий Darkvision и Relentless Endurance не привязать.

    ⚠️ Требует подтверждения: origin — сейчас LLM-текст; переводим в enum raceId или оставляем текст + маппинг.

    ДЫРА 1.6 — Metamagic / Invocation¶

    Вердикт по утверждению: подтверждаю заголовки-заделы (classes.yml:1104, classes.yml:1196). Реализации нет, отдельных реестров нет. При этом инфраструктура частично готова: в ClassResources есть SORCERY_POINTS и PACT_SLOTS, обрабатываются в ClassFeatureHelper.kt:63-64.

    Предлагаемое закрытие: MetamagicRegistry / InvocationRegistry + SpellModifier-хук на этапе SpellService (метамагия меняет уже накладываемое заклинание). Воззвания — частью FeatEffect-подобные пассивные/активные модификаторы (Agonizing Blast, Repelling Blast — к eldritch blast).

    ⚠️ Требует подтверждения: делать сейчас или после 1.3/1.4 (поскольку используют ту же инфраструктуру эффектов).

    ДЫРА 1.7 — Мультикласс — задел¶

    Вердикт по утверждению: подтверждаю. ClassLevelEntry (GameState.kt:543-546) пишется в LevelUpService.kt:206-210 с комментарием «задел»; единая таблица слотов, PB по сумме уровней, стакирование Extra Attack — не реализованы.

    Предлагаемое закрытие: MulticlassService: - combined spell slot table (правило мультикласса), - Proficiency Bonus по суммарному уровню, - Extra Attack не стакается, - отдельный пул pact slots для warlock. Это крупная фича — предлагаю отложить до стабилизации одиночного класса.

    ⚠️ Требует подтверждения приоритета.

    ДЫРА 1.8 — character_json не используется¶

    Вердикт по утверждению: подтверждаю. CharacterEntity.kt:20-21 объявляет characterJson, но вне entity не встречается. Фактическое состояние — sessions.participants_json (SessionService.kt:432 запись, 479/483/1089/1238/1308 чтение).

    Предлагаемое закрытие: сделать characters.character_json источником истины для CharacterState, а participants_json хранит только связь (participantId → characterId) и метаданные сессии. Это открывает портативный профиль, экспорт/импорт, переиспользование между сессиями.

    ⚠️ Это изменение персистентности + миграция Liquibase + изменение контракта. Требует отдельного ADR и подтверждения.

    ДЫРА 1.9 — Нет таблиц умений в БД¶

    Вердикт по утверждению: подтверждаю — каталоги статичны в classpath, в БД только characters/sessions. Загрузчиков для backgrounds.yml/tools.yml в Kotlin не найдено.

    Предлагаемое закрытие: рекомендую оставить SRD-каталоги статикой (в репозитории, версионируются, не нужна миграция), а в БД вынести только пользовательский/homebrew контент (отдельные таблицы user_content). Так сохраняем простоту и не блокируем будущий маркетплейс.

    ⚠️ Нужно ваше решение: (A) статика для всего сейчас; (B) гибрид статика+homebrew в БД; (C) всё в БД.

    ДЫРА 1.10 — Prerequisite — строка¶

    Вердикт по утверждению: подтверждаю. Feat.prerequisite: String? (FeatRegistry.kt:13), нигде не валидируется (grep: только сохранение). Форматы в feats.yml неструктурны: "CHA 13", "INT или WIS 13", "Средняя броня", "Заклинание стихии", "Способность творить заклинания" (feats.yml:35,50,55,81,101,106,...).

    Предлагаемое закрытие: sealed Prerequisite + парсер:

    sealed class Prerequisite {
    data class AbilityScore(val ability: String, val min: Int) : Prerequisite()
    data class Level(val min: Int) : Prerequisite()
    data class ClassLevel(val classId: String, val min: Int) : Prerequisite()
    data class Spellcasting(val required: Boolean) : Prerequisite()
    data class Proficiency(val type: String) : Prerequisite()
}

    Переписать prerequisite в feats.yml в структурный YAML и добавить валидацию в LevelUpService/создании персонажа.

    ⚠️ Требует подтверждения схемы YAML.
