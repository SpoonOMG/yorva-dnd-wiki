    Ревью Блока 2.8 — состояния (conditions): решения¶

    Канон — D&D 5e SRD. Метод: каждая дыра → конкретное решение в формате «как» с указанием файлов/потока данных. Архитектурные ограничения учтены: Enemy — immutable data class (GameState.kt:634), обновляется через mechanics.enemy → currentEnemy и НЕ через applyStateChanges; applyStateChanges мутирует копию CharacterState игрока (SessionService.kt:1720).

    Spec-first: любые изменения API-контракта (openapi.yaml) — до кода, отдельным согласованием. Здесь помечено, где контракт задеть.

    ФАЗА 1 — GAME-BREAKING BUGS (приоритет 1)¶

    🔴 2.8.A — Дебаффы заклинаний идут игроку, а не врагу¶

    Решение: ввести target в состояние наложения дебаффов и сделать применение зависимым от получателя.

    Как: 1. Расширить модели (не ломая существующий код — добавить дефолт): 

    data class ApplyDebuff(condition: String, target: String = StateTarget.PLAYER, durationRounds: Int)
data class AddCondition(condition: String, target: String = StateTarget.PLAYER)
    (GameState.kt:1112,1184). 2. SpellService.resolveDebuff (spells/SpellService.kt:230-234) выставить target = StateTarget.ENEMY — эффект заклинания бьёт по цели-врагу, а не по кастеру. 3. applyStateChanges (SessionService.kt): добавить ветку ENEMY. Т.к. функция работает только над CharacterState и не возвращает врага, дебаффы по врагу выносим из applyStateChanges: обогащать currentEnemy отдельным пассом applyEnemyStateChanges(allChanges, enemy) сразу после applyStateChanges (:840), возвращая новый Enemy. Одно ядро применяется к обеим целевым сущностям. 4. Enemy.statuses получает condition, длительность пишется в новый Enemy.statusDurations (см. 2.8.D).

    Проверка: cast hold-person на врага → Hold Person у врага (его statuses), у игрока — не появляется.

    🔴 2.8.B — Боевые манёвры на врага теряются¶

    Решение: единая обработка StateTarget.ENEMY в потоке наложений статусов.

    Как: 1. Пятёрку манёвров (TurnResolver.kt:933-936) оставить как есть — ApplyStatus(..., StateTarget.ENEMY). 2. Новый пасс applyEnemyStateChanges (см. 2.8.A.3) обрабатывает ApplyStatus/RemoveStatus/ApplyDebuff/AddCondition с target == ENEMY: - ApplyStatus: if (status !in enemy.statuses) enemy.statuses += status; при durationRounds > 0 — enemy.statusDurations[status] = durationRounds. - RemoveStatus: enemy.statuses -= status и enemy.statusDurations -= status (закрывает E/D). 3. После пасса присвоить currentEnemy = appliedEnemy и пробросить в TurnResponse.

    Проверка: trip → у врага в statuses появляется Сбит с ног, isProne == true.

    🔴 2.8.C — Enemy использует CON-модификатор игрока для спасброска¶

    Решение: дать Enemy собственные характеристики спасбросков.

    Как: 1. В Enemy (GameState.kt:634) добавить необязательные поля с дефолтами: 

    val conMod: Int = 0
val saveBonusOverrides: Map<String, Int> = emptyMap()  // по типу спасброска
    Значения заполняются из профиля врага (архетип/creatures.json) — см. зависимость 2.7.PP. 2. TurnResolver.kt:2297 заменить character.effectiveAttributes.conMod на enemy.conMod; для типовых спасбросков использовать saveBonusOverrides. 3. SpellService.resolveDebuff (:223) уже идёт через resolveEnemySave(target) — там тоже перейти на собственный CON врага (это единый источник).

    Проверка: враг с conMod = 2 спасброском учитывает свой CON, а не CON игрока.

    🔴 2.8.D — Enemy без statusDurations — все состояния бесконечны¶

    Решение: завести длительности у врага и тикать их.

    Как: 1. Enemy (GameState.kt:643) добавить val statusDurations: Map<String, Int> = emptyMap(). 2. Тик: в applyEnemyTurn/перед спасброском врага (или в applyEnemyStateChanges) уменьшать statusDurations на 1 и, где <= 0, снимать статус (аналогично tickDurations у игрока, SessionService.kt:2188-2208). 3. Распространение на биндинг ответа: Enemy сериализуется в TurnResponse — добавить statusDurations в схему openapi.yaml (контракт).

    Проверка: Ошеломлён, durationRounds=1 на врага снимается после его тика.

    ФАЗА 2 — ФУНДАМЕНТ (критично)¶

    🔴 2.8.F — Нет enum Condition / ConditionRegistry¶

    Решение: один источник правды для состояний + зарегистрированные эффекты.

    Как: 1. enum class ConditionId — 15 канонических SRD + служебные (BLINDED..UNCONSCIOUS, EXHAUSTION, CONCENTRATING, RAGING, HASTED, SLOWED, CURSED, MARKED… по словарю action-whitelist-core.yaml:240-264). 2. ConditionRegistry — YAML conditions.yml, загружается в @PostConstruct: - id, nameRu, nameEn, incapacitating, blocksMove/Speak/Attack/Perceive, imposesDisadvantageOn {checks, attacks, saves, dexteritySaves}, saveEnd: bool, sourceTracked: bool, magical: bool. 3. Все системные наборы (GameState.kt:604-620,675) заменить производными от registry (единый источник), сохранив публичный АПИ statuses как List<String> для совместимости. 4. Маппинг English↔русский — в YAML (nameEn↔nameRu), закрывает отсутствие маппинга (2.8.1.5).

    Проверка: ConditionRegistry["restrained"].nameRu == "Опутанный" и blocksMove == true.

    🔴 2.8.M — canMove/canSpeak/canPerceive не используются¶

    Решение: гейтить движение/речь/восприятие в диспетчеризации действий.

    Как: 1. В TurnResolver.resolve перед исполнением действия (:184) расширить блокировку: - если действие — перемещение (MOVE_*) → проверять canMove; - если действие — разговор/социальное → проверять canSpeak; - если действие — восприятие/исследование (SNIFF/SEARCH/LOOK) → проверять canPerceive. 2. Оставить !canAct || !canAttack как глобальный гейт боя. 3. Причина — из blockedCapabilityReason (уже умеет MOVE/ATTACK; добавить SPEAK/PERCEIVE ветки).

    Проверка: игрок со статусом Связан (Restrained, только NO_MOVE) не может перемещаться, но может атаковать/говорить.

    🔴 2.8.N — REMOVE_CONDITION / APPLY_CONDITION не парсятся¶

    Решение: разобрать обе команды DSL в ActionParser.

    Как: 1. ActionParser.kt:517-523: - REMOVE_CONDITION → новый ActionType.CONDITION_REMOVE (или CHECK), резолвит конкретную строку состояния (парсер condition-параметра по ConditionRegistry). - APPLY_CONDITION → ActionType.CONDITION_APPLY, требует StateTarget. 2. В TurnResolver добавить resolveRemoveCondition / resolveApplyCondition, эмитящие RemoveStatus/ApplyStatus с целевым target. 3. Это чинит «Lesser/Greater Restoration» и заклинания-снятия состояния.

    Проверка: снять ошеломление → у игрока Ошеломлён удаляется из statuses и statusDurations.

    🟡 2.8.E — RemoveStatus не чистит statusDurations¶

    Решение: в обоих местах удалять и длительность.

    Как: 1. SessionService.kt:1817-1819 (игрок): statuses.remove(change.status); statusDurations -= change.status. 2. Новый applyEnemyStateChanges (2.8.A/B): тот же паттерн для врага. 3. Проверить все места statuses.remove(...) на предмет синхронной чистки statusDurations (:1802-1803 Heal, :1912-1921 death success, :1930-1937 stabilized, :1794-1795 long rest, :2366 Уклонение).

    Проверка: после снятия статуса запись в statusDurations отсутствует; повторное наложение не погашается остатком старой длительности.

    🔴 2.8.G — Invisible отсутствует¶

    Решение: ввести канонический статус Невидим/Invisible.

    Как: 1. ConditionId.INVISIBLE + nameRu = "Невидим" в conditions.yml. 2. Эффекты (в ConditionRegistry и TurnResolver): - атакующие по невидимому не имеют цели по зрению → помеха атакующим (добавить в targetGrantsAdvantage, TurnResolver.kt:1987-1988); - сам невидимый — преимущество на атаки (добавить в hasAdvantageOnAttacks, :1984-1985); - нельзя быть целью заклинаний «требующих видеть цель» (валидация target в SpellService); - можно прятаться без укрытия (послабление в проверке Скрытности). 3. Дать источник наложению: заклинание «Невидимость» (spells.json) → ApplyStatus("Невидим", PLAYER, durationRounds).

    🔴 2.8.H — Petrified отсутствует¶

    Решение: ввести канонический статус Окаменел/Petrified.

    Как: 1. ConditionId.PETRIFIED + nameRu = "Окаменел" в conditions.yml. 2. Эффекты: - incapacitating = true (в INCAPACITATING производный); - resistance to all damage → флаг в registry, учитывать в уроне (как immunities/resistances, :163-168); - immune to poison/disease → включить в наборы; - блокировка действия/движения — наследуется от incapacitating. 3. Источник — дебафф из монстров/заклинаний (SpellService).

    🔴 2.8.I — Exhaustion не работает¶

    Решение: реализовать 6 уровней с механическими эффектами.

    Как: 1. Таблица эффектов уровня в ConditionRegistry/отдельном ExhaustionRules: | уровень | эффект | |---|---| | 1 | помеха на ability checks | | 2 | скорость ×0.5 | | 3 | помеха на атаки и спасброски | | 4 | maxHp ×0.5 | | 5 | скорость 0 | | 6 | смерть | 2. В TurnResolver/RestService учитывать: - hasDisadvantageOnChecks (+1 уровень → true); - hasDisadvantageOnAttacks (>=3); - спасброски: >=3 → помеха (resolveSaveEnds, enemy save); - maxHp: >=4 → эффективный maxHp = floor(maxHp/2) при восстановлении; - движение: >=2 → половинное, >=5 → запрет; - exhaustion == 6 → смерть (проверка в конце хода). 3. Снятие уже есть (RestService.kt:90,97 long rest −1).

    Проверка: exhaustion=3 → игрок атакует с помехой и спасбросами с помехой; exhaustion=6 → смерть.

    🔴 2.8.J — Нет conditionImmunities¶

    Решение: иммунитеты к состояниям у врага.

    Как: 1. Enemy (GameState.kt:654) добавить val conditionImmunities: List<ConditionId> = emptyList() (+ в openapi.yaml/профиль монстра). 2. В точке наложения (addConditionToEnemy, см. 2.8.A/B) пропускать состояние, если condition in enemy.conditionImmunities (не добавлять, добавить нарратив «не действует»). 3. Наполнять из YAML-профиля (undead → immune Charmed/Exhaustion/Frightened/Poisoned; construct → +Paralyzed/Petrified).

    🔴 2.8.K — Нет creatureType¶

    Решение: тип существа + валидация целей заклинаний по типу.

    Как: 1. Enemy (GameState.kt) добавить val creatureType: CreatureType? (enum: HUMANOID, BEAST, UNDEAD, DRAGON, CONSTRUCT, FIEND, ELEMENTAL, MONSTROSITY…). 2. spells.json — каждому заклинанию целевые типы (targetCreatureTypes) и целевое условие (onlyHumanoid: true у charm/person). 3. SpellService — при выборе цели проверять creatureType: Hold Person применим только к HUMANOID, иначе — иммунитет/провал. 4. Это фундамент для корректных типовых иммунитетов (2.8.J).

    🟡 2.8.L — Нет legendary resistance¶

    Решение: дать боссам пул легендарных сопротивлений и расходовать при провале спасброска.

    Как: 1. Enemy (GameState.kt:634) добавить val legendaryResistance: Int = 0 (число использований 3/day для боссов, 0 — по умолчанию) + профиль монстра/openapi.yaml. 2. Единая точка спасброска врага — SavingThrowResolver.resolveEnemySave (SavingThrowResolver.kt:62-84) и ручной save в applyEnemyTurn (TurnResolver.kt:2291-2320). В обеих при !success && legendaryResistance > 0: 

    legendaryResistance -= 1
success = true   // «Легендарное сопротивление»
    3. Возвращать обновлённый Enemy (расход LR) наружу через mechanics.enemy, чтобы счётчик не жил только в локальной копии. 4. Восстановление 3/day — при long rest / смене боя (аналогично ресурсам действия).

    Проверка: босс с legendaryResistance=3 автоматически проходит первые 3 проваленных спасброска за день, счётчик уменьшается и отображается.

    ФАЗА 3 — ТОЧНОСТЬ (важно)¶

    🟡 2.8.O — Whitelist без condition-ключей¶

    Решение: добавить статусные ключи в контекст whitelist.

    Как: 1. В ctx (SessionService.kt:810-820) добавить: isStunned, isProne, isGrappled, isRestrained, isBlinded, isCharmed, isFrightened из геттеров CharacterState (GameState.kt:495,498,501 + новые производные от registry). 2. isRaging, hasCover, hasConcealment, hasAdvantage — завести поля/геттеры или удалить из YAML, если не поддерживаются (чтобы условие не молча было false).

    🟡 2.8.P — Разные INCAPACITATING_STATUSES у игрока/врага¶

    Решение: выровнять наборы через единый источник.

    Как: 1. После введения ConditionRegistry (2.8.F) Enemy.INCAPACITATING_STATUSES (GameState.kt:675) наследует тот же набор, что и у игрока (:604), включая Недееспособен. Убрать ручной дубль.

    🟡 2.8.Q — Разные наборы помехи атакам игрока/врага¶

    Решение: унифицировать набор помехи атакам.

    Как: 1. Враг (TurnResolver.kt:2353 — Отравлен/Ошеломлён/Испуган) привести к полному набору игрока (:1985 — + Связан, Опутанный, Оглушён, Ослеплён, Сбит с ног). 2. Вынести общий набор в ConditionRegistry.imposesDisadvantageOnAttacks.

    🟡 2.8.R — Charmed неполный¶

    Решение: добавить запрет атаки на очарователя + преимущество на соц.

    Как: 1. Charmed → source (см. 2.8.Y) в ConditionRegistry/statusSource. 2. TurnResolver: если у игрока Charmed и target-действие — атака на источник очарования → блокировать. 3. Источник получает advantage на social/влияния на очарованного.

    🟡 2.8.S — Frightened неполный¶

    Решение: добавить запрет приближения и условные помехи.

    Как: 1. Frightened + source (см. 2.8.Y). 2. TurnResolver: блокировать перемещение к источнику страха; применять помехи атак/проверок только пока источник в поле зрения (проверка видимости цели).

    🟡 2.8.T — Deafened/Stunned путаются¶

    Решение: развести «Оглушён» (Deafened) и «Ошеломлён» (Stunned).

    Как: 1. Оглушён — только NO_PERCEPTION_STATUSES и NO_SPEAK-аналог (глухой не слышит); убрать Оглушён из INCAPACITATING (GameState.kt:604) и из SAVE_END_STATUSES (если Deafened не должен иметь save-end по канону — проверить). 2. Ошеломлён (Stunned) — остаётся incapacitating (+ SAVE_END). 3. Перепроверить все чтения строки Оглушён (:619,1979,1988,675).

    🟡 2.8.U — Нет advantage/авто-провала на спасброски от состояний¶

    Решение: модификаторы спасбросков от состояний.

    Как: 1. В ConditionRegistry добавить imposesDisadvantageOn {dexteritySaves, strengthSaves, allSaves}. 2. SavingThrowResolver: Restrained → помеха на DEX; Paralyzed/Stunned/Unconscious → авто-провал DEX/STR (по SRD). 3. Учесть в resolveEnemySave и resolveSaveEnds.

    🟡 2.8.V — ApplyDebuff игнорирует durationRounds¶

    Решение: писать длительность в соответствующий получатель.

    Как: 1. После 2.8.A/2.8.D ApplyDebuff пишет statusDurations[durationRounds] у PLAYER или ENEMY в зависимости от target. Игнор убрать.

    🟡 2.8.W — AddCondition без target/duration¶

    Решение: использовать AddCondition только как служебный, либо добавить поля.

    Как: 1. AddCondition оставить как краткую обёртку, но наложение идти через общее ядро (addStatusToTarget с target/duration). Если нужно полное состояние — использовать ApplyStatus(..., durationRounds). 2. Из SpellService.resolveDebuff (:230) убрать двойное добавление — оставить один путь (ApplyDebuff), чтобы не дублировать наложение.

    🟡 2.8.X — ApplyStatus пишет длительность даже для ENEMY¶

    Решение: гейтить запись длительности по target.

    Как: 1. SessionService.kt:1813-1815: писать statusDurations только когда change.target == StateTarget.PLAYER (у врага длительность живёт в Enemy.statusDurations, см. 2.8.D). 2. Это устраняет загрязнение карты длительностей игрока.

    🟡 2.8.Y — Нет source tracking¶

    Решение: связать состояние с источником (заклинанием/эффектом/монстром).

    Как: 1. CharacterState/Enemy — statusSources: Map<String, String> (статус → sourceId). 2. Заполнять при наложении через заклинания (ApplyStatus/AddCondition... с source). 3. Dispel Magic/контр-заклинания: убирать только magical состояния (ConditionRegistry.magical == true). 4. Полезно для 2.8.R/S (source страха/очарования).

    ФАЗА 4 — UX (желательно)¶

    🟢 2.8.Z — Нет REST-эндпоинтов управления состояниями¶

    Решение: добавить управляющие эндпоинты.

    Как: 1. В SessionController добавить: - POST /sessions/{id}/conditions/apply ({ condition, target }), - POST /sessions/{id}/conditions/remove ({ condition, target }) — для GM-инструментов/диагностики. 2. Контракт согласовать в openapi.yaml (spec-first) до реализации.

    🟢 2.8.AA — Нет отдельного save DC per condition¶

    Решение: DC из контекста заклинания/эффекта.

    Как: 1. Пробивать dc через StateChange (targetSaveDc: Int?) от источника наложения (заклинание spells.json даёт свой DC) вместо хардкода dc = 12 (resolveSaveEnds, TurnResolver.kt:49) и 13 + dcOffset у врага. 2. ConditionRegistry — дефолтный DC на состояние, если не задан источником.

    ФАЗА 3.5 — УТОЧНЕНИЯ ПО РЕВЬЮ (маппинг, поток, сериализация)¶

    Критичность по ревью: BB, CC, KK, NN — 🔴; DD–LL, MM, OO–TT — 🟡; UU — 🟢.

    🔴 2.8.BB — String → ConditionId: маппинг алиасов¶

    Решение: единый ConditionResolver с таблицей синонимов (русские строки из кода → ConditionId).

    Как: 1. object ConditionResolver в com.yorva.conditions: 

    object ConditionResolver {
    private val aliases = mapOf(
        "Опутан" to ConditionId.RESTRAINED,
        "Опутанный" to ConditionId.RESTRAINED,
        "Захвачен" to ConditionId.GRAPPLED,
        "Удержан" to ConditionId.GRAPPLED,
        "Грапплинг" to ConditionId.GRAPPLED,
        "Сбит с ног" to ConditionId.PRONE,
        "Сбита с ног" to ConditionId.PRONE,
        "Лежит" to ConditionId.PRONE,
        "Ничком" to ConditionId.PRONE,
        "Зачарован" to ConditionId.CHARMED,
        "Очарован" to ConditionId.CHARMED,
        // + все оставшиеся строки из перечня 2.8.1.6
    )
    fun resolve(s: String): ConditionId? = aliases[s] ?: ConditionId.fromRu(s)
}
    2. ConditionId.fromRu(s) — маппинг по nameRu. resolve принимает и русский, и English (STUNNED/Ошеломлён → STUNNED), закрывает дыру 2.8.QQ. 3. Унарная семантика по SRD: Опутан = Опутанный = RESTRAINED, все 4 строки Prone = PRONE, Grappled-строки (Захвачен/Удержан/Грапплинг) = GRAPPLED. 4. Все системные наборы (GameState.kt:604-620,675) и хардкод-проверки переводятся на ConditionResolver (см. 2.8.SS) — убирает риск «Опутан не найдётся в registry». 5. Уникальный источник: ConditionRegistry индексируется по ConditionId.

    🔴 2.8.CC — applyEnemyStateChanges: источник Enemy и порядок пассов¶

    Решение: явный поток данных Enemy через mechanics.enemy + фиксированный порядок в SessionService.processTurn.

    Как: 1. Источник врага — mechanics.enemy (результат TurnResolver.resolve, SessionService.kt:805). В processTurn уже есть var mechanics; взять val enemy = mechanics.enemy ?: currentEnemy перед применением изменений. 2. Порядок в processTurn (:838-852): 1. applyStateChanges — только StateTarget.PLAYER (2.8.PP); 2. applyEnemyStateChanges(allChanges, enemy) — только StateTarget.ENEMY → новый Enemy; 3. tickDurations — игрок (:844); 4. tickEnemyDurations — враг (2.8.MM); 5. resolveSaveEnds — игрок (:845); save-enemy — внутри applyEnemyTurn. 3. Прокинуть наружу: 

    val appliedEnemy = applyEnemyStateChanges(allChanges, enemy)
val updatedMechanics = mechanics.copy(enemy = appliedEnemy)
currentEnemy = appliedEnemy
    currentEnemy — session-поле; единственная точка чтения/записи в processTurn. 4. applyEnemyStateChanges возвращает immutable Enemy, не мутирует ничего иначе, не сериализуется сам по себе.

    🟡 2.8.DD — Petrified resistance to all damage¶

    Решение: флаг resistsAllDamage + ветка в DamageResolver.

    Как: 1. DamageResolver.apply / SpellService.resolveDamage (SpellService.kt:163-168): 

    fun apply(amount, type, resist, immune, vuln, resistsAll: Boolean = false): Int {
    if (resistsAll) return amount / 2
    // существующая логика resist/immune/vuln
}
    2. ConditionId.PETRIFIED in statuses → resistsAll = true. 3. Не разворачивать «в 13 типов» — дешёвый булев флаг (вариант A, а не B).

    🟡 2.8.EE — Exhaustion ×0.5 maxHp при получении в бою¶

    Решение: пересчёт HP сразу в момент изменения уровня истощения.

    Как: 1. Единая applyExhaustion(state, newLevel): 

    val newMax = state.maxHp / 2                                   // если newLevel >= 4
val clampedHp = minOf(state.hp, newMax)                        // урезать, если current больше
state.copy(maxHp = newMax, hp = clampedHp)
    2. Вызывать и при повышении (в бою), и при long rest (понижении), чтобы не расходились. 3. При hp == 0 — оставить 0, не эмитить новый unconscious (смерть/стабильность отдельно).

    🟡 2.8.FF — Invisible: «видит ли атакующий невидимого»¶

    Решение: проверка детекции при вычислении преимуществ/помех атак.

    Как: 1. attackerCanSeeInvisible = "see_invisibility" in attacker.statuses || "truesight" in attacker.features. 2. В targetGrantsAdvantage/hasAdvantageOnAttacks (TurnResolver.kt:1984-1988): 

    if (target.isInvisible && !attackerCanSeeInvisible) attackerDisadvantage = true
    3. See Invisibility — не состояние, а заклинание → activeModifier типа SEE_INVISIBLE (CharacterState.activeModifiers, GameState.kt), снимается по durationRounds через tickDurations. В ConditionRegistry не заводить. 4. truesight — постоянная фича существа (features), проверяется отдельно.

    🟡 2.8.GG — Frightened «в поле зрения» без системы видимости¶

    Решение: MVP-упрощение A — помеха всегда, пока источник жив (координат/LoS нет).

    Как: 1. Хранить источник страха (statusSources[FRIGHTENED], 2.8.Y). 2. Пока источник жив/не удалён — помехи применяются безусловно (TurnResolver.kt:1979,1985). 3. Запрет приближения в MVP не реализуем — «MOVE_* к цели» без координат/LoS неопределимо. Оставляем только помехи. Опционально: флаг sourceNearby, если источник в текущей сцене; при sourceNearby == true — блокировать все MOVE_* (грубое приближение), иначе не блокировать. 4. TODO: полноценный запрет приближения — после системы позиционирования.

    🟡 2.8.HH — Charmed: advantage на social от источника¶

    Решение: связать источник очарования с NPC в social-проверке.

    Как: 1. В resolveNpcInteraction (TurnResolver.kt): 

    val charmer = statusSources[ConditionId.CHARMED]
if (npcId == charmer) advantage = true
    2. Зависит от statusSources (2.8.Y). При отсутствии источника — бонусов нет.

    🟡 2.8.II — ConditionId: сериализация в JSON¶

    Решение: @JsonValue = nameRu, для обратной совместимости с русскими строками.

    Как: 1. enum ConditionId { STUNNED("Ошеломлён"), ...; @get:JsonValue val nameRu }. 2. Сериализация/десериализация по nameRu (существующий формат "Ошеломлён"). 3. ConditionId в openapi.yaml — string (nameRu); frontend/LLM не меняют контракт.

    🟡 2.8.JJ — statusSources: очистка при снятии¶

    Решение: чистить statusSources синхронно с удалением статуса.

    Как: 1. RemoveStatus (SessionService.kt:1817-1819) и enemy-пасс: statusSources -= status. 2. tickDurations (:2199-2206) и tickEnemyDurations: при истечении чистить и источник. 3. Все места statuses.remove(...) — сопроводить чисткой statusSources (Heal :1802, death :1912, stabilized :1930, long rest :1794, Уклонение :2366).

    🔴 2.8.KK — targetCreatureTypes: миграция 89 заклинаний¶

    Решение: опциональное поле, заполнить только узкие заклинания (~10).

    Как: 1. spells.json — "targetCreatureTypes": ["HUMANOID", ...]; null/отсутствие = «все». 2. Классификация вручную только для точечных: Hold Person/Charm Person (HUMANOID), Dominate Beast (BEAST), Hold Monster (все), Fear (не CONSTRUCT) и т.п.; Fireball и прочие AoE/все — не трогать. 3. SpellService — при выборе цели: если creatureType цели (2.8.K) не входит в targetCreatureTypes → эффект не действует (нарратив «не действует»).

    🟡 2.8.LL — Dispel Magic: spell level check¶

    Решение: хранить уровень заклинания-источника и проверять при диспеле.

    Как: 1. statusSpellLevels: Map<String, Int> (статус → уровень) рядом с statusSources (2.8.Y). 2. Dispel Magic: auto-dispel если level <= 3; иначе d20 + mod >= 10 + level. 3. Только для magical == true состояний (2.8.Y).

    🟡 2.8.MM — tickEnemyDurations: тик в конце каждого хода игрока¶

    Решение: тикать врага синхронно с игроком, а не только при его ходе.

    Как: 1. Вызывать tickEnemyDurations в processTurn сразу после tickDurations игрока (порядок 2.8.CC.2.4), каждый ход/атаку. 2. Исключает «вечный дебафф», когда враг всё время ошеломлён и не получает собственный ход.

    🔴 2.8.NN — Exhaustion 6 → мгновенная смерть¶

    Решение: проверка смертельной точки в момент повышения, а не в конце хода.

    Как: 1. В applyExhaustion (2.8.EE) и в обработке изменений exhaustion: if (newLevel >= 6) isDead = true немедленно. 2. Игрок не «ходит с exhaustion 6 до конца хода».

    🟡 2.8.OO — saveBonusOverrides: формат ключей¶

    Решение: унифицировать с proficiencies (короткие коды).

    Как: 1. Ключи — "str", "dex", "con", "int", "wis", "cha". 2. SavingThrowResolver.resolveEnemySave (SavingThrowResolver.kt:66-72) читает enemy.saveBonusOverrides[savingThrow.ability.lowercase()], fallback на enemy.statusSaveBonus → (позже, 2.8.C) enemy.conMod.

    🟡 2.8.PP — Разделение Player/Enemy изменений¶

    Решение: жёстко разделить ветки по StateTarget; урон врага — отдельно.

    Как: 1. applyStateChanges — только target == PLAYER (включая Damage(PLAYER), Heal, статусы). 2. applyEnemyStateChanges — только target == ENEMY и только статусы. StateChange.Damage и RemoveStatus-подобные HP-изменения врага здесь игнорировать (Damage(ENEMY) — no-op), чтобы не было двойного применения урона. 3. Damage(ENEMY) генерируется в TurnResolver, кладётся в mechanics.enemy; HP врага меняется только там.

    🟡 2.8.QQ — Валидация statuses (English vs русский)¶

    Решение: нормализация при записи через ConditionResolver.resolve.

    Как: 1. В точках добавления статуса (player/enemy пассы): ConditionResolver.resolve(raw). 2. Если null (неизвестная строка) — не добавлять в statuses, логировать. 3. Принимать и English, и русский (2.8.BB).

    🟡 2.8.RR — Petrified и isUnconscious¶

    Решение: расширить isUnconscious условием петрификации.

    Как: 1. isUnconscious (GameState.kt:489): (hp == 0 && !isDead && ...) || PETRIFIED in statuses. 2. Petrified — incapacitating + unconscious-семантика при любом HP. 3. Петрифицированный не проходит death saves (окаменел, не умирает в бою).

    🟡 2.8.SS — ConditionRegistry как источник hasDisadvantageOnChecks¶

    Решение: заменить хардкод-наборы чтением из registry.

    Как: 1. TurnResolver.kt:1978-1979 (player) и :2353 (enemy) → ConditionRegistry через ConditionResolver: 

    c.statuses.any { ConditionResolver.resolve(it)?.imposesDisadvantageOnChecks == true }
    2. Аналогично :1984-1988 (attacks/advantage) и наборы GameState.kt:604-620,675. 3. Один источник правды; синонимы работают автоматически (2.8.BB).

    🟡 2.8.TT — Invisible: «прятаться без укрытия»¶

    Решение: модифицировать условие проверки Скрытности.

    Как: 1. В resolveSkillCheck/CHECK_STEALTH (TurnResolver.kt:815-816,908-909): 

    val needsCover = ConditionId.INVISIBLE !in c.statuses
if (!needsCover) /* разрешить stealth без укрытия */
    2. Не менять DC — только условие «нужно укрытие».

    🟢 2.8.UU — Exhaustion 1: «disadvantage on ability checks» — все проверки¶

    Решение: помеха на все CHECK_* (навыки + raw ability).

    Как: 1. hasDisadvantageOnChecks учитывает exhaustion >= 1 → помеха на все ability checks. 2. Не распространять на спасброски/атаки (там свои пороги 3/3 и 3).
