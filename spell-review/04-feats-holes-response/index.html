    Аудит умений/заклинаний — Блок 2.4: Черты (feats) — Сверка дыр (ответ на 10 пунктов)¶

    Роль: технический аудитор. Только факты из кода. База-фактура: 04-feats.md. Формат — как в предыдущих блоках.

    1 (2.4.A/2.4.J). Путей level-up ровно два; tough работает только в одном¶

    Третий путь отсутствует. Подтверждено по всем записям изменения level в Kotlin-коде main:

    Путь Функция Условие tough
    Ручной LevelUpService.levelUp + SessionService.levelUp (SessionService.kt:1415-1431), endpoint POST /api/v1/sessions/{id}/levelup (SessionController.kt:192-211), фронт sessionsApi.levelUp (frontend/lib/api.ts:488-489, вызов CharacterPanel.tsx:588-592) LevelUpService.kt:94-96 — canLevelUp; работает при любом level < 20, требует наличие XP да (LevelUpService.kt:188,194)
    Авто (при начислении XP) GainXp-ветка внутри applyStateChanges (SessionService.kt:1755-1786) level += 1 (:1762) инкремент при xp >= xpForNextLevel(level) в цикле while нет — применяется только (hitDie/2)+1+conMod (:1764)

    Записи изменения level вне этих двух путей нет (единственные level += 1/level = 20/copy(... level = nextLevel) — LevelUpService.kt:211, SessionService.kt:1762,1763,1786). applyStateChanges вызывается один раз из processTurn (SessionService.kt:759), т.е. авто-повышение срабатывает только на обработке хода.

    Факт-различие (для решения по объединению): - GainXp-путь начисляет сразу весь каскад уровней в while-цикле и молча инкрементит pendingASI на 4/8/12/16/19 (:1778-1780), не спрашивая выбора. - Ручной путь levelUp требует один предопределённый уровень и ожидает явный asiChoice/featId (LevelUpService.kt:108). - Формула HP различается: авто (hitDie/2)+1+conMod (:1764) vs ручной avgHitDie(cls.hitDie)+conModAfter (:179) с ретроактивным CON (:182-186). - Оба устанавливают pendingASI: ручной — принудительно 0 (LevelUpService.kt:270), авто — инкремент (:1779). Сброса pendingASI при ручном levelUp на НЕ-ASI уровне нет.

    2 (2.4.B). allocateASI не принимает черту¶

    • allocateASI (SessionService.kt:1265-1333) принимает AsiRequest { allocations: Map<String, Int> } (SessionDtos.kt:105-107). Поля featId в DTO нет; в теле функции — только alloc.allocations (:1274).
    • Endpoint: POST /api/v1/sessions/{id}/levelup/asi (SessionController.kt:136-154).
    • Фронтенд: sessionsApi.allocateASI(sessionId, allocations) (frontend/lib/api.ts:479-480), вызов из CharacterPanel.tsx:578. Отсюда в allocateASI путь для черты отсутствует.
    • Факт: выбрать черту можно только через featId в LevelUpRequest ручного POST /levelup (LevelUpService.kt:35). Т.е. два конца: pendingASI-путь (авто-XP) вообще не даёт черты; черта доступна лишь в ручном levelUp.

    3/10 (2.4.C + 2.4.K). Фронтенд: 12 захардкоженных черт, вызова /api/feats нет¶

    • Вызов GET /api/feats во фронтенде отсутствует (grep api/feats, /feats по frontend/lib, frontend/components, frontend/app — 0 совпадений).
    • Фактические 12 опций захардкожены в <select>: frontend/components/game/LevelUpModal.tsx:263-274 (tough, alert, war_caster, sharpshooter, skilled, lucky, healer, inspiring_leader, magic_initiate, tavern_brawler, ritual_caster, athlete).
    • Бэкенд-эндпоинт существует: GET /api/feats → featRegistry.getAll() (LevelController.kt:21-22, полный путь GET /api/feats), но фронтенд его не использует. CharacterPanel/LevelUpModal список не запрашивают — берут хардкод.
    • Как фронт получает список черт → не получает из API, только из хардкода LevelUpModal.tsx:263-274.

    4 (2.4.D). Формула tough: обработка только в ручном levelUp; при level-up на 2 — не суммируется ретро¶

    • Единственное место обработки tough — LevelUpService.kt:187-196. Других совпадений по tough в Kotlin main нет.
    • Логика при взятии черты на level N (req.featId == "tough", :188): hpDelta += 2 * nextLevel. Комментарии (:189-193) фиксируют сомнения автора: неясно, не двойной ли учёт.
    • При повторном level-up на nextLevel (уже есть tough в newFeats, ветка else if ("tough" in newFeats) :194): тело пустое (:195) — повторный бонус +2 за уровень НЕ добавляется; идёт только avg+CON из :179.
    • Трекер «уровней, прожитых с tough» отсутствует — ретро-начисления за каждый прожитый уровень (в т.ч. взятие на 1 через Variant Human, а затем прирост на 2) не хранится и не вычисляется. Так как черт у Variant Human сейчас вообще нет (см. 2.4.5 — нет расовой системы), сценарий «tough на 1-м уровне» недостижим текущим кодом.
    • Факт-формула авто-пути GainXp (SessionService.kt:1764) tough не учитывает вовсе.

    5 (2.4.E). require(hasAsi xor hasFeat) только на ASI-уровнях¶

    • Условие выполняется только если needsAsi = cls.asiLevels.contains(nextLevel) (LevelUpService.kt:101).
    • asiLevels по умолчанию [4,8,12,16,19] (CharacterClass.kt:19), переопределяемо в classes.yml через asiLevels (ClassRegistry.kt:103).
    • На НЕ-ASI уровне (:120-122): require(req.asiChoice == null && req.featId == null) — передача asiChoice/featId запрещена (ошибка).
    • На ASI-уровне, если игрок не передал ни asiChoice, ни featId: hasAsi=false, hasFeat=false → require(false xor false) = require(false) → бросает IllegalArgumentException "On ASI level must provide exactly one..." (:108).
    • Фронтенд это же блокирует заранее: LevelUpModal.tsx:280 — кнопка disabled пока (mode==="asi" && sum!==2) || (mode==="feat" && !featId); по умолчанию mode = "asi" (:32). Так что без выбора подтвердить нельзя.
    • Факт: на ASI-уровне без выбора — исключение; пропустить ASI нельзя.

    6 (2.4.F). healer в ClassMatcherService.kt:25 — это алиас класса «cleric», НЕ черта¶

    • ClassMatcherService.kt:25 — строка списка keywordMap["cleric"]: ... "священник", "пастырь", "целитель", "хил", "медик", "врач", "cleric", "priest", "healer", "medic". Это маппинг синонимов класса клирик.
    • Никакого отношения к черте healer: код черты в Kotlin нигде не используется (см. 2.4.7).
    • Подтверждаю: совпадение ложное (class-alias), не признак реализации черты.

    7 (2.4.M). Prerequisite: только комментарий, исполняемого кода проверки нет¶

    • Исполняемый код проверки prerequisite отсутствует. Совпадения по prereq/prerequisite в main — только FeatRegistry.kt:13,42 (объявление и парсинг поля).
    • LevelUpService.kt:114-115 — это исключительно комментарии: 
      // prereq check simplified: if contains "13" check ability >=13 (e.g., CHA 13)
// skip strict for now, just store
      За ними пустая строка :116 и newFeats = newFeats + feat.id (:117). Проверки условия нет.
    • Единственная проверка при выборе черты — существование (:112) и repeatable (:113).

    8 (2.4.H). mobile в feats.yml отсутствует — подтверждено¶

    • grep mobile backend/app/src/main/resources/feats.yml → NOT FOUND.
    • В списке 41 черты (04-feats.md:2.4.1.5) mobile нет. Подтверждаю пропуск.

    9 (2.4.K). DTO FeatDto нет — сериализуется сам Feat¶

    • Отдельного DTO нет (grep FeatDto — 0 совпадений).
    • LevelController.feat() возвращает featRegistry.getAll() — список data-класса Feat (FeatRegistry.kt:9-15), сериализация напрямую (Jackson).
    • Во фронтенде тип списка черт отсутствует: типизирован только feats?: string[] — поле CharacterState.feats (frontend/lib/api.ts:264), не DTO каталога. DTO-тип Feat во фронте не объявлен, т.к. /api/feats не используется.

    10 (2.4.C+K). Как фронт получает список черт — резюме¶

    Не из API. Единственный источник — хардкод 12 <option> в frontend/components/game/LevelUpModal.tsx:263-274. Эндпоинт GET /api/feats существует, но фронтендом не вызывается; DTO каталога черт во фронтенде нет.
