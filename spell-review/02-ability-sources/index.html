    Аудит умений/заклинаний — Блок 2: Источники умений¶

    Технический аудит кодовой базы. Только факты из кода. Пути и номера строк — по состоянию репозитория на момент аудита. Прогресс: 2.1 (остальные подблоки — ожидают подтверждения).

    2.1. Каталог классов¶

    2.1.1. Где хранится каталог классов¶

    • Файл: backend/app/src/main/resources/classes.yml.
    • Загрузчик: ClassRegistry — backend/app/src/main/kotlin/com/yorva/classes/ClassRegistry.kt:9-205.
    • Точка входа: @PostConstruct fun loadClasses() — ClassRegistry.kt:16-46.
    • Ключ верхнего уровня: classes (ClassRegistry.kt:28).
    • При отсутствии файла / ошибке парсинга / пустом результате — loadFallback() (ClassRegistry.kt:160-204), 12 хардкод-классов.
    • Данные в памяти: MutableMap<String, CharacterClass> (ClassRegistry.kt:14), доступ через getClass(id) (:48) и getAllClasses() (:49).

    2.1.2. Поля класса (CharacterClass)¶

    CharacterClass.kt:7-22:

    data class CharacterClass(
    val id: String, // warrior, wizard, rogue, cleric
    val name: String, // "Воин"
    val description: String,
    val hitDie: Int, // 6, 8, 10, 12
    val primaryAbility: String, // STRENGTH, DEXTERITY...
    val spellcastingAbility: String?, // INTELLIGENCE, WISDOM, CHARISMA или null
    val proficiencies: Proficiencies,
    val startingEquipment: List<StartingItem>,
    val spellList: List<String> = emptyList(),
    val features: List<ClassFeature> = emptyList(),
    val narrativeHint: String = "",
    val asiLevels: List<Int> = listOf(4, 8, 12, 16, 19),
    val casterType: String = "NONE", // FULL/HALF/PACT/NONE — для таблиц слотов
    val subclasses: List<String> = emptyList(), // задел под подклассы (выбор на 3)
)

    Смежные типы (CharacterClass.kt:24-35):

    data class Proficiencies(
    val armor: List<String> = emptyList(), // LIGHT, MEDIUM, HEAVY, SHIELD
    val weapons: List<String> = emptyList(), // SIMPLE, MARTIAL
    val tools: List<String> = emptyList(),
    val savingThrows: List<String> = emptyList(), // STRENGTH, CONSTITUTION...
    val skills: List<String> = emptyList(), // athletics, stealth...
)

data class StartingItem(
    val id: String,
    val quantity: Int = 1,
)

    Строки ключей: classes.yml:2, 120, 235, 362, 461, 543, 636, 722, 795, 901, 992, 1120.

    2.1.4. Как парсятся class features из YAML¶

    Парсер: ClassRegistry.parseClass(...) — ClassRegistry.kt:54-130; блок фич — ClassRegistry.kt:70-102.

    Заполняемые поля (ClassRegistry.kt:71-101):

    Поле ClassFeature Источник в YAML Строка
    name name (обязательное, as String) :73
    level level (по умолчанию 1) :74
    description description (по умолчанию "") :75
    actionType actionType → FeatureActionType.valueOf(uppercase), иначе null :76-82
    resourceId resourceId → uppercase :83
    usesPerLevel usesPerLevel (ключ Int/String → Int, значение Int/String → Int) :84-92
    recharge recharge → RestType.valueOf(uppercase), иначе null :93-99
    choice choice → parseFeatureChoice(...) — :132-158 :100

    Ключи, реально встречающиеся на уровне фичи в classes.yml (6 пробелов отступа): actionType (18), choice (7), description (120), level (120), recharge (11), resourceId (11), usesPerLevel (10). Других ключей на уровне фичи нет. Неизвестные ключи в парсере явно не обрабатываются (пропускаются без ошибки).

    Каталог фич: 120 записей (grep -cE "^ - name:"). Часть фич — заголовки-заделы («(задел)») — 31 вхождение, например: Воинский архетип (задел) (classes.yml:75), Школа магии (задел) (:205), Метамагия (задел) (:1104), Мистические воззвания (задел) (:1196).

    Пример фичи warrior (classes.yml:34-57) с choice:

        - name: Боевой стиль
      level: 1
      description: 'Выберите 1: Оборона/Дуэлянт/Двуручник/Защита/Стрельба/Сражение двумя оружиями'
      choice:
        type: single
        options:
        - id: defense
          name: Оборона
          description: +1 AC в доспехах
        - id: dueling
          name: Дуэлянт
          description: +2 к урону одноручным оружием

    Пример фичи с ресурсом (classes.yml:58-65):

        - name: Второе дыхание
      level: 1
      description: Бонусным действием восстанавливаете 1d10 + уровень здоровья
      actionType: BONUS_ACTION
      resourceId: SECOND_WIND
      usesPerLevel:
        1: 1
      recharge: SHORT_REST

    parseFeatureChoice (ClassRegistry.kt:132-158): читает type (SINGLE/MULTIPLE, по умолчанию SINGLE), options (id/name/description, id в lowercase), maxChoices (Int/String, по умолчанию 1); при пустых options возвращает null.

    2.1.5. Поле spellcastingAbility¶

    • Есть: CharacterClass.kt:13; парсится ClassRegistry.kt:120, фолбэк-классы задают его вручную (ClassRegistry.kt:176,189,195,...).
    • Экспонируется в API: ClassController.kt:39,56,77.
    • Используется:
    • SessionService.kt:89,95,114,367,374 — при создании персонажа (в т.ч. resolveSpellSelection, spellSlots, spellMod).
    • SessionService.kt:1262 (val castAbility = cls.spellcastingAbility), :1638.
    • LevelUpService — через casterType/класс (см. 2.9).

    2.1.6. Поле hitDie¶

    • Есть: CharacterClass.kt:11; парсится ClassRegistry.kt:118 (по умолчанию 8).
    • Используется:
    • Стартовое HP: SessionService.kt:351-352 (hitDie + CONmod).
    • Level-up HP: LevelUpService.kt:175-178 (avgHitDie(cls.hitDie)), :306, :362.
    • Повышение HP в бою/апе: SessionService.kt:1626-1629 (hitDie / 2 + 1 + conMod).
    • Короткий отдых: TurnResolver.kt:1711-1720, RestService.kt:13-33.

    2.1.7. Field saving-throw proficiencies¶

    • Отдельного поля savingThrowProficiencies у CharacterClass нет. Есть Proficiencies.savingThrows: List<String> (CharacterClass.kt:28), парсится ClassRegistry.kt:60 (uppercase).
    • Использование: сливается с навыками при создании — SessionService.kt:355 ((it.proficiencies.skills + it.proficiencies.savingThrows).map { it.lowercase() }).
    • Спасброски: SavingThrowResolver.kt:31 (ability in character.proficiencies).

    2.1.8. Поле skillChoices (выбор навыков)¶

    • Поля skillChoices / числа выбираемых навыков у CharacterClass нет. Есть фиксированный список Proficiencies.skills: List<String> (CharacterClass.kt:29), парсится в lowercase (ClassRegistry.kt:61).
    • Механизм выбора опций есть только у фич — FeatureChoice/FeatureOption (CharacterClass.kt:37-49), парсится ClassRegistry.kt:132-158.
    • В classes.yml ключей skillChoices/skillChoice нет (grep — пусто).

    2.1.9. Поле startingEquipment¶

    • Есть: CharacterClass.kt:15 (List<StartingItem>), парсится ClassRegistry.kt:63-69.
    • Пример (classes.yml:25-31):
        startingEquipment:
    - id: longsword
      quantity: 1
    - id: shield
      quantity: 1
    - id: chainmail
      quantity: 1
    • Использование в коде, кроме определения и парсинга: не найдено (grep startingEquipment/StartingItem — только CharacterClass.kt:15,32 и ClassRegistry.kt). В сервисах создания/боя/inventory не применяется.

    2.1.10. Field multiclass requirements¶

    • Отсутствует: поля в CharacterClass нет; ключа multiclass/requirements в classes.yml нет (grep — пусто).
    • Единственное упоминание в коде: комментарий // classLevels for multiclass задел — LevelUpService.kt:206.

    2.1 (доп.) Поле subclasses¶

    • Поле есть: CharacterClass.kt:21, парсится ClassRegistry.kt:128.
    • Во всех 12 классах classes.yml значение subclasses: [] (строки classes.yml:119, 234, 361, 460, 542, 635, 721, 794, 900, 991, 1119, 1220).
    • Использование поля в коде, кроме парсинга: не найдено (подклассы грузятся отдельно из subclasses.yml, см. 2.2).

    2.2.3. Как выбирается подкласс (уровень и валидация)¶

    • Уровень выбора захардкожен: nextLevel == 3 — LevelUpService.kt:63,126. Поля subclassLevel нет (см. 2.1.8).
    • Список опций при выборе: subclassRegistry.getForClass(state.canonicalClassId!!) — LevelUpService.kt:64.
    • Обязательность: на 3 уровне req.subclassId обязателен, иначе исключение — LevelUpService.kt:128.
    • Валидация принадлежности классу: require(sub.classId == cls.id) — LevelUpService.kt:130.
    • Запрет смены после выбора: LevelUpService.kt:132-134.
    • При создании персонажа subclassId не задаётся (CharacterState.subclassId по умолчанию null, GameState.kt:443).
    • API-список подклассов: LevelController.kt:26,36 (GET по classId).
    • Комментарий-пометка о каноне: subclasses.yml:94 — «Жрец — домены (канонично на 1, у нас на 3 для униформы, пометка)».

    2.2.4. Парсинг subclass features — усечение¶

    SubclassRegistry.kt:40-47:

    val featsRaw = m["features"] as? List<Map<String, Any>> ?: emptyList()
val feats = featsRaw.map {
    ClassFeature(
        name = it["name"] as String,
        level = (it["level"] as? Int) ?: 3,
        description = it["description"] as? String ?: "",
    )
}
    • Читаются только name, level (default 3), description.
    • actionType, resourceId, usesPerLevel, recharge, choice не парсятся — теряются, даже если появятся в YAML (переиспользуется ClassFeature, но поля не заполняются).
    • Следствие для level-up: фильтр it.choice != null по подклассам (LevelUpService.kt:143,147) всегда пуст → выборы подклассов не срабатывают (совпадает с 1.4.1 Блока 1).
    • Формат данных: фичи записаны inline-маппингом (139 записей вида { name, level, description }) — напр. subclasses.yml:8-12. Других ключей в фичах нет (grep по {...} — только name/level/description).

    2.2.5. Subclass resources (Channel Divinity, Superiority Dice, Wild Shape)¶

    • В subclasses.yml полей ресурсов нет; «ресурсные» фичи — только текст: Канал: Сохранение жизни (:101), Канал: Сияние рассвета (:111), Канал: Направленный удар (:120), Изгнание нечестивых (:224), Клятва вражды (:244), Боевое превосходство («4 кости d8, 3 приёма») (:18), Боевой дикий облик (:182) и т.п.
    • ClassResources (GameState.kt:1244) и ClassResourceHelper знают только классовые ресурсы: channelDivinity/maxChannelDivinity (cleric — ClassResourceHelper.kt:29-32, paladin — :46-51), wildShape/maxWildShape (druid — :33-36). Инициализируются из классовых фич по имени (usesFor, ClassResourceHelper.kt:146-150), не из подклассов.
    • Superiority Dice (battle_master) отдельной сущностью не моделируются — только текст фичи.
    • Итог: подкласс не приносит собственных ресурсов; подклассовые «Канал/Кости/Облик» механически не подключены.

    2.2.6. Subclass spell lists (Domain, Circle, Oath)¶

    • В subclasses.yml списков заклинаний нет (grep spell|домен|круг|клятва — только описания фич, напр. :94,97,169,220,240).
    • Доменные заклинания заданы в коде: resolveL1Choices → Сессия (SessionService.kt:217-231): life → bless, cure-wounds; light → burning-hands, faerie-fire; war → divine-favor, shield-of-faith (+ доп. броня/оружие).
    • Покровитель (warlock) expanded spells — тоже в коде: SessionService.kt:232-238 (archfey/fiend/great_old_one).
    • Данные о доменах/кругах/клятвах как о заклинательных списках подкласса отсутствуют.

    2.2.7. Взаимодействие с l1Choices¶

    • Выбор архетипа на 1 уровне идёт не через подкласс, а через классовые фичи-выборы: Домен (classes.yml:424), Происхождение чародея (:1066), Потусторонний покровитель (:1178) → resolveL1Choices (SessionService.kt:209-245).
    • Те же сущности существуют как подклассы: life/light/war (cleric), draconic/wild_magic (sorcerer), archfey/fiend/great_old_one (warlock) — subclasses.yml.
    • Итог: для этих трёх классов выбор дублируется дважды — на L1 (l1Choices, даёт часть эффектов) и на L3 (subclassId, даёт текст фич). Связь между выборами отсутствует (l1Choices не влияет на subclassId и наоборот).
    • У колдуна дополнительно дубль-заглушка Потусторонний покровитель (задел) (classes.yml:1193) рядом с живой фичой (:1178).
