    Аудит умений/заклинаний — Блок 2.4: Черты (feats)¶

    Роль: технический аудитор. Только факты из кода. Формат — как в Блоках 1, 2.1, 2.2, 2.3. Если чего-то нет — «отсутствует». Пути и строки указаны.

    2.4.1. КАТАЛОГ ЧЕРТ¶

    2.4.1.1. Где хранится каталог¶

    backend/app/src/main/resources/feats.yml (207 строк).

    2.4.1.2. Загрузчик¶

    com.yorva.classes.FeatRegistry — backend/app/src/main/kotlin/com/yorva/classes/FeatRegistry.kt.

    • @Component, Spring-бин; загрузка через @PostConstruct fun load() (FeatRegistry.kt:24-50).
    • Источник: resourceLoader.getResource("classpath:feats.yml") (:27), парсер org.yaml.snakeyaml.Yaml (:32).
    • Корневой узел: data["feats"] as? List<Map<String, Any>> ?: emptyList() (:35).
    • Доступ: get(id: String): Feat? (:52, id приводится к lowercase), getAll(): List<Feat> (:53).
    • Лог при загрузке: Loaded ${feats.size} feats (:46).

    2.4.1.3. Структура файла¶

    Корневой ключ feats:, значение — список объектов с полями id, name, description, prerequisite, repeatable. Пример (feats.yml:2-6):

      - id: alert
    name: "Бдительный"
    description: "+5 к инициативе, не можете быть застигнуты врасплох, невидимые не получают advantage"
    prerequisite: null
    repeatable: false

    prerequisite встречается как null либо как строка ("CHA 13", "INT или WIS 13", "Средняя броня", "Тяжелая броня", "Легкая броня", "Способность творить заклинания", "Заклинание стихии", "Заговор с атакой", "DEX 13", "STR 13").

    2.4.1.4. Количество черт¶

    41 запись (подсчёт по - id:). При этом комментарий в самом файле (feats.yml:62) гласит: # Остальные SRD — заглушки для полноты 42.

    2.4.1.5. Реализованные черты (полный список id)¶

    alert, athlete, lucky, magic_initiate, healer, sharpshooter, war_caster, skilled,
tavern_brawler, inspiring_leader, ritual_caster, tough, actor, charger, crossbow_expert,
defensive_duelist, dual_wielder, dungeon_delver, durable, elemental_adept, grappler,
great_weapon_master, heavily_armored, heavy_armor_master, keen_mind, lightly_armored,

shield_master, spell_sniper, skulker, weapon_master

    2.4.1.6. Fallback¶

    • Ресурс feats.yml не найден → logger.warn("feats.yml not found") и return, карта остаётся пустой (FeatRegistry.kt:28-31).
    • Исключение при загрузке → logger.error(...), карта остаётся пустой (:47-49).
    • get(id) для отсутствующего id возвращает null (:52).
    • Резервного/встроенного каталога черт — отсутствует.
    • Дубликаты id не проверяются: значение перезаписывается в MutableMap (:38).

    2.4.2. МОДЕЛЬ ДАННЫХ ЧЕРТЫ¶

    2.4.2.1. data class Feat целиком¶

    FeatRegistry.kt:9-15:

    data class Feat(
    val id: String,
    val name: String,
    val description: String,
    val prerequisite: String? = null,
    val repeatable: Boolean = false,
)

    2.4.2.2. Поля¶

    id, name, description, prerequisite (String?), repeatable (Boolean).

    2.4.2.3. Поля actionType/resourceId/usesPerLevel/recharge/choice/effect¶

    Отсутствуют у Feat. Эти поля есть в другой модели — ClassFeature (CharacterClass.kt:51-65): name, level, description, actionType: FeatureActionType?, resourceId: String?, usesPerLevel: Map<Int,Int>?, recharge: RestType?, choice: FeatureChoice?. У Feat их нет.

    2.4.2.4. Связь Feat с ClassFeature / общий интерфейс¶

    • Общий интерфейс (interface Activatable) — отсутствует: grep Activatable по Kotlin-коду — 0 совпадений.
    • Feat — самостоятельный data class, не реализует интерфейсов, не наследует ClassFeature.
    • ClassFeature — самостоятельный data class, интерфейсов не реализует.
    • Единственная точка, где ClassFeature переиспользуется за пределами классов: SubclassRegistry.kt:40-47 — фичи подклассов парсятся в ClassFeature (только name/level/description).
    • Связи Feat → ClassFeature в коде нет.

    2.4.3. ПАРСИНГ ЧЕРТ¶

    2.4.3.1. Где парсятся¶

    FeatRegistry.load() — FeatRegistry.kt:36-45, разбор data["feats"] as? List<Map<String, Any>> (:35), элементы raw.forEach { ... }.

    2.4.3.2. Какие поля парсятся, какие игнорируются¶

    Парсятся (:37-44): - id → (it["id"] as? String ?: return@forEach).lowercase(); - name → it["name"] as? String ?: id; - description → it["description"] as? String ?: ""; - prerequisite → it["prerequisite"] as? String (только строка, не список/структура); - repeatable → it["repeatable"] as? Boolean ?: false.

    Игнорируются: нечего игнорировать — в feats.yml присутствуют только эти 5 ключей. Проверка ключей файла: id (41), name (41), description (41), prerequisite (41), repeatable (41). Ключей actionType/resourceId/usesPerLevel/recharge/choice/effect в feats.yml нет.

    2.4.3.3. prerequisite¶

    Есть: Feat.prerequisite: String? (:13), парсится как «сырая» строка (:42). Структуры/разбора нет.

    2.4.3.4. Структура FeatEffect¶

    Отсутствует. Grep FeatEffect — 0 совпадений. Модели эффекта черты нет.

    2.4.4. PREREQUISITE¶

    2.4.4.1. Тип поля prerequisite¶

    String? (FeatRegistry.kt:13). Не sealed class, не enum.

    2.4.4.2. Валидация prerequisite¶

    Отсутствует. В LevelUpService.kt:114-115 есть комментарий // prereq check simplified: if contains "13" check ability >=13 (e.g., CHA 13) и // skip strict for now, just store. Исполняемого кода проверки prerequisite в Kotlin нет (grep prerequisite — совпадения только в FeatRegistry.kt:13,42).

    2.4.4.3. Форматы в feats.yml (примеры)¶

    Строковые значения: "CHA 13" (:50), "INT или WIS 13" (:55), "DEX 13" (:81, :201), "STR 13" (:106), "Средняя броня" (:116, :151), "Тяжелая броня" (:121), "Легкая броня" (:156), "Способность творить заклинания" (:35), "Заклинание стихии" (:101), "Заговор с атакой" (:196). Остальные — null.

    2.4.4.4. PrerequisiteGroup(AND/OR)¶

    Отсутствует. Grep Prerequisite/prerequisite — только строковое поле Feat.

    2.4.5. ВЫБОР ЧЕРТ¶

    2.4.5.1. Выбор черты при создании персонажа¶

    Отсутствует. CreateSessionRequest (SessionDtos.kt:15-40) не содержит поля featId; SessionService.create (SessionService.kt:395-406) конструирует CharacterState без параметра feats (значение по умолчанию emptyList()). Расовой системы нет (см. Блок 2.3), поэтому Variant Human / Custom Lineage как источники черты отсутствуют.

    2.4.5.2. При level-up — ASI vs Feat¶

    Два независимых механизма: - Ручной LevelUpService.levelUp (LevelUpService.kt:94-122): если nextLevel in cls.asiLevels, требуется ровно одно из asiChoice / featId — require(hasAsi xor hasFeat) (:108). - Автоматический (при начислении XP) SessionService, ветка StateChange.GainXp (SessionService.kt:1755-1786): на уровнях 4/8/12/16/19 инкрементит pendingASI (:1778-1780). Опции «взять черту» в этом пути нет.

    2.4.5.3. Где обрабатывается выбор¶

    • LevelUpService.levelUp — LevelUpService.kt:105-119 (ASI или featId).
    • SessionService.allocateASI — SessionService.kt:1265-1333 (расход pendingASI только на характеристики).
    • Endpoint'ы: POST /sessions/{sessionId}/levelup (SessionController.kt:192-211) → SessionService.levelUp (:1414-1431); POST /sessions/{sessionId}/levelup/asi (SessionController.kt:136-154).

    2.4.5.4. Валидация prerequisite при выборе¶

    Отсутствует (см. 2.4.4.2; LevelUpService.kt:112-116 — берётся featRegistry.get(featId), проверяется только существование и повтор).

    2.4.5.5. Учёт repeatable¶

    Реализован в ручном пути: LevelUpService.kt:113 — if (feat.id in state.feats && !feat.repeatable) throw IllegalArgumentException("Feat already taken ${feat.id}"). В feats.yml у всех 41 черт repeatable: false. В автоматическом пути (allocateASI) проверки repeatable нет, т.к. черты там не выбираются.

    2.4.5.6. Список доступных черт для игрока¶

    • GET /api/feats → featRegistry.getAll() (все 41) — LevelController.kt:21-22.
    • LevelUpPreview списка доступных черт не содержит (LevelUpService.kt:12-26; только requiresChoice.asiOrFeat).
    • Фронтенд список не запрашивает у API: в frontend/components/game/LevelUpModal.tsx:262-274 захардкожены 12 опций (tough, alert, war_caster, sharpshooter, skilled, lucky, healer, inspiring_leader, magic_initiate, tavern_brawler, ritual_caster, athlete); вызов /api/feats во фронтенде — 0 совпадений.

    2.4.6. ЭФФЕКТЫ ЧЕРТ В ИГРЕ¶

    2.4.6.1. Влияние Feat на CharacterState¶

    Черта хранится как строка: CharacterState.feats: List<String> (GameState.kt:415). Чтение/запись state.feats найдены только в LevelUpService.kt:104,113,116,261. В TurnResolver, SessionService, SpellService, ContextBuilder обращений к feats нет.

    2.4.6.2. Влияние Feat на бой (TurnResolver)¶

    Отсутствует. Grep feat/черт в TurnResolver.kt — совпадений по чертам нет. Ветки TurnResolver, привязанные к фичам, работают только с Enemy.features (строковые коды архетипа: armor_heavy :575,1474, regeneration :2278, enrage :2285, legendary/multiattack :2326-2327, poison_strike :2350) и с классовыми фичами через ClassFeatureHelper (:174-175). CharacterState.feats не читается.

    2.4.6.3. Влияние Feat на навыки¶

    Отсутствует. Владения формируются в SessionService.create из класса и предыстории: proficiencies = (classProficiencies + bgSkills...) (SessionService.kt:354-361); черты не участвуют.

    2.4.6.4. Влияние Feat на HP¶

    Единственный механизм — tough в ручном LevelUpService.kt:187-196 (+2 * nextLevel к hpDelta). В автоматическом пути GainXp (SessionService.kt:1761-1767) бонус tough не применяется.

    2.4.6.5. Влияние Feat на AC¶

    Отсутствует. AC: 10 + attrs.dexMod при создании (SessionService.kt:353), плюс effectiveAc от экипировки (GameState.kt:502-506), плюс draconicAcFloor сорцерера (SessionService.kt:394). Черты в расчёт AC не входят.

    2.4.6.6. Влияние Feat на spellcasting¶

    Отсутствует. Черты не изменяют spellbook/spellsKnown/preparedSpells/слоты. Поля выбираются по классу (SessionService.create:371-379, LevelUpService:215-247).

    2.4.6.7. Поле featEffects в CharacterState¶

    Отсутствует. В CharacterState (GameState.kt:326-454) поля featEffects (как и classFeatures/subclassFeatures/racialTraits) нет. Есть только feats: List<String> (:415). Поле Enemy.features (:573) относится к Enemy.

    2.4.7. РЕАЛИЗОВАННЫЕ ЧЕРТЫ¶

    2.4.7.1. Механически реализованные черты¶

    Grep по всем 41 id в Kotlin-коде (backend/app/src/main/kotlin) дал совпадения только: - tough — LevelUpService.kt:188 и :194. - healer — ClassMatcherService.kt:25, но это алиас класса «cleric», не черта.

    Итого механически обрабатывается 1 черта — tough, и только в ручном LevelUpService.

    2.4.7.2. Grep по перечисленным id¶

    • lucky — 0 совпадений в Kotlin.
    • alert — 0.
    • sharpshooter — 0.
    • war_caster — 0.
    • sentinel — 0.
    • polearm_master — 0.
    • great_weapon_master — 0.
    • magic_initiate — 0.
    • Остальные 32 id — 0 (кроме healer как алиас класса и tough).

    Черты присутствуют только как данные feats.yml (name/description) и возвращаются GET /api/feats; парсинга эффектов нет.

    2.4.8. ЧЕРТЫ С ВЫБОРОМ¶

    2.4.8.1. Какие черты дают выбор¶

    В feats.yml как текст описания — magic_initiate (:17-21), ritual_caster (:52-56), spell_sniper (:193-197). metamagic_adept в feats.yml отсутствует (в списке 41 нет).

    2.4.8.2. FeatureChoice для черт¶

    Отсутствует. FeatureChoice/FeatureOption/FeatureChoiceType определены в CharacterClass.kt:37-49 и используются только ClassFeature (:64) и ClassRegistry.parseFeatureChoice (ClassRegistry.kt:132-155). Feat поле choice не имеет.

    2.4.8.3. Поля выбора в feats.yml¶

    Отсутствуют. Ключей choice/options/maxChoices в feats.yml нет (см. 2.4.3.2).

    2.4.9. ЧЕРТЫ И МУЛЬТИКЛАСС¶

    2.4.9.1. Расовые требования к чертам¶

    Отсутствуют в виде валидации. Расовой системы нет (Блок 2.3); prerequisite — свободная строка. Черты с расовым требованием (Elven Accuracy и т.п.) в feats.yml нет.

    2.4.9.2. Требования по классу¶

    Механической валидации нет. Есть строковые prerequisite, близкие к классовым: "Способность творить заклинания" (:35), "Заклинание стихии" (:101), "Заговор с атакой" (:196), "Средняя броня" (:116, :151), "Тяжелая броня" (:121), "Легкая броня" (:156).

    2.4.9.3. Валидируется ли это¶

    Нет. См. 2.4.4.2 и 2.4.5.4. Мультикласс — задел: CharacterState.classLevels (GameState.kt:445), ClassLevelEntry (:548-552). Связи черт с мультиклассом нет.

    2.4.10. ЧЕРТЫ В REST API¶

    • 2.4.10.1. Endpoint получения черт: GET /api/feats → featRegistry.getAll() (LevelController.kt:21-22). Возвращает List<Feat>.
    • 2.4.10.2. DTO черты: отдельного DTO нет — сериализуется сама Feat (FeatRegistry.kt:9-15). Во фронтенде feats?: string[] (frontend/lib/api.ts:264) — это поле CharacterState.feats, не DTO каталога.
    • 2.4.10.3. Endpoint выбора черты: отдельного нет. Выбор передаётся полем featId в POST /sessions/{sessionId}/levelup (SessionController.kt:192-211; LevelUpRequest.featId — LevelUpService.kt:33-39). Фронтенд использует sessionsApi.levelUp(...) (frontend/lib/api.ts:488-489, LevelUpModal.tsx:95).

    2.4.11. ASI vs FEAT¶

    2.4.11.1. Где обрабатывается ASI¶

    • Поле: CharacterState.pendingASI: Int (GameState.kt:406), инвариант >= 0 (:468).
    • Начисление: при GainXp на уровнях 4/8/12/16/19 → pendingASI += 1 (SessionService.kt:1778-1780).
    • Расход: SessionService.allocateASI (:1265-1333) — валидация суммы 2 (:1277-1284), применение к Attributes, пересчёт HP при росте CON (:1311-1316), AC при росте DEX (:1317-1320), pendingASI - 1 (:1327).
    • Endpoint: POST /sessions/{sessionId}/levelup/asi (SessionController.kt:136-154).
    • Фронтенд: CharacterPanel.tsx:338-341 (блок при pendingASI > 0), вызов sessionsApi.allocateASI (:578, api.ts:479-480).

    2.4.11.2. Выбор «ASI OR Feat»¶

    • В ручном пути LevelUpService.levelUp — да: require(hasAsi xor hasFeat) (:108).
    • В пути pendingASI (автоматический level-up) — нет: allocateASI принимает только allocations характеристик (AsiRequest, SessionDtos.kt:105-107), поля featId нет.
    • Фронтенд LevelUpModal.tsx:32 имеет режимы "asi" | "feat" и отправляет featId через onConfirm({ ...base, featId }) (:95), но список фитов захардкожен (см. 2.4.5.6).

    2.4.11.3. Отказ от ASI в пользу черты¶

    В ручном пути: req.asiChoice = null + req.featId != null проходит xor (:106-108), черта добавляется в newFeats (:116), pendingASI = 0 при copy (:270). В автоматическом пути отказа от ASI в пользу черты нет.

    2.4.12. ОТСУТСТВУЮЩИЕ ЧЕРТЫ¶

    2.4.12.1. Сколько черт в SRD (канон)¶

    Эталонного SRD-списка в репозитории нет. Внутренние заявления: feats.yml:62 — «для полноты 42»; frontend/components/game/LevelUpModal.tsx:260 — «12 MVP из 42 SRD». Внешний канонический список в коде не зафиксирован — требует уточнения.

    2.4.12.2. Сколько реализовано¶

    41 запись в feats.yml.

    2.4.12.3. Какие отсутствуют¶

    Внутренне: комментарий заявляет 42 при фактических 41 — расхождение −1. Конкретная «недостающая» черта в репозитории не указана. По внешнему списку SRD (вне репозитория) отсутствует, в частности, mobile; metamagic_adept (вне-SRD) также отсутствует. Точное сравнение с каноном — требует уточнения (эталона в репозитории нет).
