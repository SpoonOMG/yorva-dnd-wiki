    Аудит умений/заклинаний — Блок 2.2: Подклассы (фактура)¶

    2.2.1. КАТАЛОГ ПОДКЛАССОВ¶

    2.2.1.1. Где хранится каталог подклассов¶

    • Реестр: backend/app/src/main/kotlin/com/yorva/classes/SubclassRegistry.kt.

    2.2.1.2. Загрузчик¶

    • Класс: SubclassRegistry — SubclassRegistry.kt:17-65.
    • Метод: @PostConstruct fun load() — SubclassRegistry.kt:24-60.
    • Хранилище: MutableMap<String, Subclass> — SubclassRegistry.kt:22.
    • Доступ: get(id) (:62), getAll() (:63), getForClass(classId) (:64).

    SubclassRegistry.kt:24-35:

    @PostConstruct
fun load() {
    try {
        val res = resourceLoader.getResource("classpath:subclasses.yml")
        if (!res.exists()) {
            logger.warn("subclasses.yml not found")
            return
        }
        val yaml = Yaml()
        val data: Map<String, Any> = yaml.load(res.inputStream)
        @Suppress("UNCHECKED_CAST")
        val raw = data["subclasses"] as? List<Map<String, Any>> ?: emptyList()
    • При отсутствии файла или ошибке парсинга — logger.warn/logger.error и return; список остаётся пустым. Fallback-данных нет (:28-31,57-59).

    2.2.1.3. Структура файла¶

    • Ключ верхнего уровня один: subclasses — список объектов (subclasses.yml:1).
    • Каждый объект подкласса имеет ключи: id, classId, name, description, features.
    • features — список inline-маппингов вида { name, level, description }.

    subclasses.yml:1-12:

    subclasses:
  # Воин
  - id: champion
    classId: warrior
    name: "Чемпион"
    description: "Мастер критических ударов и атлетизма"
    features:
      - { name: "Улучшенный критический удар", level: 3, description: "Крит на 19-20" }
      - { name: "Замечательный атлет", level: 7, description: "+пол PB к проверкам STR/DEX/CON без владения" }
      - { name: "Дополнительный боевой стиль", level: 10, description: "Выберите второй стиль" }
      - { name: "Превосходный критический удар", level: 15, description: "Крит на 18-20" }
      - { name: "Выживший", level: 18, description: "Регенерация 5+CON HP/ход при HP < половины" }

    2.2.2. МОДЕЛЬ ДАННЫХ ПОДКЛАССА¶

    • Модель: data class Subclass(id, classId, name, description, features: List<ClassFeature> = []) — SubclassRegistry.kt:9-15.
    • Поля: id, classId, name, description, features.
    • Поля subclassLevel, spellLists, resource в модели отсутствуют.
    • ClassFeature (общая модель фичи, CharacterClass.kt:51-65):
    • name, level, description,
    • actionType (FeatureActionType?),
    • resourceId (RAGE/KI/BARDIC_INSPIRATION/CHANNEL_DIVINITY/WILD_SHAPE/ACTION_SURGE/SECOND_WIND/LAY_ON_HANDS/SORCERY_POINTS/PACT_SLOTS),
    • usesPerLevel: Map<Int,Int>?,
    • recharge: RestType?,
    • choice: FeatureChoice?.
    • Модель Subclass переиспользует тот же ClassFeature, что и классы.

    2.2.3. ПАРСИНГ FEATURES ПОДКЛАССА¶

    • Парсинг: SubclassRegistry.kt:41-47 — создаётся ClassFeature только с name, level, description.
    • level дефолт 3 при отсутствии (:44).
    • Поля actionType/resourceId/usesPerLevel/recharge/choice — не заполняются (остаются null/default).
    • Итог: все 139 фич подклассов — только текст. Механика не моделируется.
    • В subclasses.yml нет ни одной фичи с choice (grep choice по файлу — 0 строк) → у подклассов нет feature-выборов (в отличие от классов, где есть «Боевой стиль», «Экспертиза»).

    2.2.4. ВЫБОР ПОДКЛАССА¶

    • Подкласс выбирается только на 3 уровне и только если ещё не выбран:
    • Preview: LevelUpService.kt:63 needsSubclass = nextLevel == 3 && state.subclassId == null.
    • LevelUp: LevelUpService.kt:126 needsSubclass = nextLevel == 3 && state.subclassId == null.
    • Проверка принадлежности классу: LevelUpService.kt:130 require(sub.classId == cls.id).
    • Смена запрещена: LevelUpService.kt:132-134.
    • Уровень подкласса хардкод == 3; поля subclassLevel нет ни у Subclass, ни у CharacterClass (CharacterClass — см. 2.1.8).
    • В данных subclasses.yml:94 пометка: «Жрец — домены (канонично на 1, у нас на 3 для униформы, пометка)».
    • Распределение уровней фич подклассов в данных: level: 2 — 3 шт (wizard/druid), 3 — 44, 6 — 20, 7 — 8, 8 — 3, 9 — 3, 10 — 13, 11 — 5, 13 — 3, 14 — 14, 15 — 8, 17 — 8, 18 — 4, 20 — 3.
    • Противоречие: домены/покровители/происхождение обрабатываются в resolveL1Choices (см. 2.2.8) как фичи уровня 1, но выбор самого подкласса происходит на 3. Ниже см. факт в 2.2.8.

    2.2.5. РЕСУРСЫ ПОДКЛАССА¶

    • Инициализация ресурсов — по classId, без учёта подкласса: ClassResourceHelper.initialResources (ClassResourceHelper.kt:10-66):
    • barbarian rage, bard bardicInspiration, cleric channelDivinity, druid wildShape, warrior actionSurge/secondWind, monk ki, paladin layOnHands+channelDivinity, sorcerer sorceryPoints, warlock pactSlots, wizard arcaneRecovery.
    • ranger/rogue/else → пусто (:52-53,64).
    • Подкласс-специфичных ресурсов нет:
    • Нет типа «кость превосходства» (Superiority Dice) — grep superiority по коду = 0 совпадений.
    • ClassResources (GameState.kt) не содержит полей для Superiority Dice / улучшений Wild Shape.
    • Ресурсы инициализируются по полю characterClass.id только.
    • Восстановление ресурсов: ClassResourceHelper.restore (:128-144) — по типу отдыха (SHORT/LONG). Вызывается из SessionService при StateChange.ShortRest (SessionService.kt:1756) и StateChange.LongRest (:1769). RestService.applyShortRest/applyLongRest обрабатывают только HP/Hit Dice/слоты/статусы и ClassResourceHelper.restore не вызывают — восстановление ресурсов идёт отдельным путём через StateChange.
    • Ресурс-фичи в данных: в subclasses.yml ни у одной фичи нет resourceId/usesPerLevel/recharge (см. 2.2.3).

    2.2.6. SPELL LISTS ПОДКЛАССА¶

    • В subclasses.yml нет полей для дополнительных заклинаний подкласса (grep domainSpell|circleSpell|oathSpell|expandedSpell|spells: = 0 строк).
    • Доп. заклинания подкласса зашиты в код, в resolveL1Choices (SessionService.kt:217-244):
    • Домен (life): bless, cure-wounds (:222).
    • Домен (light): burning-hands, faerie-fire (:224).
    • Домен (war): divine-favor, shield-of-faith (:228).
    • Покровитель archfey: faerie-fire, sleep (:234).
    • fiend: burning-hands, command (:235).
    • great_old_one: dissonant-whispers, charm-person (:236).
    • Эти списки попадают в L1ChoiceResult.patronExpandedSpells / domainPreparedSpells (:176,179).
    • Подкласс-списки для остальных (школы волшебника, круги друида, клятвы паладина, домены druid moon/land и т.д.) — в коде не определены.
    • Общий spellList есть у классов в classes.yml (у всех 12 классов), но это список классов, не подклассов.

    2.2.7. ПРИМЕНЕНИЕ ФИЧ ПОДКЛАССА В БОЮ¶

    • TurnResolver обращается к target.features как к множеству строк — но это features монстров (например, armor_heavy, regeneration, enrage, multiattack, poison_strike), не фичи подклассов персонажей — TurnResolver.kt:554,2256,2263,2303,2325.
    • Критические удары — жёстко roll == 20: TurnResolver.kt:364,536,852,921,981,1138.
    • Нет механики «Улучшенный критический удар» (крит 19-20, Champion) — grep improvedCrit|critRange|critOn|19-20|18-20|critThreshold = 0 совпадений.
    • Скрытая атака (Rogue): в бою только текстовая метка (скрытая атака, с преимуществом) — TurnResolver.kt:1499; реального добавления 1d6 к урону в этом фрагменте нет.
    • Фичи fightingStyle (из классов, не подклассов) учитываются: TurnResolver.kt:1430-1432 (archery/dueling), :2279 (defense).
    • Подкласс-фичи подклассов в TurnResolver не применяются (геймплей-эффекты не активируются).

    2.2.8. ДОМЕН/ПОКРОВИТЕЛЬ/ПРОИСХОЖДЕНИЕ ЧЕРЕЗ l1Choices¶

    • L1ChoiceResult (SessionService.kt:171-182): l1Choices, fightingStyle, expertiseSkills, domainId, domainPreparedSpells, extraArmorProficiencies, extraWeaponProficiencies, patronExpandedSpells, draconicHpBonus, draconicAcFloor.
    • resolveL1Choices (:184-259) обрабатывает фичи уровня 1 (l1Features = features.filter { it.level == 1 }, :189) и специально ветвится по именам фич: «Боевой стиль», «Экспертиза», «Домен», «Потусторонний покровитель», «Происхождение чародея» (:209-245).
    • Домен/покровитель/происхождение при этом разрешаются здесь (как фичи L1), а не на уровне 3 (см. 2.2.4 — LevelUp выбирает подкласс на 3). Это две разные ветки логики.
    • domainId сохраняется в состояние (SessionService.kt:175).
    • Эффекты: тяжёлая броня (life/war), владение оружием (war), HP-бонус дракона, AC-флор 13 (draconic) — только в этой ветке.

    2.2.9. REST API ПОДКЛАССОВ¶

    • LevelController.kt:24-42:
    • GET /api/subclasses?classId=&setting= — все или по классу (:24-32).
    • GET /api/classes/{id}/subclasses?setting= — по классу (:34-42).
    • Возвращается полный Subclass, включая features (только текст: name/level/description).
    • Фильтр по классу: getForClass (SubclassRegistry.kt:64).
    • Рескин имени/описания по setting (:28-31,38-41).
    • Отдельного API для выбора подкласса нет — выбор идёт через levelUp (LevelUpService.kt:94+, поле subclassId в LevelUpRequest).

    2.2.10. ВЫБОРЫ ФИЧ ПОДКЛАССА ПРИ LEVEL-UP¶

    • LevelUpService.kt:137-173 — обработка feature-выборов при level-up:
    • Набор фич с choice != null: из cls.features (:141) + из подкласса уже выбранного (:142-144) + из выбираемого сейчас подкласса (:146-148).
    • Для подкласса: subclassRegistry.get(...).features.filter { it.level == nextLevel && it.choice != null } (:143,147).
    • Но т.к. в subclasses.yml у фич choice нет (см. 2.2.3), featuresGainedWithChoice для подкласса всегда пуст → подкласс при level-up никаких выборов не собирает.
    • Валидация входных выборов: :149-173 (количество, допустимые id, отсутствие лишних ключей).
    • Фичи подкласса попадают в featuresGained (text-only) в preview: LevelUpService.kt:67-71.
