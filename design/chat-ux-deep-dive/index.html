    docs/design/chat-ux-deep-dive.md — Глубокая проработка игрового чата¶

    Автор: Visual/UX Designer. Реализация — Frontend Engineer. Открытые вопросы к LLM Engineer/System Analyst/Backend — раздел 8.

    1. Почему это критично¶

    Игровой чат (/sessions/[id]) — единственное место, где пользователь проводит основное время. North-star-метрика продукта — «% дошедших до 10-го хода» (strategy-docs/product-strategy.md §8). Если чат не держит внимание на ходах 1–10, retention не спасут ни лендинг, ни конструктор миров. Это делает чат зоной наивысшего приоритета для UX-инвестиций.

    Аудитория — «геймер из BG3» (25–40, прошёл AAA RPG, ждёт глубины выбора и последствий, устал от «ИИ-обёртки без души»). Для него текстовый интерфейс должен ощущаться как инструмент погружения, а не форма обратной связи.

    2. Аудит текущей реализации¶

    Разобрал components/game/{TurnList,ActionInput,MechanicsStrip,CharacterPanel}.tsx и app/(app)/sessions/[id]/page.tsx. Резюме, что есть:

    • Пузырь действия игрока (справа) + пузырь нарратива ГМ (слева), под нарративом — плоская строка чипов механик (кубики, урон, статусы, XP).
    • Ввод — textarea + кнопка, Enter отправляет.
    • Панель персонажа — статичная карточка справа (HP-бар, статы, инвентарь).
    • Ожидание ответа — курсивный текст «Гейммастер размышляет…».
    • Ошибка — красная плашка под списком, действие пользователя просто исчезает.

    Найденные проблемы (это и есть предмет проработки):

    # Проблема Почему это важно
    1 История ходов живёт только в React state, нет GET эндпоинта для восстановления сессии (api-specification/openapi.yaml — только POST .../turns) Обновление страницы = потеря всего чата. Это ломает доверие мгновенно — критичнее любого визуального дефекта
    2 Нарратив ГМ — «стена текста» без внутренней структуры (нет разделения речи NPC / описания сцены / внутреннего голоса) gm-principles.md требует «конкретику через реплики NPC» — но UI не помогает это прочитать быстрее
    3 Открытые варианты действий (gm-principles.md п.4, ≥2-3 варианта) сейчас растворены в прозе — нет способа быстро выбрать один Каждый ход требует придумать и напечатать текст с нуля — повышает трение именно там, где чаще всего происходит отток (первые 10 ходов)
    4 Бросок кубика показывается как готовый факт (чип с результатом), без ощущения броска Кубики — это культовый D&D-момент; мгновенная плоская цифра не даёт AAA-ощущения
    5 Индикатор ожидания — статичный текст, нет намёка на то, «что» делает ГМ (думает / бросает кубик / применяет эффект) Ответ LLM занимает заметное время; пустое ожидание ощущается медленнее, чем структурированное
    6 При ошибке действие пользователя пропадает, нужно перепечатывать текст Наказывает пользователя за сетевую ошибку — не его вина
    7 Механики (урон, статус, XP) не связаны визуально с панелью персонажа — HP-бар просто перерисовывается Разрывает причинно-следственную связь «получил урон → полоска упала» — теряется ощущение последствий действия (ключевой принцип ГМ: «провал двигает сюжет»)
    8 data-genre токены заведены в globals.css (fantasy/scifi/cyberpunk/horror), но не применяются ни в одном компоненте Жанро-реактивная тема (ключевое отличие продукта, visual-concept.md §4) физически не работает — весь чат сейчас нейтрального цвета независимо от жанра мира
    9 Нет разделения длинной истории на сцены/главы, нет якорей для быстрой навигации назад При 10+ ходах (ровно наша целевая глубина) список превращается в бесконечный неструктурированный поток
    10 aria-live отсутствует, нет объявления нового сообщения для screen reader Базовая доступность чата не соблюдена

    3. Референсы жанра — что берём / что не подходит¶

    Референс Что взять Что не подходит нашей аудитории
    AI Dungeon Минимализм чата, быстрый цикл действие→ответ Нет структурной механики, нет ощущения «правил» — наша аудитория (BG3) ждёт систему, не только текст
    NovelAI Чистая типографика для длинного чтения Полностью убирает игровую механику из UI — нам механика (кубики, HP) — часть AAA-ощущения, её нельзя прятать
    D&D Beyond Визуальная иерархия карточки персонажа, читаемость статов Это лист персонажа не для реал-тайм чата — плотность верна для справочника, избыточна построчно в бою
    Talespire 3D-подсветка результата броска (drama reveal) 3D-движок вне бюджета (visual-concept.md — «нет живого 3D»); переносим саму идею драматизации броска, не технологию

    Вывод: наша ниша — «AI Dungeon по темпу, D&D Beyond по ощущению системы, без 3D-Talespire, но с его чувством драмы броска через 2D-анимацию».

    4. Принципы дизайна чата¶

    1. Действие игрока — всегда видимый, весомый момент. Не теряется в потоке, не исчезает при ошибке.
    2. Механика — прозрачна, но не громче нарратива. Кубики и эффекты поддерживают историю, не конкурируют с ней за внимание.
    3. Каждый ход — ощутимое последствие. Изменение HP/статуса в панели персонажа визуально связано с ходом, который его вызвал (не «само изменилось»).
    4. Трение выбора — минимальное. Если ГМ предлагает варианты — игрок может выбрать в один клик, а не печатать с нуля.
    5. Ожидание — информативно, не пусто. Разные фазы ответа (бросок → эффект → текст) видимы, а не одна и та же надпись 3–8 секунд.
    6. Жанр мира виден в интерфейсе, не только в тексте. Токены data-genre должны реально красить чат.
    7. Долгая сессия читается, а не скроллится вслепую. Визуальные якоря на значимых точках (новый квест, крупный бой, левел-ап).

    5. UX-флоу¶

    5.1 Обычный ход¶

    1. Игрок печатает действие или кликает по предложенному варианту (см. 5.4).
    2. Пузырь действия сразу закрепляется в потоке (оптимистичный рендер, не ждём ответа сервера, чтобы показать).
    3. Начинается фаза ожидания (5.3).
    4. Приходит ответ: сначала обновляется панель персонажа (с анимацией дельты), затем разворачивается нарратив, затем — чипы механик под ним (лёгкая последовательная анимация появления, не одновременная вспышка).

    5.2 Ошибка отправки¶

    • Действие игрока остаётся в потоке с индикатором «не отправлено» (визуально притушенное + иконка предупреждения), а не исчезает.
    • Под ним — компактная плашка «Не удалось получить ответ» с кнопкой Повторить (переотправляет тот же текст без перепечатывания) и Отменить (убирает неотправленное действие).

    5.3 Ожидание ответа (многофазный индикатор)¶

    Вместо одной надписи — короткая последовательность статусов (меняются по таймеру, не привязаны к реальным серверным событиям, т.к. это один LLM-вызов): Гейммастер обдумывает ситуацию… → (через ~2с) Читает историю мира… → (через ~4с) Формулирует ответ…. Если бросок кубика точно будет (эвристика: не для каждого хода) — после ответа сервера сначала проигрывается анимация броска (5.5), потом появляется текст.

    5.4 Предложенные варианты действий¶

    Под последним ответом ГМ — до 3 компактных кнопок-подсказок (если модель дала явные варианты) плюс инпут остаётся всегда доступным для свободного текста. Клик по подсказке подставляет текст в инпут (не отправляет мгновенно — игрок может подправить) либо отправляет сразу, в зависимости от решения в §8.1. Требует структурированных данных от LLM — открытый вопрос, см. §8.1.

    5.5 Драматизация броска кубика¶

    Чип кубика не появляется готовым числом. Короткая (400–600мс) анимация «вращения» значения (случайные цифры сменяются) → фиксация на финальном результате с лёгким акцентом (масштаб/цвет) при крите (natural 20/1).

    5.6 Обратная связь панели персонажа¶

    При ходе, где меняется HP/статус/XP — соответствующий блок в CharacterPanel подсвечивается кратким цветным пульсом (красным при уроне, зелёным при лечении/XP) синхронно с появлением чипа механики в чате. Это единственная связь, которой сейчас physически не существует (проблема #7).

    5.7 Длинная сессия и навигация¶

    • Каждые N ходов (или по триггеру: новый квест, левел-ап, крупный бой) — тонкий визуальный разделитель-веха в потоке (не полноценная «глава», просто лёгкая метка с кратким текстом события).
    • Кнопка «Наверх/к началу сцены» появляется после скролла вниз на N экранов.

    5.8 Восстановление сессии (блокер, не чисто UX)¶

    Без backend-эндпоинта истории это невозможно реализовать честно. UX-требование: при заходе на /sessions/[id] показывать скелетон загрузки истории, а не пустой чат. Зависит от backend, см. §8.2.

    6. Компоненты и состояния¶

    Компонент Состояния, которые нужно предусмотреть
    ActionBubble (действие игрока) default / отправляется (приглушённая, спиннер) / не отправлено (предупреждение + повторить)
    NarrativeBubble default / появление (fade+slide, не мгновенно)
    SuggestedActionChip default / hover / active / disabled (во время ожидания ответа)
    MechanicsChip (кубик) rolling (анимация) / resolved / crit-success / crit-fail
    ThinkingIndicator фаза 1/2/3 (текст меняется), без резких скачков layout
    CharacterPanel — блок HP/статус/XP idle / pulse-damage / pulse-heal / pulse-xp
    SceneMarker (веха) компактная, не кликабельная в MVP (без deep-linking)
    RetryBanner error / retrying (спиннер на кнопке)

    Все состояния должны использовать существующие семантические токены (--c-danger, --c-success, --c-warning, --c-accent) — не хардкодить hex, чтобы жанровая тема (после §8.3) автоматически подхватывалась.

    7. Мобильная адаптация (принципы, не в приоритете реализации)¶

    • Предложенные варианты (5.4) на мобильном — горизонтальный скролл чипов, не перенос строк (экономия вертикального пространства чата).
    • Многофазный индикатор ожидания (5.3) — та же логика, короче текст.
    • Панель персонажа на мобильном уже уходит вниз (column-reverse в текущем CSS) — сохраняем, но добавить свайп-переход между чатом/листом персонажа вместо вечного вертикального стека — отдельная задача, не блокирует текущую.

    8. Открытые вопросы (нужно решение до реализации соответствующей части)¶

    8.1 Структурированные варианты действий¶

    Чтобы показать кнопки-подсказки (5.4), нужны либо: - (a) LLM возвращает отдельное структурированное поле suggestedActions: string[] в дополнение к прозе нарратива, либо - (b) фронтенд/бэкенд эвристически парсит варианты из текста (ненадёжно, противоречит принципу "LLM для сюжета, код для структуры" в rules.md).

    Рекомендация: (a). Это меняет TurnResponse в OpenAPI-спеке и промпт ГМ — нужно подтверждение и передача LLM Engineer + System Analyst (по флоу ролей), не решаю это в одиночку как UX.

    8.2 История сессии (persistence)¶

    Нужен GET /api/v1/sessions/{sessionId} или GET .../turns, отдающий сохранённые ходы. Судя по схеме БД, таблица turns уже существует (0003-sessions.yaml) — данные, вероятно, пишутся, просто не отдаются наружу. Это backend-задача независимо от визуальной проработки, но она блокирует честную реализацию п.5.8 (скелетон загрузки вместо восстановления состояния означал бы обман пользователя, если данных всё равно нет).

    8.3 Применение жанровой темы¶

    Токены data-genre есть, но ничто не выставляет атрибут на <main data-surface="game">. Нужно: (1) где хранится жанр мира — поле в World? По visual-concept.md §5 это открытый вопрос к System Analyst; (2) определяется LLM при создании мира или на каждый заход. Без этого решения жанровая подсветка чата, упомянутая в принципах (§4.6), не может быть реализована — она будет просто «догадкой» на фронтенде без источника данных.

    9. Что осознанно не делаем сейчас¶

    • Голосовой ввод/вывод — не запрашивалось, не в стратегии.
    • Полноценный rich-text/markdown-движок для нарратива — только точечное визуальное разделение речи/описания (п.5.2 аудита), не общий движок форматирования.
    • Deep-linking на конкретный ход/сцену — избыточно до появления persistence (§8.2).
    • 3D/WebGL-анимация броска — плоская 2D-анимация достаточна (visual-concept.md — «нет живого 3D-движка»).

    10. Приоритизация для реализации (предложение)¶

    Из-за объёма предлагаю разбить на итерации, а не делать всё одним PR:

    1. Итерация 1 (чистый фронтенд, без изменения API): многофазное ожидание (5.3), сохранение неотправленного действия при ошибке + повтор (5.2), анимация появления нарратива, драматизация броска (5.5) на основе уже приходящих данных, пульс панели персонажа (5.6), aria-live для чата.
    2. Итерация 2 (требует решения backend/API): восстановление истории сессии (8.2).
    3. Итерация 3 (требует решения LLM Engineer): структурированные предложенные действия (8.1).
    4. Итерация 4 (требует решения System Analyst): применение жанровой темы (8.3).

    11. Критерий готовности итерации 1¶

    • Ошибка хода не уничтожает введённый текст, доступна кнопка «Повторить».
    • Индикатор ожидания меняет текст минимум дважды за типичный цикл ответа.
    • Бросок кубика показывает короткую анимацию перед финальным числом.
    • При изменении HP/XP/статуса соответствующий блок CharacterPanel даёт визуальный пульс синхронно с чипом механики.
    • Новый нарратив анонсируется через aria-live="polite".
    • npm run build проходит.
