    docs/design/character-creation-ux.md — UX экрана создания персонажа (MVP)¶

    Автор: Visual/UX Designer. Реализация — Frontend + Backend Engineer. Продуктовое решение (нарратив vs механика) подтверждено пользователем по согласованию со стратегией (strategy-docs/product-strategy.md §4, §7) — см. раздел 1.

    1. Продуктовое решение (зафиксировано, не пересматривать без запроса)¶

    Вопрос был: полноценная D&D-система классов/рас с механическими способностями, или нарративная идентичность персонажа? Ответ вывели из стратегии, не гадали:

    • Персона A («геймер из BG3», основной сегмент) ждёт нарративной глубины (последствия выбора, память мира), не механической (product-strategy.md §4: «глубина = нарративная, не механическая»).
    • Rules-engine существует для честности последствий (бросок решает исход по-настоящему), не для конструирования билда персонажа — полная система классов/рас с способностями по уровням прямо отнесена к «не входит в MVP» (docs/game-design/rules.md).
    • Раса/класс/фракция должны работать в любом жанре мира (сайфай, хоррор), что исключает фиксированный D&D-список рас (эльф/дворф) — противоречит жанро-реактивности (docs/design/visual-concept.md §4).

    Итог: раса/класс/фракция/история — свободный текст, интерпретируется LLM как контекст персонажа, не создаёт новых механических правил. Единственная механическая часть экрана — распределение атрибутов (см. §3), потому что от них зависят реальные броски (docs/game-design/rules.md — «Проверка характеристики: d20 + модификатор против DC»).

    2. Текущий пробел, который экран должен закрыть¶

    SessionService.create (backend) сейчас создаёт персонажа жёстко: CharacterState(hp = 20, maxHp = 20) — все атрибуты дефолтные (10, модификатор 0), HP не связан с CON. CreateSessionRequest принимает только worldId + characterName. Экран создания персонажа — то, что должно передавать реальные данные вместо хардкода.

    3. Состав экрана¶

    3.1 Нарративный блок¶

    Поле Обязательно Placeholder-подсказка
    Имя да «Как зовут твоего героя?»
    Пол да Мужской / Женский / Не указывать — влияет на выбор силуэта портрета (§3.4), не на механику
    Происхождение/раса нет «Кто он? Человек, изгнанный дух, потомок древнего рода — опиши как хочешь»
    Класс/архетип нет «Чем он владеет? Воин, тень-клинок, механик-изобретатель — не ограничивай себя»
    Фракция/принадлежность нет «Кому он служит или против кого идёт? (необязательно)»
    История (backstory) нет «Пара предложений о его прошлом — мастер будет помнить это»

    Свободные поля не валидируются по содержанию (это не форма с проверкой «существует ли такая раса») — единственная валидация: непустое имя, разумный лимит длины (совпадает с общим подходом к другим текстовым полям в продукте, см. CreateWorldRequest.description). Пол — закрытый выбор (не текст), так как влияет на визуальный выбор силуэта, а не является предметом свободного творчества как раса/класс.

    3.2 Механический блок — point-buy атрибутов (обновлено)¶

    Изменение от первой версии брифа: вместо фиксированного standard array (15/14/13/12/10/8, один шаблон распределения) — point-buy по правилам D&D 5e SRD (docs/game-design/rules.md, обновлено). Игрок распоряжается бюджетом 27 очков свободно, а не просто раскладывает готовый набор чисел — это даёт реальную свободу билда (например, «маг» — высокий Интеллект и низкая Сила, «воин» — наоборот), чего standard array не позволял (набор чисел был фиксирован, менялось только их расположение).

    Таблица стоимости (нелинейная, официальный SRD):

    Значение атрибута 8 9 10 11 12 13 14 15
    Стоимость (очки) 0 1 2 3 4 5 7 9

    Взаимодействие: каждый из 6 атрибутов — блок с текущим значением (старт 8) и кнопками −/+. + увеличивает значение на 1, если это не превышает 15 и в бюджете хватает очков (проверяется по нелинейной стоимости следующего шага, не текущего). − уменьшает, возвращая потраченные очки. Наверху — счётчик «Осталось очков: N из 27», обновляется живо.

    Под каждым атрибутом — живой модификатор ((value-10)/2, округление вниз) — как и раньше, для прозрачности эффекта.

    HP предпросмотр: та же логика — «Здоровье: 10 + модификатор Телосложения = N», обновляется по мере изменения Телосложения.

    Кнопка «Начать игру» активна не при полном распределении бюджета (в отличие от standard array, где распределялись все 6 чисел обязательно) — игрок может не тратить весь бюджет, если не хочет (менее оптимальный, но не запрещённый билд). Валидируется только: каждое значение в [8, 15], суммарная стоимость ≤ 27.

    3.3 Итоговая проверка перед стартом¶

    Компактная сводка (карточка-резюме) перед кнопкой «Начать игру»: имя, один заполненный нарративный тег (класс или раса, что заполнено), 6 атрибутов с модификаторами, HP. Это последний шанс поправить перед тем, как персонаж уйдёт в бой — соответствует принципу «не отправлять непроверяемое сразу».

    3.4 Портретная рамка (BG3-style), MVP-версия¶

    Справа от полей формы (десктоп) — фиксированная рамка портрета персонажа, как в character creation экранах BG3/D&D Beyond. В этом MVP — не генерация, а силуэт-плейсхолдер, зависящий от выбранного пола (§3.1): нейтральный силуэт человека, отличающийся для мужского/женского/«не указывать» (третий вариант — андрогинный/абстрактный силуэт, не про пропуск отображения). Рамка стоит на месте всё время создания персонажа (оба шага), не только на шаге атрибутов — это тот самый визуальный якорь «вот мой герой», который должен присутствовать с первого поля (имени), а не появляться только в конце.

    Технически — статичный SVG/иллюстрация-заглушка (3 варианта по полу), без сетевого запроса. Никакой связи с будущим image-gen пайплайном (docs/game-design/illustrations.md) в этом шаге не создаётся — только визуальное место, куда позже подставится сгенерированный портрет. Формат промпта для генерации (что именно уйдёт в image-модель на основе пола + нарративных полей) — отдельная задача, не в этом MVP (см. §8).

    4. UX-флоу¶

    1. На /worlds клик «Играть» на карточке мира (текущая точка входа) открывает не форму «введи имя» (как сейчас), а полноценный экран/шаг создания персонажа — замена текущего компактного модального окна.
    2. Экран организован как мастер из 2 шагов внутри одного модалього контейнера (не отдельная страница — сохраняем текущий паттерн Modal, но расширяем контент):
    3. Шаг 1 — нарративная идентичность (§3.1).
    4. Шаг 2 — распределение атрибутов (§3.2) + сводка (§3.3). Переключение — кнопки «Далее»/«Назад», без потери введённых данных при возврате.
    5. Отправка → POST /api/v1/sessions с полным пейлоадом → редирект в чат (как сейчас).

    Почему 2 шага, а не всё на одном экране: нарративные поля (много текстовых инпутов) и распределение атрибутов (интерактивный виджет) визуально и когнитивно разные задачи — смешивание на одном экране увеличивает нагрузку именно в точке первого касания игры (риск отказа до первого хода, что прямо противоречит north-star «% дошедших до 10-го хода» — если человек не пройдёт даже создание персонажа, до 10-го хода он не дойдёт вовсе).

    5. Состояния и границы¶

    Состояние Поведение
    Бюджет point-buy превышен (игрок жмёт + при 0 очков) Кнопка + неактивна/не даёт превысить 27; счётчик «Осталось: N из 27» краснеет при 0
    Атрибут на 15 (верхняя граница) Кнопка + неактивна для этого атрибута
    Атрибут на 8 (нижняя граница) Кнопка − неактивна для этого атрибута
    Имя не заполнено / пол не выбран (шаг 1) «Далее» неактивна
    Возврат с шага 2 на шаг 1 Введённые нарративные поля и пол сохраняются
    Ошибка сети при отправке Тот же паттерн, что в чате (docs/design/chat-ux-deep-dive.md §5.2) — не терять заполненные данные, дать повторить

    6. Влияние на нарратив (интеграция с LLM-контекстом)¶

    ContextBuilder.buildUserPrompt уже собирает блоки детерминированно (сеттинг → резюме → факты → ledger → история → действие). Новый блок «Описание персонажа» добавляется сразу после сеттинга мира — то есть до истории ходов, как статичный контекст личности, на которую опирается каждый последующий ход, не только первый. Формат — простой текст (не JSON), состоящий из непустых полей: имя, происхождение, класс, фракция, история. Это не создаёт новых механических правил — LLM использует это так же, как сеттинг мира, для тона и деталей нарратива.

    Это меняет TurnContext (добавить characterDescription: String?) — вопрос к LLM Engineer только по формулировке/месту в промпте, не по решению «делать или нет» (решение уже принято здесь).

    7. Контракт API (что меняется)¶

    CreateSessionRequest в api-specification/openapi.yaml — добавить опциональные нарративные поля, обязательные пол и распределение атрибутов:

    CreateSessionRequest:
  required: [worldId, characterName, gender, attributes]
  properties:
    worldId: ...
    characterName: ...
    gender: {type: string, enum: [male, female, unspecified]}
    origin: {type: [string, 'null']}       # раса/происхождение
    characterClass: {type: [string, 'null']} # класс/архетип
    faction: {type: [string, 'null']}
    backstory: {type: [string, 'null']}
    attributes:
      $ref: '#/components/schemas/Attributes'  # уже существует в схеме

    Attributes уже есть в спеке (используется в CharacterState) — переиспользуем, не создаём новую схему. Backend валидирует point-buy, а не фиксированный набор: каждое значение в [8, 15], суммарная стоимость по SRD-таблице ≤ 27 — если игрок прислал что-то другое (обман через прямой вызов API) — 400.

    SessionService.create — вместо хардкода CharacterState(hp=20, maxHp=20) строит атрибуты из запроса, HP считает по формуле 10 + conMod, сохраняет нарративные поля персонажа и пол.

    8. Открытые вопросы (не решаю в одиночку)¶

    Вопрос Кому
    Точный лимит длины backstory (токенный бюджет контекста ограничен, context-assembly.md — «Сеттинг + резюме»: 300–500 токенов, backstory туда же попадёт) LLM Engineer
    Как пол попадает в будущий промпт генерации портрета (какой конкретно текст/image-модель) — отдельная задача image-gen пайплайна, не этого MVP LLM Engineer / Game Design

    9. Что осознанно не делаем в MVP¶

    • Реальная генерация портрета (image-gen по промпту) — только силуэт- плейсхолдер в рамке (§3.4). Сам image-gen пайплайн (docs/game-design/illustrations.md) — отдельная фича.
    • Проверка «существует ли такая раса в этом мире» (семантическая валидация текста через LLM на этапе создания) — избыточно для MVP, обычная свобода текста без проверки.
    • Механические бонусы класса/расы к атрибутам (например, +2 Сила у «воина») — осознанно нет: это уже механическое углубление, которое стратегия для MVP не обещает (см. §1).
    • Настраиваемое ограничение «остались неиспользованные очки» (мягкое предупреждение, что билд не оптимален) — не блокирует отправку.

    10. Критерий готовности¶

    • Клик «Играть» открывает 2-шаговый экран вместо текущего простого поля «имя».
    • Справа в обоих шагах — портретная рамка с силуэтом, меняющимся по полу.
    • Пол выбирается на шаге 1 (обязательно, 3 варианта).
    • Атрибуты распределяются point-buy: бюджет 27, нелинейные цены SRD, значения 8–15, счётчик остатка очков живёт и блокирует невалидные действия.
    • HP при старте сессии реально вычисляется из CON, а не хардкод 20.
    • Нарративные поля и пол видны в промпте LLM (можно проверить логированием/stub-ответом).
    • npm run build и ./gradlew :app:test проходят.
