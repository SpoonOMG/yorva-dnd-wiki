    Фаза 2 — план реализации ADR-0012…0019 (фундамент эпика)¶

    Working doc (не ADR). Фактура собрана из docs/adr/0011–0019, _REPORT-PHASE-1A.md, docs/phase-1a-plan.md и разведки кода backend/app/src/**. Файл:строка — актуально на 2026-09-22, состояние ФАЗЫ 1a (3 регрессии закрыты).

    Overview¶

    ФАЗА 2 переводит принятые ADR-0012…0019 из «проекта» в код. Это 8 ADR + незакрытые дубли из ADR-0011 (#1/#2/#3/#4/#7) + gap #6 (hitDie ?: 8). Работа декомпозируется на 8 подфаз — по одной на ADR (ADR атомарны и связаны жёстким графом зависимостей; безопасное слияние без разрыва «один коммит = один логический шаг» невозможно). Каждая подфаза закрывает ровно один ADR + сопутствующий дубль ADR-0011.

    Ключевая сложность фазы — смена типа statuses: List<String> → List<StatusId> (ADR-0013) и statusDurations: Map<String,Int> → Map<StatusId,StatusInstance> (ADR-0014): это сквозной breaking-change по всем резолверам и ~20 тестам. Второй по объёму блок — spec-first удаление mana (ADR-0016) с правкой openapi.yaml + фронтенда. Третий — breaking-change SavingThrow.dc (ADR-0017).

    Миграции БД — минимальны: движок в основном «code-defined» (Kotlin-реестры, spells.json, classes.yml), а не табличный. Реальных Liquibase-миграций — 2 (см. ниже).

    Order¶

    Строго по графу зависимостей, каждая подфаза — отдельный мерджабельный коммит с зелёными тестами:

    1. 2.1 Damage — фундамент, ни от чего не зависит, нужен 0013/0019.
    2. 2.2 Condition core — зависит от 2.1 (resistanceToAll, Resolver-паттерн).
    3. 2.3 Lifecycle — зависит от 2.2 (kind).
    4. 2.4 Exhaustion+Rest — зависит от 2.2/2.3 (AdvDisadvantageResolver, pass-order).
    5. 2.5 Mana removal — независим от 2.1–2.4 (можно параллельно, но не раньше из-за spec-first: объём контракт+фронт велик, лучше отдельным этапом).
    6. 2.6 Spell DC — зависит от 2.5 (mana-ветки в resolveSpellOrSummon удалены).
    7. 2.7 XP/LevelUp — независим (свой кластер; можно параллельно с 2.5/2.6, но LevelUpApplier трогает spellSlotsFor/critRange — пересекается с 2.6 по LevelUpService, поэтому после 2.6).
    8. 2.8 Activatable — финал, тянет всё (0012/0013/0016/0017) + закрывает 0011.

    Возможный параллелизм: 2.5∥2.7 (разные файлы), 2.2∥2.5. Но из-за пересечения SessionService/ TurnResolver/GameState в 2.2 и 2.5 — строго последовательно надёжнее.

    Risks (топ-5)¶

    1. Смена типа statuses/statusDurations (0013/0014) — сквозной breaking-change по ~20 тестам и всем резолверам. Митигация: поэтапная миграция (0013 → 0014), unit-тесты реестра статусов.
    2. Spec-first разрыв (0016 K1) — backend/openapi.yaml/frontend меняются одновременно; риск временного рассинхрона UI (mana-бар) с моделью. Митигация: сначала спека, затем backend, затем frontend, один коммит на слой.
    3. Авто-каскад level-up (0018 B2/E1) — общее ядро LevelUpApplier легко рассинхронизировать с ручным путём; ASI-остановка — обязательство для UI. Митигация: unit-тесты ядра на всех классах + Gherkin level-up.feature.
    4. Двойная мутация HP врага (0011 #4) — StateChange.Damage(ENEMY) (мёртвый write-only) vs Enemy.copy(hp). Митигация: консолидация в единую точку строго 1:1 (E1), тест «урон врага применяется один раз».
    5. Схемные Liquibase-миграции (0012/0016) — 2 миграции (item_archetypes.damage_type, item_archetypes.mana_bonus); при spec-first порядке риск рассинхрона схемы и кода. Митигация: миграции атомарно с подфазами 2.1/2.5, проверка на чистой БД.

Истощение L1 даёт помеху на hazard save, хотя должно только L3 (disadvantageSaves).
