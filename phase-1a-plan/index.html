    Фаза 1a — план точечных регрессий движка¶

    Working doc (не ADR, статус Accepted не требуется).

    Overview¶

    Три точечные регрессии правил, найденные аудитом (docs/spell-review/chek-lists/audit/). Реализуются по одной, каждая — маленький коммит. Ни одна не трогает контракт API (все изменения — внутри правил движка и состояния CharacterState/Enemy).

    # Регрессия Суть Сложность Открытых вопросов
    1 tough (Живучий) +2 HP/уровень начисляется неверно/не ретро средняя 2
    2 Improved Critical крит захардкожен == 20, critRange нет средняя 1
    3 Спас врага к спасу врага прибавляется CON игрока средняя 2

    Класс задачи: [flash] (документация/планирование; реализация — позже, по модели по каждой регрессии отдельно).

    Order¶

    Рекомендуемый порядок реализации — по возрастанию открытых вопросов:

    1. #1 tough — самодостаточно, канон однозначен (SRD), данные не трогает БД.
    2. #2 Improved Critical — одно новое поле critRange + 2 крит-точки в TurnResolver.
    3. #3 Спас врага — требует решения по источнику данных (SA / Game Design), делается последней.

    Regression #1 — tough (Живучий)¶

    Что нужно¶

    Канон (SRD, feat Tough): максимум HP увеличивается на +2 за каждый уровень, ретроактивно (включая уровни, прожитые до взятия черты). Далее +2 на каждом новом уровне.

    Текущее состояние (file:line)¶

    • backend/app/src/main/kotlin/com/yorva/leveling/LevelUpService.kt:187-196 — в levelUp:
    • if (req.featId == "tough") hpDelta += 2 * nextLevel (:188-193) — начисляет +2*nextLevel только в момент взятия; комментарий в коде фиксирует путаницу с двойным счётом.
    • else if ("tough" in newFeats) { } (:194-196) — пустая ветка: на последующих уровнях (когда tough уже в state.feats) +2 не начисляется.
    • Ретро-трекера уровня взятия нет.
    • LevelUpService.kt:360-363 — hpDeltaFor (для preview) возвращает только avgHitDie + conMod, вообще не учитывает tough → preview расходится с actual.
    • LevelUpService.kt:117-119 — момент взятия черты: newFeats = newFeats + feat.id.
    • Авто-каскад StateChange.GainXp (ADR-0018 E1) не обрабатывает feats — SessionService.kt:2188-2219 (см. audit-05:2.4.A / 2.4.J).
    • GameState.kt:453 — feats: List<String> есть; отдельного трекера tough нет.

    Связь с ADR¶

    • ADR-0018 C3 — единая HP-формула avgHitDie + conModAfter + ретро-CON (avgHitDie: d6=4/d8=5/d10=6/d12=7; ретро-CON (conModAfter - conModBefore) * level).
    • ADR-0018 B2 — единое ядро LevelUpApplier.applyLevelUp (два пути: ручной/авто).
    • ADR-0003 — clockwork детерминированная механика (без броска HP).

    Файлы¶

    • backend/app/src/main/kotlin/com/yorva/leveling/LevelUpService.kt (:175-201, :360-363).
    • backend/app/src/main/kotlin/com/yorva/sessions/SessionService.kt (:2188-2219 — GainXp).
    • backend/app/src/main/kotlin/com/yorva/rules/GameState.kt (:453 — feats; возможно новый трекер).

    Подход (вариант)¶

    Унифицировать прирост HP в одном источнике, вызываемом и из preview, и из levelUp, и из GainXp: 1. базовый: avgHitDie + conModAfter; 2. ретро-CON (уже есть, :182-186); 3. tough: если "tough" in newFeats → +2 за новый уровень; при первом взятии — ретро +2 * (уровней до взятия). Для ретро нужен либо трекер (toughTakenAtLevel: Int?), либо формула «при взятии начислить 2 * (nextLevel - 1) сверх +2 текущего уровня». Решение — за реализующей ролью (Backend), согласовать с ADR-0018 C3.

    Тесты¶

    Gherkin (русский) в component-tests/ + unit: - tough на ASI-уровне → +2*level суммарно, без двойного счёта; - следующий уровень после tough → avg + con + 2; - preview.hpDelta == фактическому hpDelta из levelUp; - авто-каскад GainXp с уже взятой tough → +2.

    Риски¶

    • Двойной счёт (уже отражён в комментариях :189-193).
    • Рассинхрон preview/actual (hpDeltaFor не учитывает tough).
    • Миграция существующих персонажей с уже взятой tough (нужен ли ретро-пересчёт HP?).

    Оценка сложности¶

    Средняя (логика + консистентность двух путей ручной/авто).

    Regression #2 — Improved Critical (Улучшенный критический удар)¶

    Что нужно¶

    Подкласс Чемпион (subclasses.yml:7-8, :11): на 3 уровне крит 19-20, на 15 — 18-20. Поле critRange в состоянии персонажа; крит = attackRoll >= critRange.

    Текущее состояние (file:line)¶

    • critRange в коде отсутствует (0 вхождений); в LevelUpService не вычисляется/не хранится.
    • backend/app/src/main/resources/subclasses.yml:7-8 — «Улучшенный критический удар, level 3, крит на 19-20»; :11 — «Превосходный, level 15, крит на 18-20».
    • TurnResolver.kt — крит всегда == 20, всего 21 место (см. отчёт). Боевые криты с удвоением урона — ровно 2:
    • :813 (resolveAttackCatalog) — val crit = attackRoll == 20; :828 hit = crit || ...; :831 critDoubles.
    • :1713 (resolveAttack) — val crit = attackRoll == 20; :1751 hit; :1755 critDoubles.
    • Остальные 19 мест — не криты: авто-попадание/авто-успех (roll == 20 для проверок, спасбросков, death save, social) — их Improved Critical НЕ меняет.

    Связь с ADR¶

    • ADR-0018 B2 — critRange вычисляется в едином ядре levelUp (при выборе подкласса Champion на L3 / апгрейде на L15).
    • ADR-0012 — damage resolver (крит влияет на урон — без изменения контракта).

    Файлы¶

    • backend/app/src/main/kotlin/com/yorva/rules/GameState.kt:338-510 — добавить critRange: Int = 20.
    • backend/app/src/main/kotlin/com/yorva/leveling/LevelUpService.kt — при levelUp: если subclassId == "champion" и level >= 3 → 19; >= 15 → 18.
    • backend/app/src/main/kotlin/com/yorva/rules/TurnResolver.kt:813, 828, 831, 1713, 1751, 1755 — заменить attackRoll == 20 на attackRoll >= character.critRange.

    Подход (вариант)¶

    1. Поле critRange: Int = 20 в CharacterState (инициализация по умолчанию сохраняет обратную совместимость со старыми сессиями).
    2. В LevelUpService.levelUp после обработки подкласса пересчитать critRange по subclassId + level.
    3. В TurnResolver заменить crit = attackRoll == 20 на crit = attackRoll >= character.critRange в двух точках :813, :1713.

    Тесты¶

    • Champion L3: roll 19 → крит (удвоение урона), roll 18 → нет.
    • Champion L15: roll 18 → крит.
    • Не-Champion / Champion L<3: critRange == 20, roll 19 → нет.

    Риски¶

    • Перепутать 21 место (auto-hit/auto-success) с критом — менять только :813, :1713.
    • Spell attack (resolveSpellOrSummon:1897) и специальные атаки (resolveSpecialAttack) тоже могут критовать в 5e — открытый вопрос (см. отчёт).
    • Смежно sneakDice (audit-03:2.2.18) — out of scope этой фазы.

    Оценка сложности¶

    Средняя (новое поле + широкий, но локальный разброс по TurnResolver).

    Regression #3 — Спасбросок врага использует CON игрока¶

    Что нужно¶

    Спасбросок врага (в т.ч. против оглушающих статусов в начале хода) должен использовать модификаторы врага, не игрока. В 5e: d20 + ability_mod врага (+ proficiency).

    Текущее состояние (file:line)¶

    • TurnResolver.kt:2683-2688 (applyEnemyTurn):
    • :2687 saveTotal = saveRoll + character.effectiveAttributes.conMod + enemy.statusSaveBonus — прибавляется conMod игрока.
    • :2698 отображение modifier = character.effectiveAttributes.conMod.
    • Несогласованность: SavingThrowResolver.kt:62-86 (resolveEnemySave) для спасов от заклинаний использует только enemy.statusSaveBonus (без ability mod) — два разных расчёта.
    • Enemy (GameState.kt:682-725) НЕ имеет ability-модификаторов (conMod/strMod/…).
    • creature_archetypes (таблица БД, 0036-creature-archetypes.yaml) НЕ имеет ability-колонок — только save_bonus_vs_status (boss=4, epic=6; остальные 0). ArchetypeRow — CatalogService.kt:297-333.

    Связь с ADR¶

    • ADR-0019 I1 — enum Ability + AbilityResolver.resolveAbility (единый резолв ability) — механизм для ability-модификаторов.
    • ADR-0017 H2 — единый proficiencyBonus.
    • ADR-0011 — single source of truth: устранить дубль двух расчётов спаса врага (resolveEnemySave vs inline в applyEnemyTurn).

    Файлы¶

    • backend/app/src/main/kotlin/com/yorva/rules/TurnResolver.kt:2683-2698.
    • backend/app/src/main/kotlin/com/yorva/rules/SavingThrowResolver.kt:62-86.
    • backend/app/src/main/kotlin/com/yorva/rules/GameState.kt:682-725 (добавить attributes: Attributes в Enemy).
    • backend/app/src/main/kotlin/com/yorva/catalog/CatalogService.kt:297-333 + liquibase-миграция 0036-creature-archetypes.yaml (если добавляем ability-колонки).

    Подход (варианты, решить на SA/Game Design)¶

    1. Добавить ability-колонки в creature_archetypes (новая liquibase-миграция) → Enemy.attributes → спас врага от ability врага.
    2. Выводить conMod врага детерминированно из ранга/уровня (без миграции).
    3. Минимально: убрать character.effectiveAttributes.conMod (заменить на вражий источник либо 0) — но это не полноценный спас.
    4. Рекомендация: унифицировать оба расчёта через SavingThrowResolver.resolveEnemySave, прокинув ability-модификатор врага как вход. Источник данных — открытый вопрос.

    Тесты¶

    • Спас врага против статуса НЕ зависит от CON игрока (фиксируем enemy-источник, меняем CON игрока → результат неизменен).
    • resolveEnemySave и inline-расчёт в applyEnemyTurn дают согласованный результат.

    Риски¶

    • Решение по источнику данных (миграция БД vs derivation) — блокирует точную реализацию.
    • Влияние на баланс: у boss/epic уже save_bonus_vs_status = 4/6; добавление ability mod усилит их спас — согласовать с Game Design.

    Оценка сложности¶

    Средняя (данные + унификация двух расчётов).

    Dependencies¶

    • 1 и #2 обе пишут в LevelUpService (HP и critRange в едином ядре levelUp) — можно объединить.¶

    • 2 и #3 обе пишут в TurnResolver, но в непересекающихся местах (:813/:1713 vs :2687).¶

    • 3 зависит от решения по источнику ability-модификаторов врага (SA / Game Design) — делается последней.¶

    • Общая зависимость: ADR-0018 B2 (LevelUpApplier.applyLevelUp) — единая точка для #1/#2.

    Out of scope¶

    • #4 mana vs slots — эпик, реализация ADR-0016 — вне этого цикла.
    • sneakDice (audit-03:2.2.18) — смежен с #2, но не входит в эту фазу.
    • Реализация AbilityResolver (ADR-0019 N1) — ФАЗА 2; здесь только enum Ability как точка опоры для #3.
    • ФАЗА 2+ не планируется.
